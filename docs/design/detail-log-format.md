# 生データの保存形式（設計案）

> 状態：**提案**。未実装である。
> 元データを消さない試作（ジャーナルと断片を今の `raw_lines` と並べて書き、突き合わせる）から始める。移行と削除は、障害注入の試験で欠落と重複がないことを確かめてから入れる。
> 数値は、利用者の実データ（10-19 の 1 日分）の端末外の複製で測った集計値である。座標や中身は含まない。
> 計測のコード、条件、依存の版は [`tools/detail-log-bench/`](../../tools/detail-log-bench/) にある。時間はすべてデスクトップ（OpenJDK 17、x86-64、C 実装の圧縮器）での経過時間（wall-clock）であり、端末（Pixel 8a）では 2〜4 倍遅いと見込む（推定）。端末での計測は試作で行う。

## 課題

生データ記録は、GNSS の観測値、航法メッセージ、衛星の状態、NMEA、測位、IMU（加速度、ジャイロ、磁気）を記録する。
今は GnssLogger 形式の 1 行を SQLite の `raw_lines(time, line)` に入れ、日のアーカイブで型付きの Parquet に変換している。

- **大きい。** 4.5 時間の最高精度（Max）を含む 1 日が 645 万行、データベースが 728 MB になった。最高精度は 1 時間 157 MB である。
- **変換でメモリが尽きる。** 1 日分を読んで変換し、OOM で落ち続けて 1 日分の位置が失われた。今の `ParquetReader.readFile` も IMU 1 日分で 935 MB のヒープを使い、512 MB では OOM になる。書き出し（`Exporter`）、月の統合、`ArchiveStore.read` も 1 日分以上を配列に読む。
- **記録の経路が重い。** 1 行ごとに文字列を作り、SQLite に 1 行ずつ入れる。書き込みは共有の I/O executor に並び、アーカイブの処理の後ろで待つ。
- **黙って捨てている行がある。** `Archive.tableFor` は `Fix` 行を扱わない。10-19 の 14,710 行は、アーカイブの時点で消えた。

保存形式は GnssLogger 互換でなくてよい（GnssLogger 形式は書き出しで作る）。
記録したデータを失わないことを最優先とし、データ効率、処理性能、頑健さの順に評価する。

## 要件

| 要件 | 内容 |
| --- | --- |
| 損失（通常時の目標） | プロセスの死で 2 秒以内、カーネルの停止や電源断で 32 秒以内 |
| 損失（障害時の保証） | 時間の上限は保証しない。失った範囲（ジャーナルごとの `seq` の隙間と末尾、時刻）を必ず台帳に記録し、LifeLog と端末診断に出す。黙って失わない |
| 確定と削除 | 入力（ジャーナル、`raw_lines` の行、テキスト、断片、古い世代）は、それを含む出力が耐久化され、台帳（`synchronous=FULL`）に確定した後にだけ消す。再実行で重複しない。読んでいるファイルは消さない |
| メモリ | バイト数と行数で上限を決める。どの呼び出し側も 1 日分を配列に読まない |
| 記録の経路 | 1 サンプルあたりの割り当てが 0、書き込みは 2 秒ごと、fsync は 30 秒ごと |
| 容量 | 最高精度で 1 時間 12 MB 以下、生データで 1 時間 8 MB 以下 |
| 同期 | 当日分を断片で送れる（v2 の object と commit が前提）。日の世代が正本である |
| 書き出し | GnssLogger 形式を時間窓ごとにストリームで作る |
| 互換 | 既存の `raw_lines` と既存の Parquet を読み、移行できる |

### 時間軸

| 項目 | 実測 |
| --- | --- |
| IMU の実際のレート | 要求 100 Hz に対して Accel と Gyro は 119.2 Hz、Mag は 100.0 Hz。要求 50 Hz に対して 59.6 Hz と 50.0 Hz |
| レートの変化 | 区間の途中では 256 サンプルの窓 7,648 個のうち 7 回。ほぼ区間の境界にある |
| ジッタ（`elapsedRealtimeNanos` の間隔） | p5〜p95 で ±21〜28 µs、標準偏差 15〜22 µs |
| 欠落 | 間隔の 2.3〜3.2% が周期の約 2 倍。100 ms を超える空きは区間の境界の 18 回 |
| 重複と逆行 | センサーごとの `elapsedRealtimeNanos` は重複 0、逆行 0 |
| Accel と Gyro | Gyro の 97.3% は Accel と `elapsedRealtimeNanos` が一致するが、`time` まで一致するのは 75.0% |
| IMU の `time` | 配送時の壁時計からサンプルの経過を引いた値（下記）。`elapsedRealtimeNanos` との差が 10 分の中で p50 3 ms、最大 17 ms 揺れる |
| GNSS のエポック | 1 Hz。`TimeNanos` の間隔の揺れは ±1.3 µs。`TimeNanos` の逆行が 15 回（時計のリセット） |
| GNSS の配送の遅れ | コールバック時の壁時計は、GNSS 時刻から求めた UTC より p50 1.7 s 遅い（p1 0.6 s、p99 1.8 s） |
| NMEA | 時刻の 95% が直前と同じ（1 エポックの文がまとめて届く） |

ns の時刻を可逆に保つ費用は、正規分布のエントロピーから 1 サンプル約 16 bit が下限である。
時刻の列の符号を比べた（1 サンプルあたりの bit。128 値のブロックの FOR bit-packing と zigzag + varint の小さい方）。

| 系列 | 差分 | 2 階差分 | 周期の残差 | 32 値の直線の残差 |
| --- | ---: | ---: | ---: | ---: |
| Accel、Gyro の `elapsedRealtimeNanos` | 17.2 | 18.0 | 17.1〜17.2 | 17.0 |
| Mag の `elapsedRealtimeNanos` | 17.5 | 18.6 | 18.1 | 17.1 |
| エポックの `TimeNanos` | 10.2 | 8.3 | 17.6 | 11.7 |
| エポックの `utcTimeMillis` | 9.3 | 9.0 | 9.4 | 8.9 |

IMU は周期のまわりに揺れるので 2 階差分は差分より悪く、格子と例外の方式も成り立たない。
差分 + FOR は全系列で最良から 2 bit 以内であり、Parquet の `DELTA_BINARY_PACKED` で足りる。

### 列

| 列 | 実測 | 意味 |
| --- | --- | --- |
| IMU の値 | 前の値と同じは 1〜7%。zstd 3 で 1 値 12.8〜19.4 bit | 較正後の値で雑音が多い |
| IMU の整数カウント | 最頻の刻みの整数倍に正確に戻るのは 0〜0.9%（Gyro は 0.01 刻み以内に 68〜75% が寄るが、刻みが揺れる） | 整数に戻せない |

| 信号ごとの系列 | 信号は 118 個。`State` の 99%、`ReceivedSvTimeUncertaintyNanos` の 75% が同じ信号の前の値と同じ | 信号ごとに並べる |
| 衛星の状態 | C/N0、方位、仰角は小数 1 桁 | Float32 で可逆 |

| NMEA | GSV が 40%、GSA が 25% のバイト。zstd 3 で 9.0 分の 1 | 文のまま圧縮する |

## 形式の比較

### 条件

すべての表（下の schema 4）を、到着順の 10 分の断片に分け、断片ごとに 1 つの row group で書いた（`measure.py`）。
断片の中の並びは設計どおりである（IMU は `ern`、信号と衛星は信号ごと、他は `seq`）。
Parquet は pyarrow で書き、整数は `DELTA_BINARY_PACKED`、float は PLAIN、文字列は辞書（`message` と `Data` を除く）とした。
「自前のチャンク」は、同じ断片の同じ列に最良の変換（差分、2 階差分、FOR、XOR、byte split、ALP）と zstd 3 をかけた列の大きさの和（列ごとに 16 B を足す）であり、**推定**である。書いて読み戻した完全な形式ではない。
断片は時刻の窓だけで切った（エポックは移行の規則で判定し、その最初の行の断片にまとめる）。測ったレートでは、行数の上限（IMU は 10 分で最大 71,502 行）と 16 MiB には届かない。pyarrow は schema 4 の key-value metadata を書かない（1 ファイル数百 B の差と見込む）。
gzip の水準は 9（pyarrow の既定）である。
行形式とデータベースは 1 日分の表を到着順で書いた（`survey.py`）。

### 記録の経路

1 サンプルあたり、デスクトップの JVM での経過時間（`jvm/Bench.scala`、`jvm/Proto.scala`）。試作はフレームのヘッダと CRC を書かず、fsync の行はフレームごとに fsync した値である。

| 方式 | CPU | 割り当て | fsync |
| --- | --- | --- | --- |
| 今（テキスト + SQLite） | 文字列化 267 ns + INSERT（端末で 2〜5 µs と推定） | 608 B + 時刻の切り出し | WAL の同期の設定しだい（未確認） |
| 記録器が今の writer で Parquet を直接書く | 2.2 µs | 1.7 KB | – |
| ジャーナル（試作、無圧縮） | 54 ns（`write()` を含む） | 0.06 B（実質 0） | 30 秒ごと |

ジャーナルの割り当て（0.06 B、計測の誤差の範囲）は、試作の IMU の符号化部分だけの値である。
センサーの配送、`LoggerState` の更新、文字列を持つ系列（NMEA、航法メッセージ）、バッファの拡張は含まない。端末での割り当て、最大メモリ、fsync の遅れは試作で測る。
フレームを Deflate 1 で圧縮すると IMU は 95.0 MB から 65.2 MB に縮むが、CPU は 373 ns になる。
短いフレームはよく縮まない（zstd 3 で 1 秒のフレームは 73.2 MB、600 秒は 47.9 MB）。
記録の経路では圧縮せず、断片で圧縮する。
fsync は 1 回 約 2 ms だった（デスクトップの NVMe）。

### 案の検証

| 案 | 判定 | 根拠 |
| --- | --- | --- |
| IMU を整数カウントに戻す | 不採用 | 正確に戻るのは 0〜0.9% |
| 十進の float を整数化（ALP） | 保留 | GNSS の表は、ALP を含む列ごとの変換で 1 時間 0.8〜1.1 MB 縮む。Parquet の中で整数化した列（C/N0 × 10 など）にする案を後で比べる |
| 信号ごとの系列 | 採用 | 断片の中の並びとして |
| エポックの共通の列を 1 回 | 採用 | `gnss_epoch` |
| 公称周期 + 残差、格子と例外 | 不採用 | 差分より 1% しか縮まない。揺れが周期の 0.3% ある |
| 差分 + FOR | 採用 | `DELTA_BINARY_PACKED` |
| 学習した zstd の辞書 | 不採用 | NMEA の 1 分の断片で悪化した（初回の計測。計測のコードは残していない） |
| ADR、受信時刻の予測 | 保留 | 1 時間 0.1 MB 未満（初回の計測。コードは残していない）。2 実装で浮動小数の計算を揃える費用に見合わない |
| 追記専用のジャーナル + CRC、write と fsync の分離、ホットとコールドの 2 段、日 = 断片の連結 | 採用 | 下記 |
| 自前のコールドの形式 | 不採用 | 5〜13% の差に、仕様、版、fuzzing、JVM と WASM の 2 実装の費用が見合わない |

## 推奨

記録の経路はジャーナル（自前、端末の外に出ない）、確定した後は Parquet（schema 4、gzip 9）とする。

| 段 | 形式 | 書く側 | 寿命 |
| --- | --- | --- | --- |
| ジャーナル | 追記専用のフレーム | 記録のプロセス | 断片が台帳に確定するまで |
| 断片 | Parquet、日付と表ごとに 1 ファイル。row group は圧縮後 4 MiB 以下（通常は 1 つ） | 確定のプロセス | 日の世代に含まれるまで |
| 日の世代 | Parquet、表ごとに 1 ファイル。row group は断片をそのまま写す | 確定のプロセス | 次の世代に置き換わるまで |

生データの表は月の統合をしない。1 日のファイルが既に大きく、月のファイルは 1 GB を超えうる。

## schema 4

### 共通の規則

- 版は Parquet の footer の key-value metadata に置く：`ashidori.schema`（`4`）、`ashidori.table`、`ashidori.inputs`（断片は入力の ID、世代は含む断片の ID の一覧）、`ashidori.generation`、`ashidori.rowgroups`（row group ごとの `src` と入力の `seq` の範囲）。今の writer は key-value metadata を書かないので、それがないファイルは schema 3 以前であり、表は旧い表名（`gnss_raw`、`imu` など）で分かる。
- 型は Android API の型に合わせる。`Str` は UTF8 の converted type を持ち、`Binary` は持たない（reader は converted type で区別する）。
- 値がない（`has*()` が偽、API が返さない）ときは null とする。値としての NaN は NaN のまま書く（今の writer は NaN を null にするので、schema 4 では変える）。schema 3 以前のファイルでは、NaN と値なしはどちらも null である。
- 先頭の列は時刻（ms）である（`ArchiveStore.read` と復元器の約束）。
- `src` は入力の元（ソース）の ID である。台帳の `AUTOINCREMENT` で採番し、再利用しない。ソースはジャーナル、凍結した `raw_lines` の表、旧い形式のテキストファイルのどれかで、作った順に番号が増える。
- `seq` はソースの中の位置である。ジャーナルではイベントの連番（ジャーナル全体で 1 つの数列。イベントは 1 回のコールバック：IMU の 1 サンプル、1 エポックの全観測値、1 回の衛星の状態、1 つの文やメッセージ、1 回の測位）、凍結した表では rowid、テキストでは行の先頭のバイト位置である。`(src, seq)` は端末で一意である。
- 移行したエポックは、その最初の `Raw` 行の `seq` を ID とする。移行のバッチはエポックの途中で切らない。
- 断片の中の並びは表ごとに決める（下表）。表とソースをまたぐ順は `(time, src, seq)` とする。

- **エポックの結合：** `gnss_signal` は `(src, seq)` で `gnss_epoch` に結ぶ。`TimeNanos` はデータとしてだけ持つ（リセットをまたいで一意でない）。
- **IMU の `time`：** 今の記録器の式をそのまま使う：コールバックの中で `System.currentTimeMillis() − (SystemClock.elapsedRealtimeNanos() − event.timestamp) / 10⁶`（ms、切り捨て）。壁時計の補正（NTP、手動）をそのまま受け、配送の揺れを含む。`ern` は `event.timestamp` であり、起動ごとに 0 から数える。断片は 1 つのジャーナル、つまり 1 回の起動の中にあり、起動をまたぐ並びは `time` で決める。新しい時刻の定義（基準の時刻からの計算）は、精度を測るまで採らない。
- **Accel と Gyro は別の表にする。** 時刻が違う組があるので、1 行にすると旧データを可逆に移せない。
- **`gnss_nav` の `time`：** 新しい記録ではコールバック時の壁時計、移行した行では今と同じく直前の記録の時刻である。
- 記録器が書いていない列（`CarrierCycles`、`CarrierPhase`、`CarrierPhaseUncertainty`、Fix の `NumberOfUsedSignals` など）は持たない。書き出しでは空の欄にする。
- `raw` の鍵の種別と送信の区分に、これらの表をすべて加える（[鍵の階層](key-hierarchy.md) の種別の表）。

## ジャーナル

### ファイル

| 項目 | 内容 |
| --- | --- |
| 名前 | 書いている間は `detail/journal/<src>.open`、閉じたら `<src>.ajl` |
| 作成 | ファイルを作って先頭を書き、fsync し、ディレクトリを fsync してから、サンプルを入れる |
| 先頭 | magic `ASHJ`、版、`src`、起動の識別子（`BOOT_COUNT`）、作成時の壁時計と `elapsedRealtimeNanos`、schema の ID、機種。CRC32C |
| 閉じ方 | CLOSE フレームを書き、fsync し、名前を `.ajl` に変え、ディレクトリを fsync する |
| 切り替え | 10 分ごと（壁時計の 00、10、…分）、日付の境界、記録の停止、16 MiB に達したとき、いずれかの表の行数が上限（下記）に達したとき |
| 排他 | 書き手はファイルロックを持つ。確定のプロセスは `.ajl` だけを読む |

### フレーム

| 欄 | 大きさ | 内容 |
| --- | --- | --- |
| magic | 4 | `AJF1` |
| len | 4 | ヘッダを含むフレームの長さ。36 以上 1 MiB 以下 |
| type | 1 | DATA、LOSS（捨てたイベントの範囲）、CLOSE |
| series | 1 | Accel、Gyro、Mag、GNSS 観測値、衛星の状態、航法メッセージ、NMEA、測位 |
| flags | 2 | 予約 |
| frame_seq | 8 | ジャーナルの中の連番。0 から 1 ずつ |
| first_event | 8 | 最初のイベントの `seq` |
| crc32c | 4 | フレーム全体（この欄を 0 にして）に対する CRC32C |
| events | 可変 | イベントの列。各イベントの `seq` は前のイベントからの差分（varint。系列ごとのバッファなので飛ぶ）。値は列ごとに、時刻は zigzag + varint の差分、他は API の型の bit のまま |

- 1 つのイベントは 1 つのフレームに収める。GNSS の 1 エポック（時計と全観測値）は 1 イベントなので、`gnss_epoch` と `gnss_signal` の行は同じフレームで確定し、片方だけが残ることはない。
- 系列ごとに事前確保のバッファを 2 面持ち、専用のスレッドが 2 秒ごとに入れ替えて `write()` する。共有の I/O executor は使わない。fsync は 30 秒ごとと停止時に行う。
- `write()` が途中で失敗したら、最後の完全なフレームの終わりまで `ftruncate` してから書き直す。読む側は `frame_seq` の重複も拒む。

### 損失の追跡

`seq` はジャーナルごとに 1 から隙間なく振り、先頭の `seq` をジャーナルの先頭に書く。
系列ごとのバッファから書くので、ファイルの中では系列をまたいで順が入れ替わる（Accel の `seq` = 10 が書かれる前に、GNSS の `seq` = 11 が書かれることがある）。
このため「残った最後のイベントより後」だけでは失った範囲を表せない。
失った範囲は、ファイルを走査して次の 2 つを求める。

- **隙間：** 先頭の `seq` から、ファイルにある最大の `seq` までのうち、ファイルにない `seq`。
- **末尾：** ファイルにある最大の `seq` より後。

`seq` は隙間なく振るので、失ったイベントは必ずどちらかに入る。
バッファから捨てたイベントも、その LOSS フレームを失ったイベントも、隙間として見つかる。LOSS フレームは原因（捨てた）を添えるだけである。
「先頭から隙間なく揃っている最後の `seq`」が、全系列を通じた連続保存済みの位置である。

| 量 | 意味 | 出し方 |
| --- | --- | --- |
| 最後に `write()` が成功した `frame_seq` と時刻 | プロセスの死で残る位置 | 端末診断 |
| 最後に fsync が成功した `frame_seq` と時刻 | 電源断で残る位置 | 端末診断 |
| 未保存の時間 | いちばん古い未書き込みのイベントからの経過 | 10 秒を超えたら端末診断、30 秒を超えたら通知 |
| 捨てたイベント | バッファの上限を超えた分の `seq` の範囲と時間 | LOSS フレーム（原因の記録。範囲は走査でも求まる） |
| 失った範囲 | ジャーナルごとの隙間と末尾（`src`、`seq` の範囲、時刻の範囲）。隙間は「失った」、書き手が死んだジャーナルの末尾は「失った可能性がある」として分けて記録する。正しく閉じたジャーナルには末尾の記録を作らない | 確定のとき、子と manifest と同じトランザクションで台帳に書く。回復のときは閉じる前にも書き、再起動の時刻を添える。LifeLog（新しい種別）、60 秒を超えたら通知 |

失った範囲を台帳に書くのは確定のときであり、これだけで欠けなく覆える（形式モデルで確かめた）。
回復が閉じる前に書く記録は、末尾の時刻の範囲（最後のイベントから再起動まで）を残すためである。
回復の順序：ジャーナルを走査して壊れた末尾を切る → 失った範囲を台帳に確定する → fsync して CLOSE を書き、閉じる。
回復の途中で落ちても、ジャーナルは `.open` のまま残るので、次の起動で同じ回復をやり直す。
通知と端末診断は、起動のたびに台帳から作る。

### 破損

検査：magic、`len` の範囲とファイルの大きさ、CRC、`frame_seq` が前のフレームの次であること。

- **末尾の破損**（不正なフレームの後に有効なフレームがない）：書き込み途中の電源断とみなす。不正なバイト列を `detail/quarantine/<src>.tail` に写し、そこで切る。失った可能性のある範囲を台帳に記録してから閉じる。
- **末尾以外の破損**（不正なフレームの後に、magic を探して有効なフレームが見つかる。または `frame_seq` が飛ぶ）：原本を `detail/quarantine/<src>.ajl` にそのまま残し、有効なフレームだけで断片を作る。失った範囲を記録し、端末診断に出す。隔離した原本は自動では消さない。

## 確定と削除

### 台帳

台帳は別のデータベース `detail-ledger.db` に置く。

- `journal_mode=WAL` かつ `synchronous=FULL` とする。WAL の `NORMAL` は電源断で直前の commit が戻りうる。
- 起動のたびに両方の値を読み戻して確かめる。違えば（または開けない、整合性の検査に失敗したら）入力の削除を止める。出力は作り続け、入力は残し、端末診断に出す。
- 1 回の確定の手順のどれかが失敗したら、その回は何も消さない。

| 表 | 主な列 | 一意制約 |
| --- | --- | --- |
| `detail_source` | `src`（`AUTOINCREMENT`）、種別（ジャーナル、凍結した表、テキスト）、識別子（ファイル名、表名、テキストはデバイス、inode、大きさ、更新時刻、SHA-256）、状態 | 識別子 |
| `detail_input` | `src`、`seq` の範囲、状態（確定済み、削除済み）、manifest（下表の子の一覧） | （`src`、範囲の始まり） |
| `detail_child` | 入力、日付、表、ファイル名、行数、時刻の min/max、SHA-256、消費した世代 | （入力、日付、表） |
| `detail_generation` | 日付、世代、表ごとのファイル名、含む子の一覧、状態 | （日付、世代） |
| `detail_loss` | `src`、失った `seq` の範囲（隙間と末尾）、時刻の範囲、原因（捨てた、書き手の死、破損）、隔離したファイル | （`src`、範囲の始まり） |

1 つの入力は、日付と表ごとに複数の子（断片のファイル）を持つ。
入力の確定は、全部の子と manifest を 1 トランザクションで書く。
入力を消せるのは、その入力が確定済みのときだけである（子の一部だけが確定した状態はない）。

### 断片の確定

1. 台帳で入力が確定済みなら、手順 7 へ進む（再実行）。
2. 子（日付 × 表）ごとに一時ファイルに書く。行数がいずれかの上限を超える子は複数の row group にする（1 row group は圧縮後 4 MiB 以下）。
3. 各ファイルを読み戻し、行数と各行の CRC の合計が入力から数えた値と一致することを確かめる。
4. 各ファイルを fsync する。
5. 最終の名前に変える（名前は入力と子から決まる）。
6. ディレクトリを fsync し、台帳に全部の子と manifest を書く（1 トランザクション、`synchronous=FULL`）。
7. 入力を消す。ジャーナルはファイルを消す。凍結した表は確定した `seq` の範囲の行を消す。テキストは全部の入力が確定した後にファイルを消す。

台帳にない最終の名前のファイルと一時ファイルは、起動時に消す。

### 日の世代

1. 入力の集合を固定する：その日の、台帳にあって未消費の子と、公開中の世代。
2. 表ごとに、固定した子の row group を写して 1 ファイルにする（`<table>/<YYYY-MM-DD>.g<n>.parquet`）。再符号化しない。
3. 読み戻して行数を確かめ、fsync、名前の変更、ディレクトリの fsync を行う。
4. 台帳で、世代 `n` を公開し、固定した子を消費済みにする（1 トランザクション）。
5. 固定した子のファイルと、前の世代のファイルだけを消す（下の読む側との排他に従う）。

固定の後に確定した子（遅れて届いたデータ、日付の境界の近くの GNSS）は未消費のまま残り、次の世代に入る。

### 読む側とファイルの削除

- 読む側（アプリの画面、書き出し、送信）は、`detail/gc.lock` の共有ロックを取り、公開中の世代と未消費の子を台帳の 1 つの読み取りトランザクションで一覧にする。
- 共有ロックは、一覧のファイルを読み終わるまで持つ。一覧のファイルは、読む順に開いては閉じ、同時に開くのは 64 個までとする。ロックを持つ間は一覧のどのファイルも消されないので、一度に全部を開く必要はない。
- 消す側は排他のロックを待つ。長い書き出しの間は削除が遅れるだけで、記録と確定は止まらない（ロックは削除だけを止める）。
- 世代と子を別々の読み取りで得ると、その間に新しい世代が公開されて子が消費され、どちらにも入らない行ができる（形式モデルの `_mixedread`）。共有ロックは削除を止めるが、公開は止めない。
- 削除の側は、同じロックを排他で取ってから `unlink` する。開いたファイルは、名前を消しても読み終わるまで読める。
- ロックはプロセスをまたぐ `flock` であり、アプリの領域のファイルで使える。

### 移行

- **`raw_lines`：** 移行を始めるとき、台帳にソースを作り、その名前で表の名前を変える（`raw_lines` → `raw_lines_src<n>`。名前の変更は 1 トランザクション）。空の `raw_lines` を作り直す。凍結した表には誰も書かないので、rowid は再利用されない。後から `raw_lines` に入った行は別のソースとして移す。
- **バッチ：** 凍結した表の rowid の範囲（20 万行以下かつ 16 MiB 以下、エポックの途中で切らない）を 1 つの入力とする。削除は確定した rowid だけで行う。行は時刻の順に並んでいないので、時刻の範囲では消さない。
- **エポック：** 移行する `Raw` 行は、rowid の順で連続し `TimeNanos` が同じ行の並びを 1 エポックとし、その最初の行の rowid を `seq` とする（今の記録器は 1 回のコールバックの行を続けて書く）。
- **旧い形式のテキスト（`migrateLegacyLogs`）：** 今のコードは 5,000 行ずつ `raw_lines` に入れ、最後にファイルを消す。途中で落ちた端末では、同じ行が `raw_lines`（とそこから作ったアーカイブ）とファイルの両方にあり、どの行がどこから来たかは分からない。
  - 新しい版は、起動時に残っているテキストを取り込まない。`detail/quarantine/legacy/` に移して残し、端末診断に出す。中身が同じ行を見つけて黙って重複を除くことはしない。
  - 利用者は、書き出す、別のソースとして取り込む（重複の可能性の印を付ける）、消す、を選べる。
  - 新しい版の取り込み（利用者が選んだとき）は `raw_lines` を経由しない。ファイルの識別子でソースを作り、行の境界で切ったバイト範囲を入力とし、全部の入力が確定した後にファイルを消す。
- **既存の Parquet（`gnss_raw`、`imu` など）：** そのまま読む。新しい配置への書き直しは任意で、旧ファイルを入力とする世代として扱い、公開の後にだけ消す。

### 形式モデル

`formal/tla/DetailLog.tla`（ジャーナル、断片、世代、回復、読む側）と `formal/tla/DetailMigrate.tla`（移行）で検査する。
動作と設計の手順の対応、反例の試験への写し方は [`formal/README.md`](../../formal/README.md) にある。

| 設定 | 内容 | 結果 |
| --- | --- | --- |
| `DetailLog` | サンプル 3（日 1 が 2、日 2 が 1、系列 2 つ）、ジャーナル 2、日 1 の世代 2、読む側 1、障害 1 回（捨てたサンプルを含む） | 成立（7.6 万状態）。全動作と 5 つの場面に到達する |
| `DetailLog_2faults` | 同じく障害 2 回 | 成立（34 万状態） |

| `_gcread`、`_mixedread` | 読む側との排他なしに古い世代を消す、世代と子を別の読み取りで得る | `ReaderOK` が破れる |
| `DetailMigrate` | 凍結した表の行 3（時刻の順でない）を 2 バッチ、後から来た行 1、途中まで取り込まれた旧いテキスト、障害 2 回 | 成立。確定と削除の間の到着、同じ入力のやり直し、順でないバッチ、隔離したテキストに到達する |
| `DetailMigrate_rowid`、`_bytime` | 後から来た行が同じ表で rowid を再利用する、凍結した表のバッチを時刻の範囲で消す | `Durability` が破れる |
| `DetailMigrate_halfimport`、`_reimport`、`_nounique` | 途中まで取り込まれたテキストをソースとして移す、今のコードで取り込む、確定済みの入力をやり直す | `NoDup` が破れる |

- `Durability`：一度 fsync したサンプル（移行では元の表やファイルにある行）は、耐久な入力に残っているか、公開中の行にちょうど 1 回ある。
- `NoDup`：公開中の行を多重集合で数え、同じサンプルは 1 回以下である。
- `LossReported`：ジャーナルが消えた後、そのサンプルは公開されているか、台帳の損失の範囲（隙間か末尾）に入る。範囲はファイルの走査だけで作る。ジャーナルが残る間は走査が後で報告する。それが必ず起きることは `DetailLog_live` が確かめる。
- `LossOnlyUnsaved`：損失の範囲は、fsync したサンプル、ジャーナルにあるサンプル、公開中のサンプルを含まない（ジャーナルを消した後も検査する）。
- `ReaderOK`：読む側は一覧のファイルをすべて開け、一覧を読んだ時点で公開されていた行をちょうど得る。
- 到達の場面は履歴変数で確かめる：固定の後に確定した子が次の世代に入る、途中で失敗した同じジャーナルを作り直して確定する、2 日にまたがるジャーナル、系列の入れ替えや捨てたサンプルによる隙間の報告、新しい世代の公開をまたぐ読む側。移行では、確定と削除の間に来た行、同じ入力のやり直し、順でないバッチ、隔離したテキスト。
- モデルにないもの：末尾以外の破損と隔離、表ごとのファイル（1 つの子にまとめた）、日 2 の世代、ジャーナルの削除が電源断で戻る場面（入力が増えるだけ）。反例はまだ実装で再生していない（実装と同時に作る）。モデルは正しく閉じたジャーナルにも末尾の記録を作るが、末尾にサンプルはないので結果は変わらない。

## メモリとディスクの上限

上限はバイト数と行数で決める。時間（「30 秒分」など）は、測ったレートでの目安である。

| 対象 | 上限 |
| --- | --- |
| 記録のバッファ | 事前確保で計 1 MiB（IMU 3 系列に各 256 KiB、他に 256 KiB）。最高精度では 30 秒分以上に当たる。超えたら捨てて LOSS に記録する |
| ジャーナル 1 つ | 16 MiB。行数は 1 表あたり IMU 131,072、`gnss_signal` と `gnss_sat` 32,768、`nmea` と `gnss_nav` 65,536、他 16,384 |
| 確定の処理 | 1 表ずつ作る。1 表の列の配列は「行数の上限 × 固定長の列の幅」（最大は `gnss_signal` の 32,768 × 216 B = 6.8 MiB）と可変長の値（入力の 16 MiB 以下）、出力のバッファはその非圧縮の大きさ以下、読み取りのバッファは 1 MiB。合計 40 MiB 以下 |
| 重い処理の同時実行 | 断片の確定、日の世代、移行、書き出し、書き直しは 1 つのワーカーで順に行う |
| Parquet の読み出し | row group ごとのストリーム。1 ページの展開後の大きさは 8 MiB 以下で、超えたら壊れたファイルとして扱う |
| 併合（`ArchiveStore.read`、書き出し） | footer の非圧縮の大きさで、同時に開く row group の合計を 32 MiB 以下に抑える。収まらない窓（重なる row group が多い、同じ時刻の行が多い）は、並べた run を一時ファイルに書き出す外部ソートで処理する。全件の `Vector` と全体の並べ替えをやめる。キャッシュはバイト数（16 MiB）で限り、生データの表は丸ごとキャッシュしない |
| 外部ソート | 1 回の併合で開く run は 16 個まで。超えたら 16 個ずつ併合して run を減らす（多段）。生データの読み出しが同時に開くファイルは、Parquet と run を合わせて 64 個までとする（一覧のファイルは共有ロックで守られるので、開くのは読む直前でよい） |
| 予算を単独で超える row group（今の writer の 5 万行の row group、壊れた footer） | row group を丸ごと読まない。時刻の列と必要な列だけを列ごと、ページごとに読み、行番号と並べる鍵を run に書き出してから、外部ソートの入力にする |
| ジャーナルの滞留 | 未確定が 256 MiB か空きが 1 GiB を下回ったら通知と端末診断。空きが 512 MiB を下回ったら生データだけを止める（位置の記録は続ける）。理由を LifeLog に残す。容量のためにジャーナルを消さない |
| 書き込みの失敗（ENOSPC、I/O エラー） | 記録のバッファに残し、上限を超えたら捨てて LOSS とする。確定の失敗は入力を残して再試行する |

## 読み出し時の要約

- 画面や Web 閲覧で IMU や GNSS を描くときは、1 秒ごとの要約（件数、`|a|`、`|g|`、`|m|` の最小、最大、平均、エポックごとの C/N0 の平均と使った衛星の数）を読み出すときに作る。保存も送信もしない。
- 要約は row group のストリームから作り、上の併合のメモリの上限に従う。アプリはバイト数で限ったキャッシュに置く。Web 閲覧は WASM か JS で同じ計算をする。
- 端末で 1 日分の要約に 1 秒以上かかるなら、要約の表を保存する案を測って比べる（試作で測る）。

## GnssLogger 形式の書き出し

1. 範囲に重なる公開中の出力（未消費の子、公開中の世代の row group）を、台帳の時刻の min/max で選ぶ。読む側のロックの手順で開く。
2. サンプルの時刻で 10 分の窓に分ける。到着の窓と時刻の窓は重なる（GNSS は 1.7 s、IMU は 30 ms ずれる）ので、窓に重なる row group をすべて読み、窓の中の行だけを取る。併合のメモリの上限を超えるときは外部ソートに切り替える。
3. 表ごとに `(time, src, seq, idx)`（IMU は `(time, ern)`）で並べ、表をまたいで時刻で k-way に併合する。同じ時刻では `(src, seq)` の順とする。
4. `gnss_epoch` と `gnss_signal` を `(src, seq)` で結んで `Raw` 行にし、他の表はそのまま行にする。

到着順は、`seq` を持つ GNSS 側の行でソースの中だけ戻る。IMU の行は時刻の順に置く。

## 同期

- **v1（現行）：** 当日分は送らない。日の世代を送る。
  - 世代の全部の表のファイルを送った後に、世代の manifest（表、ファイル名、大きさ、SHA-256）を送る。
  - 復元側は、manifest が届き全ファイルが一致する世代のうち最大のものを使う。途中まで送った世代は使わない（`sync-protocol.md` の更新が要る）。
- **v2（[鍵の階層](key-hierarchy.md) の object と commit、未実装）が前提：** 当日分の断片を送る。
  - 1 つの object に複数の Parquet ファイルを入れる形式（平文の型を 1 つ加える：ファイル名、長さ、SHA-256 の一覧と本体）。
  - object は暗号化と Padmé の切り上げの後で 8 MiB 以下にする。平文は 7.5 MiB 以下とする。row group は作るときに圧縮後 4 MiB 以下に抑え、それでも 7.5 MiB を超えるファイルはバイト列で part に分ける（`file, part, parts`、全体の SHA-256。読む側は結合してから解く）。
  - object は kid（`raw`、月、世代）をまたがない。月の境界で分ける。
  - 日の世代を公開したら、世代の object を送り、断片と前の世代の object を置き換える commit を出す。CAS に失敗したら v2 の規則で head を読み直して再試行する。
  - 端末の断片と世代の削除は送信を待たない。送る前に消費された断片は、世代の送信で送られる。

## プライバシー

- **平文の秘匿：** 変わらない。断片も世代も、端末の鍵で暗号化してから送る。サーバは内容を読めない。
- **メタデータ：** 今（v1）は、日ごとの生データの量が見える。当日分を送ると、送信ごとに次が見える。
  - 送信の窓（生データのジョブは 6 時間ごと、従量制でない回線）に生データがあったか。
  - その量（Padmé で 12% 以内に丸めた値）。量から記録モード（最高精度は 1 時間 11.7 MB、生データは 7.8 MB）と時間が推測できる。
  - 送信の時刻（Wi-Fi に接続できた時刻）。

| 対策 | 隠せるもの | 費用 |
| --- | --- | --- |
| 当日分を送らない（v1 と同じ） | 日より細かい量と時刻 | 当日の backup を失う |
| 一定の間隔で、空でも送る | 送信の有無と時刻 | 1 日数回の 4 KiB の object |
| 窓ごとの量を粗い段階（8 MiB の 2 の冪）に丸める | 量の細部 | 最大 2 倍の通信と保存 |
| 窓ごとに最高精度の最大量まで埋める | 量と記録モード | 6 時間で 70 MB、1 日 280 MB。現実的でない |

推奨：当日分の送信は既定で無効にし、有効にしたときは一定の間隔で送る。残る危険（記録の有無と大まかな量）は設定の説明に書く。

### 影のモードの削除の抑止

影のモードでは、生データの原本を消す、上書きする、切り詰める経路をすべて 1 つの共通の抑止（`DetailGuard`）に通す。

- **状態の保存：** モードは `detail/mode`（fsync する）と台帳の `detail_mode` の両方に置く。両方のプロセスが起動時に読む。ない、読めない、2 つが食い違うときは影のモードとして扱う。切り替えは、両方を書いて fsync してから再起動する。
- **呼び出し：** 削除、置き換えの名前の変更（`REPLACE_EXISTING`）、`truncate`／`setLength`、SQLite の `DELETE` は、生データとアーカイブのコードでは `DetailGuard` の関数でしか行わない。各呼び出しは対象の種類と範囲を渡し、許されなければ何もせず、拒んだ件数と最後の対象を端末診断に出す。
- **静的な検査：** 試験で、該当するパッケージに `File.delete`、`Files.delete*`、`REPLACE_EXISTING`、`setLength`、`truncate`、`DELETE FROM`、`db.delete(` が `DetailGuard` の外にないことを確かめる。

| 経路 | 今の場所 | 影のモードでの扱い | 守るもの |
| --- | --- | --- | --- |
| 日のアーカイブの後の `raw_lines` の削除 | `ArchiveStore.compactDay` → `Db.deleteHot` | しない。検証の結果によらない。日のアーカイブは今どおり作るが、`raw_lines` の行は残す。他の表（`fixes` など）の削除は今どおり | 全部の `raw_lines` の行（検証の基準） |
| 既存の日のファイルの置き換え | `ArchiveStore.writeVerified`（遅れた行を合わせて置き換え） | 生データの表は、旧ファイルの全行（`distinct` で減らさない）を含むことを読み戻して確かめた場合だけ許す | 既存の生データの日のファイル |
| 月の統合による日のファイルの削除 | `ArchiveStore.mergeMonths` | 生データの表は月の統合をしない（設計どおり）。他の表は今どおり | 生データの日のファイル |
| 旧い形式のテキストの取り込みと削除 | `ArchiveStore.migrateLegacyLogs` | 取り込みも削除もしない。隔離に移す（名前の変更だけ） | 旧い形式のテキスト |
| ジャーナルの削除 | 新しい経路の確定 | しない | 全ジャーナル |
| 子と古い世代の削除 | 日の世代の掃除 | しない | 全部の子と世代 |
| 起動時の掃除（台帳にないファイル、一時ファイル） | 新しい経路の起動 | しない。一覧を端末診断に出す | 途中で止まった出力 |
| 壊れた末尾の切り捨て | 回復 | しない。有効なフレームを別のファイルに写し、原本はそのまま残す | 原本のジャーナル |
| 短い書き込みの後の `ftruncate` | ジャーナルの書き手 | しない。そのジャーナルを閉じて（途中のフレームは残す）、新しいジャーナルに切り替える | 原本のジャーナル |
| 作り直しで既存の名前に上書きする | 断片の確定、日の世代 | しない。試行ごとに別の名前で書き、台帳はその名前を指す | 前の試行の出力 |
| 隔離の削除 | 端末診断の操作 | 利用者の明示の操作だけ | 隔離したファイル |

- 影のモードでは原本を何も消さない。検証器の結果は削除の条件にしない。削除は切り替えの後にだけ有効にする。
- 影のモードの出力（ジャーナル、子、世代）と残した `raw_lines` は増え続ける（最高精度で 1 時間 約 210 MB：`raw_lines` 157 MB、ジャーナル 41 MB、出力 12 MB）。使う容量に上限（例：8 GiB）を設ける。上限を超えるか、空きが 2 GiB を下回ったら、影の書き込みを止め、それでも足りなければ生データ（両方の経路）を止める。位置の記録は続ける。止めたことと期間を端末診断に出し、その期間を検証の報告に書く。
- **切り替えの後の削除：** 日や期間の完了の印では消さない。検証器が説明のない差なしと確かめた行の集合を、ID（`raw_lines` の rowid、`(src, seq)`）の一覧として台帳に固定し、その一覧の行だけを消す。一覧の後に届いた行や、検証していない行は残る。
- **保持の試験：** 影のモードで、記録、日のアーカイブ、確定、世代、掃除、起動、回復、短い書き込み、kill を含む操作列を流す。前後で守るもの（`raw_lines` の削除が許されていない行、旧い形式のテキスト、生データの日のファイル、ジャーナル、子、世代、隔離）の一覧と SHA-256 を取り、消えたもの、変わったものがないこと（許した置き換えは旧ファイルを含むこと）を確かめる。各経路で拒んだ件数が 1 以上であることも確かめ、抑止が実際に呼ばれたことを示す。1 か所の抑止を外すと試験が落ちることも確かめる。

### 検証器

基準は、分岐する前のイベントの同一性を持つ記録とする。今の日のアーカイブは基準にしない（`Fix` 行を捨て、`distinct` で同じ行を減らし、NaN と値なしを区別しない）。

- **基準：** 影のモードでは、`raw_lines` に列 `src`、`seq`、`vals` を加え（`ALTER TABLE ADD COLUMN`、値は null 可）、記録器はジャーナルに渡すのと同じイベントについて、今と同じ書式のテキスト行と一緒に書く。
  - `src`、`seq`：ジャーナルと同じイベントの ID。
  - `vals`：その行の各欄について、値の有無（null か値か）と、浮動小数点の欄は API から得た元の bit 列（float は 32 bit、double は 64 bit）を並べた BLOB。テキストは NaN と値なしを区別できないので、その区別をここに残す。
  - テキスト行も `vals` も、記録器が受け取った値から今の書式化の関数と単純な bit の書き出しで作り、新しい符号化を通らない。
- **独立した復号：** 検証器は、新しい経路の reader を使わずに基準のテキストを復号する（`tools/detail-log-bench/extract.py` と同じ規則の別の実装）。新しい出力は Parquet の reader で読む。
- **対応付け：** GNSS は `gnss_epoch` と `gnss_signal` を `(src, seq)` で結び、`idx` の順に `Raw` 行に戻して比べる。その他の GNSS 側の表は `(src, seq)` で対応付ける。IMU の表は `src` も `seq` も持たないので、各 Parquet ファイルの footer に row group とソースの対応表（key-value metadata の `ashidori.rowgroups`：row group の番号、`src`、入力の `seq` の範囲）を置く。子の row group は 1 つの入力から作り、世代は row group をそのまま写して対応表をつなぐので、どの row group も 1 つの `src` に属する。検証器は、対応表から各行の `src` を、表からセンサーを、列から `ern` を得て、基準の行の `(src, seq)` から求めた `(src, センサー, ern)` と対応付ける。この鍵が基準で一意でないときは、その行を差として報告する。
- **比べるもの：** 系列ごとの件数（出現の回数）、各値の有無と値（`vals` の bit 列と bit 単位で一致：float は Float32、double は Float64。整数はテキストの値）、型。null と NaN の取り違えは `vals` との比較で見つかる。テキストの行も `vals` と照合し、テキストの経路そのものの誤りも差として出す。
- **欠落の照合：** 基準にあって新しい出力にないイベントは、損失の台帳の範囲（`src`、`seq`）に入っていれば説明済み、入っていなければ説明のない差とする。新しい出力にあって基準にないイベントも、下の既知の差に当たらなければ説明のない差とする。
- **既知の差：** 一括では除外しない。次の 1 つずつについて件数と各例を報告に残す。
  - K1：テキストの書式の曖昧さ。基準のテキストの欄は空だが、`vals` ではその欄が NaN である（今の書式は NaN を空にする）。新しい出力の比較は `vals` に対して行うので、この差はテキストと `vals` の照合でだけ現れる。`vals` が NaN を示す欄に限り、欄ごとに数える。
  - K2：`gnss_nav` の `time`。基準には `Nav` 行の時刻がない（直前の記録の時刻を使う）ので、`time` 以外の欄を比べる。
  - K3：テキストの経路だけが失ったイベント（今の 3 秒のバッファがプロセスの死で消えた）。LifeLog のプロセスの死の記録から 3 秒以内のイベントに限る。
  - K4：記録器が書かない列（`CarrierCycles` など）。基準の欄が空であることを確かめる。
- **報告：** 日ごとに、比べた件数、一致、既知の差（種類ごとの件数と例）、説明のない差を、端末診断と報告のファイルに出す。報告は検証器の結果として台帳に記録する。影のモードでは削除の条件に使わない。切り替えの後は、説明のない差がない行の ID の一覧を固定する材料にする。

### 切り替えの条件

期間だけでは切り替えない。次をすべて満たす（第 4 回のレビューの条件）。

- 上記の削除禁止・比較基準・FD制御を実装し、影モードで原本保全を確認する。
- 全変異の反例を実ファイル＋SQLiteで再生し、短いwrite、truncate失敗、回復中の再障害、部分成功、旧版からの更新、読者競合を検査する。
- 実端末で完全な符号化の可逆性、損失報告、メモリ・FD・容量・fsync遅延を確認する。
- 観測期間中の**未説明の差分をゼロ**にし、切り戻し後も既存の新形式データを読めることを確認する。

| 試験 | 内容 |
| --- | --- |
| 確定の境界での終了 | 断片の確定、日の世代、回復、移行の各手順（書き込み、読み戻し、fsync、名前の変更、ディレクトリの fsync、台帳、削除）の直後に kill し、再起動後に欠落と重複がないことを確かめる。形式モデルの反例を、この試験の操作列として流す |
| 電源断の模擬 | fsync していない書き込み、名前の変更、`synchronous=FULL` でない台帳の commit を戻したディスクの像から再起動する |
| 台帳の設定 | `synchronous` を変えた台帳で起動し、削除が止まることを確かめる |
| ENOSPC と I/O エラー | ジャーナル、断片、台帳の書き込みで失敗を注入する。途中まで書いたファイルが検証で拒まれ、記録が止まらず、失った範囲が記録されることを確かめる |
| 破損 | フレームの末尾の切断、途中のビット反転、`frame_seq` の飛びと重複。隔離と損失の記録を確かめる |
| 遅れたデータ | 世代の固定の後に断片を確定させ、次の世代に入ることを確かめる |
| 読む側 | 世代を選んでから開くまでの間に新しい世代を公開し、削除が待つことを確かめる |
| 再移行 | 移行とテキストの取り込みを各手順で止めて再実行し、行が一度だけ出力されることを確かめる。凍結の後に `raw_lines` に入った行が残ることを確かめる |
| 系列の入れ替え | 系列ごとのバッファを、書き込みの途中で落とす。走査が隙間を見つけて報告することを確かめる |
| 回復の途中の障害 | 回復の各手順（走査、切り捨て、台帳、CLOSE、名前の変更）で再び kill し、やり直しで同じ結果になることを確かめる |
| 子の部分的な成功 | 一部の子だけ fsync や名前の変更が済んだところで落とし、作り直しと掃除を確かめる |
| 旧いテキストの途中までの取り込み | 旧い版で取り込みを途中で止めた端末の像から更新し、テキストが隔離されて二重に移らないことを確かめる |
| 公開中の読む側 | 読む側が一覧を読んでからファイルを開くまでの間に、新しい世代の公開と消費、古いファイルの削除を挟む |
| 規模 | 最高精度 4 時間（約 650 万行）と、その 2 倍のレートで、メモリ、開いたファイルの数の上限を超えないことを確かめる |
| 端末での計測 | 完全な符号化（フレーム、CRC、30 秒ごとの fsync、短い書き込みの処理）での可逆性、損失の報告、割り当て、最大メモリ、容量、fsync の遅れ |

## 実装の見積もり

| 項目 | 規模 |
| --- | --- |
| ジャーナル（書き手、走査、回復、隔離）と fuzzing | 中 |
| 台帳（別のデータベース、設定の確認）、断片の確定、日の世代、読む側のロック | 中 |
| Parquet writer の拡張（統計、Binary、key-value metadata、NaN、列の API、row group の上限）と row group の写し | 中 |
| row group ごとの reader、`ArchiveStore.read` の併合と外部ソート | 中 |
| 書き出しの k-way 併合 | 小 |
| 移行（表の凍結、テキストのソース）と、進行中のストリームの圧縮の置き換え | 中 |
| v2 の同期への接続 | v2 に含める |

## 未決事項

| 項目 | 推奨・論点 |
| --- | --- |
| `energy_state` | 生データの開始、停止、レートの要求の変化は `energy_state` に残る。断片をそこで切ることはしない。ジャーナルの書き込みと確定の電力を `EnergyModel` に入れる |
| `pressure` | 5 秒の中央値の小さい表のままとする。生の気圧を生データに加えるかは別に検討する |
| センサーの FIFO | `maxReportLatencyUs` で AP を眠らせると、配送の遅れとバッファの大きさが変わる。ジャーナルの上限と時刻の符号を測り直す |
| 未較正のセンサー | 記録する内容が変わるので別に検討する |
| zstd | gzip（水準 9）で容量の目標を満たす。zstd（3 なら符号化が 10 倍速い）と gzip の低い水準は、Android での入手の方法と合わせて端末で比べる |
| 自前のコールドの形式 | GNSS の表だけ 1 時間 0.8〜1.1 MB 縮む（推定）。採らないが、GNSS の行数が増える使い方が出たら見直す |
