# 外部への送信の設定とオフラインの地域データ（設計案）

> 状態：機能 1（送信先ごとの外部送信の設定）は**実装済み**である（[10 章](#10-機能-1-の実装)。設計から変えた点もそこに記す）。機能 2（オフラインの地域データ）は、日本の区画の地図のパック（ズーム 8〜14）を**実装済み**である（[11 章](#11-機能-2-の実装)。設計から変えた点もそこに記す）。パックは未公開であり、公開には所有者の承認が要る（[11.5 節](#115-公開の手順)）。施設データを地図に描く層（[6.16 節](#616-施設の層)）も実装した。
> 外部のレビュー（1 回目、2 回目）の指摘を反映した。2 回目のレビューは、容量の計測と通信の経路の試作に進むことを認め、製品の実装の前に、再起動をまたぐ許し、MapLibre の印、容量の予算の式、スタイルの束を含む復旧を設計に入れることを条件とした（本版で反映）。
> 容量の計測と通信の経路を確かめる試作は先に進めてよい。製品に組み込む前に、設定の変更、再起動、リダイレクトを含む端末での試験を必須とする。
> 利用者の判断を待つ点を [未決の事項](#9-未決の事項) に挙げる。
> 外部のサービスについて確かめていない事項は「未確認」と書く。
> 現行の仕様は [`privacy.md`](../privacy.md) と [README の「地名と位置情報の送信」](../../README.md#地名と位置情報の送信) にある。

本書は二つの機能を扱う。

1. **送信先ごとの外部送信の設定**：送信先ごとに、送るかどうか、いつ送るか、どの精度まで送るかを利用者が決める。
2. **オフラインの地域データ**：地域を選び、詳細な地図と施設データを事前に端末へ取得する。

二つは互いに関わる。
地域データがあればオンライン地図に頼らずに済み、地域データの取得自体も外部への送信の一つになる。

## 1. 課題と目標

### 課題

- 外部への送信を制御する設定は「オンライン地図と地名検索」のスイッチ一つ（保存値 `blockExternalLocation`）だけである。
- 実際の送信先は複数あり、送る情報も精度も異なる。地図の配信元には表示範囲を、Android の Geocoder には滞在地の座標を、Overpass には検索した位置を送る。
- 利用者には「この送信先にこの精度なら送ってよいが、あの送信先には送らない」という判断がありうる。一つのスイッチではこれを表せない。
- オフライン地図は日本でズーム 10、全世界でズーム 5 までである。通信できない場所（山、海外の旅行先）で詳細な地図を見る手段がない。

### 目標

1. 送信先ごとに、送信の可否、時機（操作時のみ、自動）、精度を選べる。
2. 新規の導入の既定と、既存の利用者の動作を変えない。
3. 設定の結果を ✓ ／ ⊖ の一覧で示し、説明の段落を置かない。
4. 地域を選んで、詳細な地図と施設データを事前に取得できる。取得で何が誰に伝わるかが画面で分かる。
5. 地域データの取得と更新が記録を妨げない（記録の領域を残し、記録の処理と独立に動く）。

### 対象外

- OS の測位サービスが送る情報（fused と network provider、Google 位置情報の精度）。一覧には参照の行だけを置く（[未決 5](#9-未決の事項)）。
- Web ビューア（ブラウザ）の地図。ブラウザの設定はブラウザに保存する別の仕組みである（[`web-viewer.md`](../web-viewer.md)）。
- 同期プロトコルの変更。

### 2.3 一覧から分かること

- Geocoder には、自分の滞在地だけでなく、同期した他の端末の現在地も送りうる（`PeerStatus.scala:321`）。
- Overpass の予備のインスタンスは、1 回の検索の送信先を最大 4 ホスト、3 者に広げる。
- 静止画（フィード、期間のカード、他の端末）は、設定がオンの間、過去の日の範囲を地図の配信元へ自動で送る。表示中の地図より伝わる範囲が広い。
- 地図と静止画の送信先は、選んだ地図（`mapStyle`）で決まる。**例外は地図の種類のサムネイル**であり、送信が許される候補をすべて現在の表示範囲で描く。選んでいない地図の配信元にも表示範囲が伝わる。
- MapLibre の出典の画面は、出典の URL によってはカメラの位置をブラウザに渡す。

## 3. 設定とデータのモデル

### 3.1 送信先と選べる値

設定は送信先（`Dest`）ごとの規則（`Rule`）の集まりとする。
規則は時機（`When`）と精度（`Level`）の組である。

| `Dest` | 画面の名前 | 選べる時機 | 選べる精度 |
| --- | --- | --- | --- |
| `ofm` | オンライン地図（OpenFreeMap） | 送信しない、操作時のみ、自動 | 地域、地区、制限なし |
| `gsi` | オンライン地図（地理院タイル） | 同上 | 同上 |
| `custom` | オンライン地図（カスタム） | 同上 | 同上 |
| `geocoder` | 地名検索（Android） | 送信しない、自動 | 地域、地区、正確 |
| `overpass` | 施設のオンライン検索 | 送信しない、操作時のみ | 地区、正確 |
| `data` | 地図・施設データの取得 | 送信しない、操作時のみ、自動 | 全域のみ、区画 |

時機の意味は次のとおりである。

- **送信しない**：その送信先には、操作があっても送らない。入口（ボタン、地図の種類）を無効にする。
- **操作時のみ**：利用者がその表示やその検索を指示したときだけ送る。地図では今の「オンライン地図で表示（表示範囲を送信）」に当たり、一度許した地図は、その画面でオフライン地図に戻すか設定を変えるまで保つ（画面を離れても、再起動しても続く）。
- **自動**：表示や記録に合わせて送る。地図では静止画とサムネイルも含む。

Geocoder には操作の入口がないので「操作時のみ」を置かない。
Overpass には自動の検索を設けない（今の方針を保つ）。

### 3.2 精度の意味

精度は、**送る座標やタイル番号の粒度**である。
送信先から見た位置の候補の範囲（最低の匿名範囲）は保証しない。

| 精度 | 地図のタイル（T1〜T3） | 地名検索 | 施設の検索 |
| --- | --- | --- | --- |
| 地域（約 10 km） | ズーム 12 までのタイル番号を送る。それより拡大した表示はズーム 12 のタイルを引き伸ばす | 0.1° の格子の中心の座標を送り、答えは市区町村と国だけを使う | 選べない |
| 地区（約 1 km） | ズーム 15 までのタイル番号を送る | 0.01° の格子の中心の座標を送る | 0.01° の区画とその周囲 8 区画を合わせた bbox を送り、端末内で近い順に絞り込む |
| 制限なし、正確 | 配信元の最大ズームまで | 座標のまま | 位置と半径のまま |

粒度は位置を隠す範囲ではない。
送信先は、次の手がかりで粒度より細かく位置を推測しうる。

- **隣り合うタイル**：表示範囲が上限のズームのタイルの境界をまたぐと、隣り合うタイルを要求する。表示の中心が境界の近くにあると分かる。
- **順序と時刻**：MapLibre は中心に近いタイルから要求する傾向がある。要求の順序と時刻、既知の画面の大きさから、表示の中心と範囲を絞れる。
- **緯度による縮み**：格子とタイルの実寸は緯度で変わる。0.01° の経度は北緯 35° で約 0.9 km、北緯 60° で約 0.56 km である。タイルの 1 辺は `40075 km × cos(緯度) / 2^z` であり、北緯 35° でズーム 12 は約 8 km、ズーム 15 は約 1 km である。
- **境界の通過**：格子は固定である（毎回同じ区画の中心を送る）。区画の境界を越えた時刻は伝わり、道路などの補助の情報と合わせると移動の経路を絞れる。
- **Overpass の 9 区画**：周囲 8 区画を含めても、bbox の中央の区画は一意に分かる。伝わる粒度は約 3 km 四方ではなく、中央の 0.01° の区画である。周囲を含めるのは、半径の検索が区画の境界で切れないためである。

ほかに次の点を定める。

- OpenFreeMap のベクタタイルの最大ズームは 14 と理解している（未確認）。その場合、OpenFreeMap の「地区」と「制限なし」は同じ要求になる。
- 地名検索の「地域」は「…付近」の地名を出さない。ずらした点の町名は誤りになりうるためである。
- 区画ごとに決まったタイルの集合を常に要求する方式（表示によらず同じ集合を送る）は、隣り合うタイル、順序、時刻による推測を減らすが、通信量が増える。将来の案として残す。

「データの取得」の精度は次のとおりである。

| 精度 | 意味 |
| --- | --- |
| 全域のみ | 日本と全世界のオフライン地図、日本の施設データのように、利用者の選んだ範囲を含まない archive だけを取得する。地域データは取得しない。日本全体を取得した事実と IP アドレスは伝わる |
| 区画 | 加えて、利用者が選んだ地域の区画（[6.4 節](#64-区画)、約 130 km 四方）を取得する |

### 3.3 型

`core` に置く。

```scala
enum Dest(val key: String):
  case Ofm extends Dest("ofm")
  case Gsi extends Dest("gsi")
  case CustomTiles extends Dest("custom")
  case Geocoder extends Dest("geocoder")
  case Overpass extends Dest("overpass")
  case Data extends Dest("data")

enum When:
  case Never, OnAction, Auto

/** 送信先ごとに意味が異なる。Whole と Cell は Data だけが使う。 */
enum Level:
  case Area, District, Exact, Whole, Cell

/** off: Overpass で使わないインスタンスのホスト。 */
final case class Rule(when: When, level: Level, off: Set[String] = Set.empty)

final case class Policy(rules: Map[Dest, Rule]):
  def rule(d: Dest): Rule
```

`Policy` は、送信先ごとに選べない組（Geocoder の `OnAction` など）を持たない。

### 3.4 保存するキー

既存の `settings` の SharedPreferences に置く。

| キー | 型 | 既定 | 内容 |
| --- | --- | --- | --- |
| `externalPolicy` | String（JSON） | なし（なければ移行する） | 送信先ごとの規則 |
| `externalConsents` | String（JSON） | なし（なければ `mapConsents` から移行する） | 地図の画面ごとの同意。送信先と精度を含む |
| `mapConsents` | String（JSON） | 既存 | 移行の元。移行後は読まず、旧版向けの派生値を書く（[3.6 節](#36-旧版との互換)） |

`externalPolicy` は `MapConsents` と同じく、版付きの一つの JSON とする。

```json
{"v":1,"rules":[
  {"dest":"custom","when":"action","level":"exact"},
  {"dest":"data","when":"auto","level":"cell"},
  {"dest":"geocoder","when":"never","level":"exact"},
  {"dest":"gsi","when":"action","level":"exact"},
  {"dest":"ofm","when":"action","level":"exact"},
  {"dest":"overpass","when":"action","level":"exact","off":[]}
]}
```

規則、同意、世代、旧版向けの派生値は、一度の `SharedPreferences.Editor` で書く（今の `persist` と同じ）。

### 3.5 既定値、復旧値、読み込みの順序

**新規の導入の既定**と、**読めない値からの復旧値**を分ける。

| 送信先 | 新規の導入の既定（今の動作） | 復旧値 |
| --- | --- | --- |
| `ofm`、`gsi`、`custom` | 操作時のみ、制限なし | 送信しない |
| `geocoder` | 送信しない | 送信しない |
| `overpass` | 操作時のみ、正確、全インスタンス | 送信しない |
| `data` | 自動、区画 | 操作時のみ、全域のみ（手動の取得だけ） |

復旧値は、値が壊れている場合、未知の版の場合、送信先の項目が欠けている場合に使う。
同意はすべて捨てる。
`data` だけは「送信しない」ではなく「操作時のみ」とする。オフライン地図を手動でなら取得できるようにするためであり、自動の取得と自動更新は止まる。

読み込みは次の順に行う。

1. 重複したキーを拒む解析で JSON を読む。読めなければ破損とする。
2. `v` を見る。1 でなければ未知の版とする。
3. 既知の送信先の規則から未知の項目を除き、未知の送信先の規則を除く。
4. 除いた後の値を `Policy` に復号し、符号化し直したものが、除いた後の値の正準形と一致することを確かめる。送信先の重複、選べない組、型や値の誤りはここで不一致になり、破損とする。
5. 欠けている送信先を復旧値で補う。アプリの更新で送信先を加える場合は、`Settings.migrate()` がその送信先の既定を明示的に書く。読み込みで欠けていれば、それは移行の漏れか破損であり、復旧値を使う。

破損と未知の版の値は、保存し直さない。
新しい版のアプリが書いた値は、利用者がこの版で設定を変えるまで残る。
「データの扱い」の画面は、この状態の間「設定を読み込めません（データの手動取得のみ）」の 1 行を出す。
利用者が変えた時点で、この版の形式で書く。

### 3.6 旧版との互換

旧版のアプリ（`blockExternalLocation` と `mapConsents` だけを読む）に戻した場合の保証は、旧版の Boolean が表せる範囲に限る。

**保証すること**：旧版は、新しい設定が自動の送信を許していない地図の配信元と Geocoder へ、自動では送らない。
`blockExternalLocation` の派生値は、規則がすべて旧設定のオフ（[3.7 節](#37-移行)の右列）と一致するときだけ false、ほかは true とする。

**`mapConsents` の派生値**：精度が「制限なし」で、送信先が「操作時のみ」の同意だけを書く。
精度に制限のある同意は旧版に渡さない。
旧版は精度の制限を知らず、制限なしで送るためである。

**保証できないこと**（旧版の `blockExternalLocation=true` の動作による反例）：

- Overpass を「送信しない」にしても、旧版は「オンラインで検索」を押せば送る。
- `data` を「操作時のみ」「送信しない」にしても、旧版は起動時にオフライン地図と施設データを自動で取得する。
- 地図の送信先を「送信しない」にしても、旧版は「オンライン地図で表示」を押せば制限なしで送る。

Android は同じ署名の版の下げを、データを残したまま行わせないのが通例であり（`adb install -d` などの例外がある）、この範囲で十分と判断する。

### 3.7 移行

起動時の `Settings.migrate()` で、`externalPolicy` がなければ `blockExternalLocation` から作る。
`onlineVenues` の移行（今のコード）を先に行う。

| 送信先 | `blockExternalLocation` が true、または値がない（今の既定） | false |
| --- | --- | --- |
| `ofm`、`gsi`、`custom` | 操作時のみ、制限なし | 自動、制限なし |
| `geocoder` | 送信しない | 自動、正確 |
| `overpass` | 操作時のみ、正確、全インスタンス | 同左 |
| `data` | 自動、区画 | 同左 |

- 新規の利用者は左列になる。今の既定と同じである。
- `blockExternalLocation` が壊れている（型違い）場合は、今の `MapConsents.load` と同じく左列とし、同意を捨てる。
- `mapConsents` は `MapConsents.load` と同じ規則で読み、精度「制限なし」の同意として `externalConsents` に移す。
- `data` の「区画」は地域データの機能とともに入る。地域データの取得は操作でだけ始まるため、移行の時点で新たな送信は起きない。
- 「動作を変えない」の根拠は、次の同値性の試験とする（[8.1 節](#81-core-の単体試験jvm)）。旧設定の 2 通りから作った `Policy` について、新しい判定が今の判定と一致することを、判定の関数だけでなく、待機中の静止画、再試行を待つ取得、再起動の後に読み戻した同意、画面の外に出た地図、停止した作業の状態を含めて確かめる。

## 4. SendGate と送信の契約

### 4.1 状態

| 状態 | 今 | 変更後 |
| --- | --- | --- |
| 設定 | `blocked: Boolean` | `policy: Policy` と `paused: Boolean` |
| 世代 | 全体で一つの `gen`（メモリだけ、起動ごとに 0 から） | 送信先ごとの `gens: Map[Dest, Long]`。変更のたびに作る 64 ビットの乱数で、保存する（[4.2 節](#42-送信の許しpermit)） |
| 起動の識別子 | なし | プロセスの起動ごとに作る 128 ビットの乱数 `epoch`。保存しない |
| 票（ticket） | `Long` | 送信先ごとの世代の写し（`Ticket(gens)`） |
| 許可（grant） | 表示 → 世代 | 表示 → （送信先、その世代） |
| 同意 | 地図の画面 → 地図 | 地図の画面 → （地図、送信先、精度） |

送信先ごとに世代を分けるのは、Geocoder の設定を変えたときに、表示中のオンライン地図の許可や待機中の静止画まで取り消さないためである。

### 4.2 送信の許し（Permit）

外部へのすべての要求は、要求を作った時点の **許し** を持つ。

```scala
enum Mode:
  case OnAction, Auto

/** 要求を作った時点の起動の識別子、送信先、その世代、操作か自動か、精度。 */
final case class Permit(epoch: Epoch, dest: Dest, gen: Long, mode: Mode, level: Level)
```

許しが有効であるのは、次をすべて満たす間である。

- `epoch` が今のプロセスの起動の識別子と等しい。再起動の前に作った許しは、どの世代でも通らない。
- `paused` でない。
- 送信先の規則の時機が、`mode` が `Auto` なら `Auto`、`OnAction` なら `Never` でない。
- 送信先の世代が `gen` と等しい（規則が、精度だけの変更を含めて変わっていない）。

**世代の保存**：

- 世代は単調な番号ではなく、規則の変更と一時停止の開始・解除のたびに作る 64 ビットの乱数とする。キー `externalGens`（版付きの JSON）に、規則と同じ `SharedPreferences.Editor` で書く。
- `externalGens` を読めない場合は、全送信先に新しい乱数を作る。値が失われても、古い世代と一致することはない。
- 起動の識別子は保存しないので、メモリの許しは再起動をまたがない。保存した世代は、再起動をまたぐ作業（WorkManager）が規則の変更を見分けるために使う。

**再起動をまたぐ作業**：

- WorkManager の作業は許しを保存しない。入力に、予約した時点の送信先、`mode`、世代だけを保存する。
- 作業は実行のたびに、保存した世代が今の世代と等しく、今の規則が `mode` を許す場合に限り、新しい許しを `permit` で得る。得られなければ、送らずに作業を終える（再試行も予約しない）。
- 規則の変更は、世代の保存の後に該当する作業を取り消す。保存と取り消しの間でプロセスが止まっても、残った作業は世代の不一致で送らない。

許しは次の時点で確かめる。

1. 送信の直前（接続を開く前、`Geocoder` を呼ぶ前）。
2. 再試行のたび（`SendGate.firstSuccess` の次のホスト、`ResumableDownload` の再要求、WorkManager の再実行）。
3. リダイレクトのたび。自動のリダイレクトは使わず（`setInstanceFollowRedirects(false)`）、送信先ごとの許可されたホストの一覧に転送先が含まれ、許しがまだ有効な場合だけ従う。GitHub の転送先のホスト名は、実装の時に確かめて一覧に固定する。
4. 応答の受信中。許しが無効になった時点で接続を切る（[4.4 節](#44-outbound)）。

精度を下げる処理（`Precision.snap`、問い合わせの組み立て）は許しの `level` に従い、送信の直前に、送る値がその粒度であることを確かめる。

### 4.3 SendGate の API

```scala
final class SendGate(initial: Policy, initialConsents: Map[String, Consent],
                     persist: (Policy, Map[String, Consent]) => Unit):
  def policy: Policy
  def rule(d: Dest): Rule
  /** 規則を変える。変わった場合は d の世代を進め、d の許可と同意を消し、保存し、
    * listener に d を伝える。精度だけの変更でも同じ。 */
  def setRule(d: Dest, r: Rule): Boolean
  /** 一時停止の開始と解除。どちらでも全送信先の世代を進める。 */
  def setPaused(p: Boolean): Boolean
  def onChange(f: Set[Dest] => Unit): () => Unit

  def permit(d: Dest, mode: Mode): Option[Permit]   // 今の規則で許されなければ None
  def valid(p: Permit): Boolean

  def remember(surface: String, map: String, d: Dest): Unit  // d が OnAction の場合だけ
  def forget(surface: String): Unit
  def consent(surface: String): Option[Consent]               // その送信先が OnAction の間だけ
  def grant(owner: AnyRef, p: Permit): Unit
  def revoke(owner: AnyRef): Unit
  def online(owner: AnyRef, d: Dest): Boolean
  def networkAllowed: Boolean
```

- `block`、`setBlock`、`switchOn`、`blockFor` は移行の間だけ残し、呼び出し元を移した後に消す。
- 同意は、与えた時点の精度を持つ。規則の変更は精度だけの変更でも同意を消すので、精度を上げた後に古い同意で送ることはない。

### 4.4 Outbound

アプリが自分で HTTP で通信する箇所（Overpass、データの取得、同期のオフライン地図の確認）は、すべて `Outbound` を通す。

```scala
object Outbound:
  /** p が有効で、url のホストが p.dest の許可されたホストの場合だけ接続を開く。
    * 接続は p.dest ごとに登録し、p が無効になった時点で切る。 */
  def open(p: Permit, url: String): HttpURLConnection
```

- 接続の登録は、`SendGate.onChange` で、変わった送信先の接続をすべて `disconnect` する。
- リダイレクトは `open` の中で一つずつ確かめる（[4.2 節](#42-送信の許しpermit)）。
- 同期（`SyncClient`）は対象外とする。同期の設定が制御する。

**Geocoder** は OS の API の呼び出しであり、`open` では包めない。

- 呼び出しの直前に許しを確かめる。
- 呼び出しは一つの専用のスレッドに直列にし、同時に OS に渡す問い合わせを一つに限る。
- OS に渡した後の問い合わせは取り消せない。取り消しの限界は、規則の変更の時点で実行中の 1 件である。
- 呼び出しから戻った時点で許しが無効なら、答えを捨て、保存しない。

**MapLibre** は `HttpRequestUtil.setOkHttpClient` で interceptor を挟む。

*印*：アプリが MapLibre に渡す遠隔の URL には、すべて印のパラメータ `ashidori-t=<トークン>` を付ける。

- トークンは 128 ビットの乱数であり、それ自体は意味を持たない。端末内の表がトークンを **持ち手、送信先、`mode`、精度、世代** に結び付ける。持ち手は、地図の画面（`map`、`period`）、静止画（`snapshot`）、サムネイル（`thumb:<送信先>`）のいずれかである。
- トークンは（持ち手、送信先、`mode`、精度、世代）の組ごとに一つ作り、組が変わらない間は同じ値を使う。表は保存し、再起動の後も同じトークンを使う。MapLibre の端末内のキャッシュが URL を鍵にする場合も、規則が変わらない限り、再起動の後にキャッシュが効く（試作で確かめる）。
- トークンの表は許しではない。interceptor は、トークンの持ち手が **今の起動の許し**（[4.2 節](#42-送信の許しpermit)）を持ち、その許しの送信先、`mode`、精度、世代がトークンの組と一致することを確かめる。再起動の前の許しは起動の識別子が異なるので通らず、持ち手は再起動の後に許しを得直すまで送れない。

interceptor の検査は次の順に行う。

1. 印のない要求、表にないトークンの要求は拒む。
2. 要求の URL を、トークンの送信先の URL の型（ホストとパスの先頭）と照合する。一致しなければ拒む。カスタムの URL が組み込みの地図と同じホストを指す場合も、トークンが送信先を決めるので区別できる。
3. 持ち手の今の許しを確かめる。`mode` が `OnAction` なら、その地図の画面の今の表示が送信先の許可（grant）を持つことも確かめる。画面の外に出た地図は許可を返しているので、その後の要求は拒まれる。
4. タイルの URL から z を読み、精度の上限を超える要求を拒む。
5. 印を取り除いてから送る。印は端末の外に出ない。

*interceptor で確かめられない同意と、その担保*：

- **要求を出したのが、トークンの持ち手の地図か**：interceptor は、どの MapView や静止画が要求したかを知らない。判定（一段目）が、持ち手ごとにトークンを埋めたスタイルを作り、その持ち手にだけ渡すことで担保する。スタイルの一時ファイル（`MapStyle.styleFile`）は持ち手ごとに分け、内容のハッシュによる共有をしない。
- **静止画の票の順序**：待機中の静止画が設定の変更の前に予約されたものかは、静止画の待ち行列（`SnapshotQueue`）が開始の直前に許しを得ることで担保する。

*印を運べない経路*：スタイル、TileJSON、スプライト、フォントのうち、試作で印が最終の要求まで届かないと分かった種類は、MapLibre に遠隔の URL として渡さない。アプリが `Outbound` で取得して端末内のファイルに置き、`file://` で参照する（別の HTTP の経路）。これらは座標を直接含まない。それ以外に印のない要求が interceptor に届いた場合は拒む（地図はその資源なしで描かれる）。

### 4.5 一時停止

一時停止は、地図、地名、施設の検索、データの取得への送信をまとめて止める。

- 規則は書き換えない。停止の間は、すべての送信先を「送信しない」として判定する。
- 開始と解除のどちらでも、全送信先の世代を進める。停止の前に作った許しと票は、解除の後も無効である。
- 開始の時点で、`Outbound` の接続をすべて切り、MapLibre の待機中の要求は持ち手の許しの失効で拒み、データの取得の WorkManager の作業と、予約した再試行を取り消す。
- 解除しても、操作による送信は再開しない。自動の処理は規則に従って新しい許しで始める。データの取得は、規則が自動なら改めて予約する。
- 同期、OS の測位、他のアプリへの受け渡しは止めない。名前と画面の 1 行でこれを示す（[5.2 節](#52-データの扱い)）。

### 4.6 三つの防御線

1. **判定**：判定の関数が、送ってはいけない場合に端末内のスタイルを選び、要求そのものを作らない。今と同じく、これが主である。
2. **MapLibre の通信可否**：`MapLibre.setConnected` をプロセス全体に効かせる。今と同じく補助である。
3. **送信の直前の確認（新規）**：`Outbound`、Geocoder の直前の確認、MapLibre の interceptor（[4.4 節](#44-outbound)）。

### 4.7 判定の関数と精度の適用

`BaseMapPolicy` の引数を `block: Boolean` から、地図の送信先の規則に変える。

| 関数 | 今 | 変更後 |
| --- | --- | --- |
| `interactive` | `block` が false なら選んだ地図、true なら同意した地図 | 選んだ地図の送信先が Auto なら選んだ地図、OnAction なら同意した地図、Never ならオフライン地図 |
| `snapshot` | `block` が false なら選んだ地図 | 選んだ地図の送信先が Auto なら選んだ地図、ほかはオフライン地図 |
| `thumbnail` | `block` が false なら描画 | 候補ごとに、その候補の送信先が Auto の場合だけ、その精度の上限で描画する。ほかは同梱の見本 |
| `offerAlternatives` | `block` かつ地図なし | 「オンライン地図で表示」の地図の送信先が OnAction かつ地図なし |
| `detailMap` | 選んだ地図、なければ最後のオンライン地図 | 加えて、送信先が Never の地図を除く。すべて Never なら None |

サムネイルは、選んだ地図の送信先だけでなく、各候補の送信先へ表示範囲を送る。
各候補の規則で判定するので、自動を許していない送信先へは送らない（[未決 17](#9-未決の事項)）。

精度は次の関数で適用する。

- `Precision.snap(lat, lon, gridDeg): (Double, Double)`：固定の格子の区画の中心を返す。Geocoder と Overpass の「地区」「地域」で使う。
- `Precision.maxZoom(level): Option[Int]`：地域は 12、地区は 15、制限なしは None。
- `TileStyle.capped(style, maxZoom, holder, permit)`：スタイルのすべてのソースの `maxzoom` を上限以下にし、すべての遠隔の URL に持ち手と許しの組のトークンを付ける（[4.4 節](#44-outbound)）。ラスタ（地理院、カスタム）はアプリが JSON を作る。OpenFreeMap はスタイルの URL を直接 MapLibre に渡しているため、スタイルと TileJSON を先に取得し（座標を含まない）、ソースを `tiles` と `maxzoom` を持つ形に書き換えて端末に置く。

| 「オンラインで検索（位置を送信）」（`CheckInSheet.scala`、`PlaceSheet.scala`） | 常に表示 | Overpass が Never または一時停止なら表示しない |
| `PinnedDownload.autoStart`、`PinnedWorker`（`BasemapDownload.scala`） | 常に動く | `autoStart` は `data` が Auto の場合だけ。作業は予約の時点の送信先、`mode`、世代を入力に持ち、実行のたびに許しを得直し、再試行のたびに確かめる |
| 地域データの取得（新規） | ― | `data` が「区画」で Never でない場合だけ。操作で始め、更新は Auto と自動更新の設定がある場合だけ自動 |

### 4.9 形式検証

[`formal/README.md`](../../formal/README.md) が将来の課題に挙げる `SendGate` の TLA+ モデルを、送信先ごとの世代と許しで作る。
タイルの送信先 2 つ（同じホストのカスタムを含む）、Geocoder 1 つ、表示 2 つ、静止画の待ち行列、再試行、リダイレクト、一時停止を含め、次を検査する。

- 送信先 d への送信は、その時点で有効な d の許しを持つ場合だけ起きる（自動、操作、再試行、リダイレクトのすべて）。
- 表示が送信先 d へ送るのは、d が Auto か、その表示が d の現在の許可を持つ場合だけ（別の表示の許可で送らない）。
- Never の送信先へは、操作による送信も含めて送らない。一時停止の間はどこへも送らない。
- 一時停止の解除の後に、停止の前の許しで送らない。
- 再起動の後に、再起動の前の許しで送らない。保存した作業は、予約の後に規則が変わっていれば送らない。
- 送信先 d の規則の変更は、d と異なる送信先の許可と票を無効にしない（取り消しすぎない）。
- Geocoder は、規則の変更の時点で OS に渡していた 1 件を除き、変更の後に古い許しで送らない。

## 5. 画面の流れ

### 5.1 設定の入口

設定の「プライバシー」のスイッチ「オンライン地図と地名検索」を、行「データの扱い」に置き換える。
行の補足は送信を許す送信先の数とする（例「外部への送信 2 件を許可」、一つもない場合は「外部への送信なし」、一時停止の間は「外部への送信を停止中」、設定を読み込めない間は「データの手動取得のみ」）。

### 5.2 データの扱い

画面案の画面 5 に合わせる。
設定の結果を ✓ ／ ⊖ の一覧で示し、段落の説明は置かない。

```
← データの扱い

保存先
  ✓ この端末                       812 MB
  ✓ 同期サーバ                     暗号化して送信 · 最終 5分前   ›

外部への送信                       ✓ 許可  ⊖ 送信しない
  地図・検索への送信を停止                                    [  ]
  同期、位置の取得、他のアプリは対象外
  ✓ オンライン地図（OpenFreeMap）   表示範囲 · 操作時のみ          ›
  ✓ オンライン地図（地理院タイル）  表示範囲 · 操作時のみ          ›
  ⊖ オンライン地図（カスタム）      未設定                        ›
  ⊖ 地名検索                        滞在地・他の端末の位置        ›
  ✓ 施設のオンライン検索            位置 · 操作時のみ              ›
  ✓ 地図・施設データの取得          選んだ区画 · GitHub            ›
    位置の取得                      OS の設定による               ›
```

- ✓ は送信の **許可** を示し、今送信していることは示さない。⊖ は送信しない。見出しの右に凡例を置く。
- 記号の形で状態を示し、色だけに頼らない。✓ の記号は、今の送信の操作と同じ tertiary の色にする。
- 2 行目は「何を · いつ」とし、精度が制限なしでない場合は精度を付ける（例「表示範囲（約 1 km）· 自動」）。
- 地名検索の 2 行目は、送信しない間も送る対象（滞在地・他の端末の位置）を示す。許可の間は「滞在地・他の端末の位置 · 自動」とする。
- 一時停止のスイッチは「地図・検索への送信を停止」とし、対象外を 1 行で示す。停止の間は各行の ✓ を ⊖ の表示にし、2 行目を「停止中」とする。
- 「位置の取得」は OS の測位の参照であり、アプリが送信を制御しないので記号を付けない。[未決 5](#9-未決の事項) の結論まで表示だけにする。
- 設定を読み込めない場合（[3.5 節](#35-既定値復旧値読み込みの順序)）は、見出しの下に error の色で「設定を読み込めません（データの手動取得のみ）」を出す。

### 5.3 送信先の詳細

行を押すと、その送信先の画面を開く。
選択肢は 2 群のラジオボタンと、送信先のホストの 1 行だけとする。

```
← オンライン地図（地理院タイル）

送信
  ○ 送信しない
  ● 操作時のみ
     表示を許した地図は、戻すまで保持
  ○ 自動

精度
  ○ 地域 約 10 km      [格子の凡例]
  ○ 地区 約 1 km       [格子の凡例]
  ● 制限なし           [格子の凡例]

送信先  cyberjapandata.gsi.go.jp

                         [キャンセル]  [適用]
```

- 2 群の変更は「適用」でまとめて一つの規則として保存する。適用するまで、規則も送信も変わらない。時機を先に選んでも、精度を選ぶ前に制限なしで送る中間の状態はない。
- 「適用」は変更がある間だけ有効にする。変更を残したまま戻る場合は、変更を捨てる。
- 「送信しない」の間も精度の群は選べる。次に許可するときの精度を先に決められる。
- 精度の凡例は、地図の上の格子と、送る座標の粒度の区画の塗りで示す（画面案の凡例と同じ）。
- 施設のオンライン検索は、精度の下に「検索先」としてホストごとのスイッチを置き、運営者が同じホストはまとめて示す。すべてオフは選べない（その場合は「送信しない」を選ぶ）。
- カスタムは「送信先」の行に URL のホストを出し、押すと今の URL の入力を開く。
- 地名検索は「送信先」の下に「対象  滞在地・他の端末の位置」の 1 行を置く。
- 適用の後、待機中と実行中の処理はその時点で新しい規則に従う（[4.2 節](#42-送信の許しpermit)）。

## 6. オフラインの地域データ

### 6.1 現状

| 項目 | オフライン地図 | 施設データ |
| --- | --- | --- |
| 内容 | 日本（ズーム 6〜10、`japan.pmtiles`）と全世界（ズーム 0〜5、`world.pmtiles`）、スタイル、フォント、スプライト | 日本の施設 1,073,493 件（`venues.aven`） |
| 大きさ | 約 64 MB（archive 63,591,472 バイト） | 約 18 MB |
| 作り方 | `tools/basemap/build.sh`：Protomaps の日次ビルド（`https://build.protomaps.com/<日付>.pmtiles`）から go-pmtiles の `extract` で切り出す | `tools/venues/build.sh`：Geofabrik の日本の抽出から pyosmium で抜き出す |
| 配布 | GitHub Releases（タグ `basemap-<版>`）、同期サーバ（R2） | GitHub Releases（タグ `venues-<版>`） |
| 完全性 | APK に固定した大きさと sha256（`basemap-pin.json`） | 同じ（`venues-pin.json`） |
| 端末 | `filesDir/basemap/<版>/`（`BasemapStore`）、`PinnedDownload` が Range で再開する | `filesDir/venues/<版>/` |

スタイルは二つのソースを重ね、日本を全世界の上に、文字をすべての図形の上に置く（`tools/basemap/assemble.py` の `layers`）。
MapLibre は `pmtiles://file://` のソースを端末内で読んでおり、PMTiles の読み込みはこのアプリで動作を確かめた形式である。

起動時には `AshidoriApp.scala:44` 以降が `Basemap.cleanup()` と `VenueData.cleanup()` を呼び、固定した版以外をすべて消す。
地域データはこの掃除を流用しない（[6.7 節](#67-保存と復旧)）。

### 6.2 要件

- 地図の上の固定の枠に地図を動かして範囲を合わせ、大きさを 1 行で示す（画面案の画面 6）。
- 取得済みの一覧に、名前、大きさ、取得日、︙（更新、名前を変更、削除）、新しい版の印を示す。期限は設けない（画面案の画面 7）。
- 取得したデータは改ざんを検出できる（sha256）。
- 取得は中断しても再開でき、どの時点で止まっても一貫した状態に戻る。
- 既定では従量制でない回線を待つ。
- 地域データの取得で伝わる情報と、自動更新の有無を、取得の前に画面で示す。
- 取得と配置が記録の領域を使い切らない。

### 6.3 方式の比較

| 方式 | 配信元に伝わる範囲 | 端末の負担 | 完全性 | 配信元の負担 | 評価 |
| --- | --- | --- | --- | --- | --- |
| A. 固定の区画ごとのパックを静的ファイルで配る | 選んだ枠を含む区画の集合（約 130 km 四方の単位）と、その組み合わせ、順序、履歴 | 区画が枠より広い分だけ大きい。展開なし | ファイルごとの sha256 | 静的ファイルのみ | **採る** |
| B. 大きな archive（日本全体の詳細）を取得し、端末で使う | 細かな選択の範囲は送らない。日本全体を取得した事実と IP アドレスは伝わる | 未計測。数 GB と見込むが根拠はない。端末で切り出すなら一時的に 2 倍の容量 | archive の sha256 | 大きなファイル 1 つ（2 GiB を超えるなら分割） | 計測の後に、A に加える選択肢として決める（[未決 8](#9-未決の事項)） |
| C. 端末から大きな PMTiles へ Range 要求を送り、枠の分だけ切り出す | 枠そのもの。要求するバイト範囲がタイルの番号に対応するため、配信元は範囲を復元できる | 要求の数が多い | 切り出した部分は archive の sha256 で照合できない。タイルごとの署名つき一覧が別に要る | 細かい Range 要求が多数 | 採らない |
| D. MapLibre の機能でオンライン地図の配信元からタイルを一括取得する | 枠そのもの（タイル単位） | タイル数が多い（ラスタ） | なし | 配信元にタイルの一括取得を課す。各配信元の利用条件は確かめていない | 採らない |

A を採る理由は次のとおりである。

- 伝わる範囲が区画の単位に粗くなる。枠の位置そのものは送らない（組み合わせなどからの推測は [7.1 節](#71-設定ごとに伝わるもの)）。
- 今の配布の仕組み（静的ファイル、大きさと sha256 の固定、Range での再開、検証の後の原子的な配置）を使える。
- 区画は複数の地域で共有でき、重複して取得しない。

### 6.4 区画

区画は、Web メルカトルのズーム 8 のタイルとする（識別子 `8-<x>-<y>`）。

- 1 辺は北緯 35° で約 128 km であり、緯度が高いほど縮む。
- PMTiles のタイルの番号と揃うので、区画の内側のタイルはズーム 8 以上で区画の外にはみ出さない。隣の区画とタイルが重ならない。
- `tools/basemap/japan.geojson`（長方形の集まり）と交わるズーム 8 の区画は 136 個である（海だけの区画を含む。本書の作成時に数えた）。
- パックはズーム 8〜14 の、その区画の内側のタイルを持つ。タイル数は最大 5,461 である。Protomaps の公開ビルドの最大ズームは 15 だが、ズーム 15 は取得しない。ズーム 15 以上の店舗などは施設データから描く（[6.16 節](#616-施設の層)）。
- パックの大きさは計測していない。都市部と山間部で大きく異なると見込む。区画ごとの大きさは、最初の作業として日本の全区画で測る。

### 6.5 パック、スタイルの束、カタログ

| ファイル | 内容 |
| --- | --- |
| `ashidori-region-8-<x>-<y>-<版>.pmtiles` | 区画の地図（PMTiles v3、ズーム 8〜14）。zip に包まない |
| `ashidori-venues-8-<x>-<y>-<版>.aven` | 区画の施設データ（日本の外の区画だけ。[6.13 節](#613-施設データ)） |
| `ashidori-regions-style-<スタイル版>.zip` | パックの層の雛形、フォント、スプライト。パックの文字列の文字の範囲を含む |
| `ashidori-regions-<版>.json` | カタログ：区画ごとのファイル名、大きさ、sha256、範囲、ズーム、ビルドの日付、スタイル版、施設の件数。スタイルの束の大きさと sha256 |

カタログの例を示す。

```json
{"format":"ashidori regions catalog v1","version":"20261201","build":"20261201",
 "minzoom":8,"maxzoom":14,
 "styles":[{"style":"s1","file":"ashidori-regions-style-s1.zip","bytes":2345678,"sha256":"…"}],
 "cells":[
  {"cell":"8-227-100","style":"s1",
   "map":{"file":"ashidori-region-8-227-100-20261201.pmtiles","bytes":123456789,"sha256":"…"},
   "venues":null}
 ]}
```

- パックはスタイル版を持ち、同じスタイル版の束で描く。束はオフライン地図の archive から独立させる。オフライン地図の版の更新とパックの版がずれても、パックの描画は変わらない。
- スタイル版は Protomaps の層の定義（`@protomaps/basemaps` の版）とフォントの範囲で決める。パックの版が変わってもスタイル版が同じなら、束は取得し直さない。

完全性は二段で確かめる。

1. APK はカタログの大きさと sha256 を固定する（`regions-pin.json`、今の `BasemapPin` と同じ形式）。カタログの取得は座標を含まない。
2. パックとスタイルの束はカタログの大きさと sha256 で照合する。照合の後に PMTiles のヘッダを読み、範囲が区画の内側に、ズームがカタログの値に収まることも確かめる。

この形では、データの更新はアプリの版の更新とともに届く（今のオフライン地図と同じ）。
アプリと独立にデータを更新するための署名つきのカタログは、[未決 6](#9-未決の事項) とする。

配布は GitHub Releases のタグ `regions-<版>` とする。
1 リリースあたり 1,000 アセット、各ファイル 2 GiB 未満の上限に収める。
日本の区画だけなら、地図のパックは 136 個以下である。
2 GiB を超えるパックが出た場合は、その区画をズーム 9 の 4 区画に分ける。

### 6.6 地域とパックの関係

利用者が名前を付けて管理する単位を **地域**、取得の単位を **パック** とする。

- 地域は名前と区画の集合を持つ。枠で選んだ範囲が複数の区画にかかれば、その地域は複数のパックを参照する。
- 参照数は保存せず、地域の区画の集合から毎回求める。保存した数と実際がずれることがない。
- 地域の大きさは、その地域が参照するパックの合計とする。他の地域と共有するパックも含める。
- 地域の名前の既定値は、枠の中心の地名を端末内の索引で求めたもの（例「つくば市周辺」）とする。索引で求まらない場合は「地域 1」のように番号を付ける。Geocoder は使わない。

### 6.7 保存と復旧

```
filesDir/regions/
  state.json                         地域（名前、区画）、各パックの状態と版、取得日
  packs/<cell>/<版>/map.pmtiles      完全なパック（検証の後の改名で現れる）
  packs/<cell>/<版>/venues.aven
  styles/<スタイル版>/               スタイルの束を展開したもの
  .download/<file>.part              取得中のファイル
```

パックの状態は「予定」「取得済み」「使用不可」のいずれかである。
「使用不可」は、ファイルは完全だが描くのに要るスタイルの束がない状態であり、地図には組み込まない。

**書き込みの順序**：

1. 利用者の操作の時点で、`state.json` に地域と、取得するパックを「予定」として書く（一時ファイルと改名）。各パックには、カタログが示すスタイル版を記す。
2. パックのスタイル版の束が `styles/<スタイル版>/` になければ、束を取得し、sha256 を確かめ、一時のディレクトリに展開してから改名で置く。ディレクトリがあれば束は完全である。
3. パックを `.download/` に取得し、sha256 とヘッダを確かめる。
4. ディレクトリの改名で `packs/<cell>/<版>/` に置く。
5. 束のディレクトリがあることを確かめてから、`state.json` のそのパックを「取得済み」にする。

束は必ずパックより先に置き、束のないパックを「取得済み」にしない。

**起動時の照合**（地域データ独自の処理。`Basemap.cleanup()` は流用しない）：

- 4 と 5 の間で止まった場合、パックのディレクトリはあるが状態は「予定」である。ディレクトリは検証の後にだけ現れるので、束があれば「取得済み」に直す。
- 「取得済み」と「予定」のすべてのパックについて、記したスタイル版の束があることを確かめる。ない場合（束を消した、束の展開の途中で止まった、`state.json` を走査から作り直した）は、パックを消さずに「使用不可」とする。`data` の規則が許す場合は束の取得を予約し、置けた時点で「取得済み」に戻す。許さない場合は、一覧に「使用不可」と「再取得」の操作を出す。
- 3 で止まった場合、`.part` を残し、次の取得で続きから取得する（大きさが揃っていれば検証から再開する）。
- 状態にない区画のディレクトリ、どの地域も参照しない版、どのパックも参照しない束は、削除の候補とする（使用中は消さない）。
- 状態を読めない場合は、ディレクトリの走査からパックを復元し、各パックのヘッダとカタログからスタイル版を求め、束の有無で「取得済み」か「使用不可」とする。地域は区画ごとに一つずつの仮の地域として作り直す。データを消さない。

**使用中のファイルを消さない**：

- スタイルは作るたびに番号を持つ。地図と静止画は、読み込んだスタイルの番号を登録し、別のスタイルに替えるか破棄した時点で解除する。
- 削除と更新は、新しいスタイル（そのパックを含まない、または新しい版を含む）を全地図に適用した後、古い番号を参照する地図と静止画がなくなってから古いファイルを消す。
- 消せなかったファイルは `state.json` の削除の待ちに残し、起動時と参照の解除の時に処理する。

**版の保持**：

- 更新では、新しい版の検証と配置が済むまで古い版を残す。通信できない場所で更新が失敗しても地図は消えない。
- スタイルの束は、取得済みのパックが一つでも参照する版を残す。

**記録のデータベースとの分離**：状態は記録のデータベースに入れず、`state.json` に書く。地域データの処理が記録のデータベースの書き込みと競合しないためである。

### 6.8 容量の予算

256 MB は監視の閾値であり、予約された領域ではない。
記録は予約をせずに書き続けるので、記録のための領域は「大きな処理が使ってよい量から除く予備」として守る。
アプリの大きな書き込みは共通の予算（`StorageBudget`）を通す。

**対象**：オフライン地図と施設データの取得と展開、地域データのパックとスタイルの束の取得と展開、バックアップの書き出しの一時ファイル（`VACUUM INTO` の複製）。

**記号**：

| 記号 | 意味 |
| --- | --- |
| `F` | その時点の空き容量（`getUsableSpace`）。書き込んだバイトはすでに引かれている |
| `R_j` | 処理 j が予約したバイト数（取得なら残りの大きさ、展開なら展開後の大きさ、バックアップなら複製の見込み） |
| `W_j` | 処理 j が予約の後に書いたバイト数。書いた分だけ増やす |
| `O_j = max(0, R_j − W_j)` | 処理 j の未消化の予約。書いた分は `F` に反映されるので、予約からは引く（二重に数えない） |
| `L` | 記録の予備。`max(256 MB, 現在の記録モードの書き込み速度 × 24 時間)` |

記録の書き込み速度は、記録のデータベースとアーカイブの増え方を直近の数時間で測った値とし、測れない間はモードごとの既定値を使う。
最高精度のモードでは `L` が数 GB になりうる（今の形式で 1 時間 157 MB。[`detail-log-format.md`](detail-log-format.md)）。
その間は大きな処理が始まらないことがあり、これを受け入れる。

**式と確かめる時点**：

- **予約の受付**：新しい予約 `r` は `F − Σ O_j − L ≥ r` の場合だけ受け付ける（`Σ` は受付済みのすべての処理）。受け付けない場合は始めず、`setRequiresStorageNotLow` と同じく後で再試行する。
- **書き込み中**：各処理は 1 MiB 書くごとに `W_j` を増やし、`F − Σ O_j < L` になれば書き込みを止める。取得は `.part` を残して一時停止し、展開は一時のディレクトリを消して中断する。予約は返す。
- **段階の境目**：取得から展開に移る前、バックアップの複製の前に、その段の大きさで予約し直す。
- **完了と中断**：予約を返す（`R_j` を消す）。消した一時ファイルの分は `F` が戻る。

記録は予約を持たないので、`F` を減らし続ける。
`F − Σ O_j` が `L` を割った時点で大きな処理はすべて止まり、それ以降の空きは記録だけが使う。
大きな書き込みは一度に一つに限る（予約を直列にする）ので、確かめる時点の間に複数の処理が同時に空きを減らすことはない。
他のアプリによる容量の消費は防げない。予算が守るのは、このアプリの重い処理が記録の予備を使うことである。

### 6.9 取得

- WorkManager の一意の作業（`regions-download`）が、待ち行列のパックを 1 つずつ取得する。今の `PinnedWorker` と同じく、`ResumableDownload`（Range での再開）と `DownloadRetry` を使い、`Outbound` を通す。
- 作業は予約の時点の送信先（`data`）、`mode`、世代を入力に持ち、実行のたびに新しい許しを得て、再試行のたびに確かめる（[4.2 節](#42-送信の許しpermit)）。
- 既定では従量制でない回線を待つ（`regionsMetered` が false）。モバイルデータ通信の場合は、今のオフライン地図と同じ確認の画面を出す。
- 取得の要求は端末のトークンもクッキーも持たない。User-Agent は今と同じ `ashidori/<版>` とする。
- 取得の順序は、選んだ順でも中心からの順でもなく、区画の識別子の順とする。順序から選択の中心を推測させないためである。

### 6.10 地図への組み込み

端末内のスタイルは、今のスタイルに取得済みのパックのソースを加えて作る。

- パックごとにソース `r-8-<x>-<y>`（`pmtiles://file://…/map.pmtiles`、`minzoom` 8、`maxzoom` 14、`bounds` は区画）を加える。
- 層は、パックのスタイル版の雛形を、パックのソースの名前で複製する。順序は「全世界の図形、日本の図形、パックの図形、全世界の文字、日本の文字、パックの文字」とし、今の `assemble.py` の重ね方に従う。
- フォントとスプライトは、パックの層ではスタイルの束のものを使う。MapLibre のスタイルの `glyphs` は一つしか指定できないため、束のフォントはオフライン地図のフォントの範囲を含む上位の集合とし、パックがある場合は束のフォントを `glyphs` にする。
- 区画の内側では、パックの図形がオフライン地図の図形を覆う。文字の重なりは MapLibre の衝突の判定に任せる。区画の境界と、ズーム 8〜10 で日本のソースと重なる部分の見た目は実機で確かめる。
- ソースの数が増えると描画の負担が増える。パックの数の上限（例 16）を設け、実機で測ってから決める。上限を超える使い方が要る場合は、端末で複数のパックを一つの PMTiles に合成する方式を検討する（[未決 11](#9-未決の事項)）。
- パックの追加と削除でスタイルを作り直し、表示中の地図に読み込み直させる（[6.7 節](#67-保存と復旧)）。スタイルの照合（`OfflineBasemapStyle.remoteUrls` が空）は今と同じく行う。

### 6.11 範囲の選択

画面案の画面 6 に合わせる。

```
✕  この範囲の地図を取得

   ┌──────────────┐   区画の枠（薄い線）を地図に重ねる
   │   固定の枠   │
   └──────────────┘

   180 MB · 空き 41.2 GB
   GitHub に伝わる範囲: 区画 2 個
   [✓] Wi-Fi 接続時に自動更新

   [キャンセル]          [ダウンロード]
```

- 枠は画面に固定し、利用者は地図を動かし拡大縮小して範囲を合わせる。
- 枠と交わる区画を地図に薄い線で示す。取得するのは枠ではなく区画であり、その区画が配信元に伝わる。
- 大きさはカタログの値の合計であり、見積もりではない。取得済みの区画は除く。予算（[6.8 節](#68-容量の予算)）に収まらない場合は、ダウンロードを無効にし「空き容量が不足」と出す。
- 自動更新の有無はこの画面で選ぶ。初回の既定はオンで、前回の選択を引き継ぐ。`data` が「操作時のみ」の場合は、この行を出さない。
- 区画が上限（例 4 個）を超える縮尺では、「範囲を狭めてください」と出し、ダウンロードを無効にする。
- カタログにない区画（日本の外など）は灰色にし、合計に含めない。
- 入口は、地図のタブの ︙ の「地図をダウンロード」と、「オフラインのデータ」の「＋ 範囲を選んで取得」とする。

### 6.12 管理の一覧と更新

画面案の画面 7 に合わせ、「オフラインのデータ」とする。
今の「オフライン地図」と「施設データ」の行も、同じ部品でこの一覧に入れる。

```
← オフラインのデータ                     ＋ 範囲を選んで取得

  ✓ 関東                新しい版     412 MB · 2026/10/13   ⋮
  ✓ つくば周辺                        38 MB · 2026/11/02   ⋮
```

- 状態は先頭の記号で示す（✓ 取得済み、↓ 取得中・待機中、! 失敗・使用不可）。失敗は error の色の 2 行目に理由を出し、使用不可は「使用不可（スタイル未取得）」とする。
- 取得日は、その地域のパックを最後に取得した日とする。
- 「新しい版」の印は、地域のパックのどれかについて、APK のカタログの版が端末の版より新しい場合に出す。

- 期限は設けない。古い版も削除されるまで使える。
- 自動更新（`regionsAutoUpdate`）は、新しいカタログを持つアプリに更新された後、取得済みの区画の新しい版を取得する。`data` が「自動」の場合だけ動き、「操作時のみ」では一覧の「更新」でだけ更新する。
- 「モバイルデータ通信でも取得」（`regionsMetered`、既定オフ）は、自動更新の行の先の画面に置く。

### 6.13 施設データ

- 日本は今の施設データ（日本全体で約 18 MB）をそのまま使う。区画に分けても伝わる範囲が粗くなるだけで、大きさの利点が小さいためである。
- 日本の外の区画は、地図と同じ区画で施設データのパックを作る。地域を取得すると、地図と施設のパックを合わせて取得する。
- `VenueData` は今は索引を一つだけ開く。区画の索引を複数開き、検索の位置に交わる索引だけを引くように変える。`VenueIndex` の AVEN 形式は格子の原点と大きさを持つので、形式は変えずに区画ごとに作れる。
- 施設の名前での検索（`VenueData.search`）は、取得済みのすべての索引を引き、距離で並べる。

### 6.14 外部送信の設定との関係

- 地域データの取得は、`data` が「区画」で「送信しない」でなく、一時停止でない場合だけ使える。「全域のみ」では「＋ 範囲を選んで取得」を出さない。
- 範囲の選択とダウンロードの操作を、区画を送る同意とする。取得の画面に「GitHub に伝わる範囲: 区画 N 個」を出す。
- 同期サーバからは地域データを取得しない（[未決 9](#9-未決の事項)）。
- 地域データは端末内のデータなので、取得済みの範囲の表示は外部への送信の設定に関係なく使える。
- オンライン地図に精度の上限（地区、地域）がある場合、上限より拡大した部分を地域データで描く組み合わせは、後の課題とする（[未決 12](#9-未決の事項)）。

### 6.16 施設の層

> 状態：**実装済み**（`core:VenueIndex.within`、`core:VenueMapLayer`、`app:ui/VenueLayer.scala`。「訪れた日」は `core:VisitIndex`、`app:VisitDays`）。

**決定**：地域データのパックはズーム 14 までとし、店舗などは施設データから地図に描く（利用者の判断、2026 年 11 月）。

- Protomaps のビルドは、店舗の POI の多くをズーム 15 のタイルにだけ持つ。ズーム 14 までのパックでは、表示のズーム 16 以上で店名が消える。
- 施設データ（`venues-20261014`、AVEN 2、`VenueIndex`）はチェックインのために取得済みで、日本全体を約 18 MB で覆う。これを記号の層として地図に重ねれば、パックにズーム 15 を持たせずに店名を描ける。
- パックのタイル数は、ズーム 8〜15 の最大 21,845 に対し、ズーム 8〜14 では最大 5,461 である。大きさの差は区画ごとの計測で確かめる（[6.4 節](#64-区画)）。

**網羅の検証**：ズーム 15 のタイル 1 枚の範囲で、Protomaps light が描く POI と施設データを照合した。

| 範囲 | 基図が描く POI（名前つき） | うちバス停、トイレ、ベンチ | 施設データ | 同じ名前で 30 m 以内 | 施設データだけ |
| --- | --- | --- | --- | --- | --- |
| 東京駅（15/29105/12903） | 258（210） | 31、25、9 | 269 | 155 | 107 |
| つくば駅（15/29137/12858） | 68（67） | 21、0、0 | 94 | 44 | 48 |

- バス停、トイレ、ベンチを除くと、名前つきの基図の POI の 97〜100% が施設データにある。表記の揺れ（英語名だけの POI、`name` のない POI）と 30 m を超える位置のずれを許して照合した。
- 施設データだけにある施設は、居酒屋、会社、土産物店、交番、銀行、薬局、ホテル、官公庁などである。

**欠けるもの**：

- バス停（`highway=bus_stop`）。施設データは抽出していない。基図はズーム 18 で描く。
- トイレ、ベンチ、水飲み場。チェックインの対象でないため、`tools/venues/build_index.py` が除く。
- 建物の細部。ズーム 15 のタイルの建物の形と名前は補えない。ズーム 15 以上ではズーム 14 のタイルを引き伸ばす。

**表示の規則**（`VenueMapLayer`）：

| 表示の始まり | 対象 |
| --- | --- |
| ズーム 15 | 駅、バスターミナル、空港などの交通、モール、百貨店、スーパー、博物館、劇場、公園、動物園、水族館、テーマパーク、スタジアム、城、大学、病院、役所、図書館、観光地 |
| ズーム 16 | ほかのすべて |
| ズーム 17 | 事務所（`office=*`。官公庁を除く） |

- ズーム 14.5 未満では層を空にする。表示の範囲の外側に縦横 25% ずつ広げて読み、1 段先のズームの施設まで含め、層の `filter` で始まりのズームまで隠す。拡大した直後に、次の読み込みを待たずに現れる。
- 色は Protomaps light の POI の文字の色に揃え、群で分ける（交通 `#315BCF`、文化 `#EF56BA`、緑地 `#20834D`、飲食 `#CB6704`、買い物 `#1A8CBD`、公共 `#6A5B8F`、その他 `#6F6A66`、事務所 `#8C8781`）。文字の大きさと配置は light の `pois` 層と同じで、縁取りは白とする。字体はその地図のスタイルの文字の層から取る。
- アイコンは、オフライン地図ではスプライトの同じ名前の画像（駅は `train_station`）を使う。ほかの地図と、スプライトにない種類では、群の色の点とする。
- 衝突の順（`symbol-sort-key`、小さいほど先に置く）は「（始まりのズーム − 15）× 10 + 群の順」とする。群の順は交通 0、文化と緑地 1、飲食と買い物 2、公共 3、その他 4、事務所 5 である。ズーム 17 以上ではモールと百貨店を 20 + 群の順とし、中の店と飲食店を先に置く。
- 層は基図の POI と地名の層の下に置く（Protomaps の `*-pois`、`*-places_*`、OpenMapTiles の `poi_*`、`place_*`）。見つからない場合はアプリの経路の層の下に置く。衝突では基図の文字が勝つ。
- 同じ名前（NFKC、小文字、空白を除く）の施設は 50 m 以内で一つにする。駅は路線や事業者ごとに点があるので 400 m 以内で一つにする。上限は 1,200 件で、衝突の順、中心からの近さの順に選ぶ。GeoJSON は 256 Ki 文字までとし、名前は 48 文字で切る。
- 基図の POI との名前の照合はしない。描画済みの POI を読む `queryRenderedFeatures` が、エミュレータの主スレッドで 8〜70 ms かかった。同じ位置の同じ名前は、層の順により基図の POI が衝突で勝つ。点が数百 m 離れている場合は両方が出る（東京駅の駅名など）。

**読み込み**：カメラが止まって 200 ms 後に、表示の範囲を地図ごとに 1 本の背景のスレッドで読み（`VenueIndex.within`）、GeoJSON のソースを置き換える。カメラが動き始めた後と、新しい要求が来た後に届いた古い答えは捨て、変わらない答えも捨てる。施設データの取得と削除（`VenueDownload` の通知）で表示中の範囲を読み直し、データがなければ層を空にする。スタイルを外すときに地図のカメラのリスナーを外し、地図を閉じるときにスレッドも止める。`within` は範囲と交わる区画を含むブロックだけを展開し、展開したブロックは既存の LRU（24 ブロック、16 MiB）に残る。東京駅の周りの計測を示す。

選別と GeoJSON の作成は、エミュレータのデバッグ版で 15〜80 ms（ズーム 15 の 1,764 件では約 300 ms）かかり、背景のスレッドで行う。主スレッドの仕事は、ソースの置き換え（0.1〜6 ms、解析は MapLibre の背景で行う）と、スタイルを読み込むたびの層の追加（3〜7 ms）である。パンの間に描画の遅れは記録されなかった。

**字形**：字形（`glyphs`）のないスタイルの記号の層は、アイコンも含めて何も描かない（地理院の地図で確かめた）。

- ラスタの地図（地理院、カスタム）のスタイルには、オフライン地図があればそのフォント（`file://`、全 BMP の範囲）を `glyphs` に入れる。オフライン地図の取得と削除で、表示中のラスタの地図を読み込み直す。
- オフライン地図がなくラスタの地図を表示する場合と、基図のない画面では、層を置かない。

**送信**：施設データは端末の中にあり、層のために送るものはない。施設データがなければ層は空である（説明の文言は出さない）。オンラインのベクタの地図（OpenFreeMap）では、層の文字の字形をその地図のフォントから読む。伝わるのは文字の範囲であり（[7.1 節](#71-設定ごとに伝わるもの)の「フォントの要求」）、その地図の同意の範囲に収まる。

**読み上げ**：地図の上に、触れない透明な view を重ね、描かれた施設（衝突の後に残ったもの）を仮想の view として示す（`ExploreByTouchHelper`）。TalkBack は「名前、種類」（例「ロフト、雑貨店」）を読む。

- 仮想の view の番号は OpenStreetMap の id ごとに、層の寿命の間で固定する。地図を動かしても同じ番号が別の施設を指さず、焦点は同じ施設に残る。焦点のある施設が見えなくなった場合は、焦点を外す（別の施設に移さない）。
- 対象は、地図の上に描くアプリの view（シート、ボタン、バナー）に覆われない部分だけとする。幅いっぱいの覆い（シート）で範囲を縮め、その範囲だけを `queryRenderedFeatures` で読み、小さな覆い（ボタン）の下のアイコンは除く。シートの移動と状態の変化（`TrackMap.overlaysChanged`）、ウィンドウの配置の変化のたびに、150 ms 待ってから一覧を作り直し、覆われた施設に焦点があれば外す。地図を止めたままシートを半分まで上げると、施設の節点は 28 件から 16 件になり、シートの上に収まった（`uiautomator dump`）。
- 衝突の順と中心からの近さで 100 件に絞ってから画面の座標に変換する。各 view の範囲は、アイコンとラベル（文字の大きさと、全角 1 em、半角 0.6 em、8 em で折り返すとした幅）を覆う。
- 一覧は支援技術が尋ねたときにだけ主スレッドで作る。エミュレータで、東京駅のズーム 16 の 28 件に 13.2 ms かかった。`uiautomator dump` で、施設の節点がシートの上端とチェックインのボタンにかからないことを確かめた。

**操作**：記号のタップ（TalkBack では仮想の view の実行）で、施設のシート（`app:ui/VenueCard.scala`）を日のシートの上に開き、記号を群の色の輪で示す。シートは施設のアイコン、名前、種類、現在地からの距離（位置がある場合）、「チェックイン」と「訪れた日」を持つ。地図の空いた所のタップ、閉じるボタン、戻る操作で閉じる。何も送らない。

- 「チェックイン」の対象は文脈で決める（`core:VenueCheckIn.target`）。日の表示で選択中の滞在（施設が 1 km 以内の場合）、次に表示中の日の滞在で施設が中心から 150 m 以内（または滞在の半径以内）のもの（最も近い滞在との差が 25 m 以内のものから、時刻が現在に近いもの）、次に今日の表示で現在地（30 分以内の位置）が 100 m 以内なら現在とする。どれもなければボタンを出さない。
- 対象が過去の滞在なら、ボタンにその滞在を示す（「チェックイン（12:14 の滞在）」）。
- 滞在へのチェックインの時刻は、場所のシートと同じく滞在の開始から 10 分後（短い滞在は中央）とする。日の表示はその滞在に「✓ 施設名」を出す。押すとシートを閉じるので、二度押しても一件である。スナックバーの「取り消し」はチェックインを削除し（同期される削除。[`sync-protocol.md`](../sync-protocol.md) の Tombstones）、それが付けた場所の名前を戻し、それが作った場所を削除する。

**滞在先の選択**：過去の滞在の滞在先とチェックインの修正は、一つの画面（`app:ui/VenuePicker.scala`）で行う。日の「✎ 編集」と場所のシートの「滞在先を選択」から開く。

- 上半分は滞在に合わせた地図で、滞在の位置と半径、施設の層を描く。下半分は滞在に近い施設と過去のチェックイン先の一覧、施設データの名前の検索である。地図の施設のタップと一覧の選択は同じ動作で、その滞在にすぐチェックインし、施設を輪で示す。TalkBack では各施設の操作の名前を「チェックイン」とする。
- 地図のタップでは、施設が滞在の印より先に当たる。滞在の印は施設に重なるため、印を先にすると重なった施設を選べない。
- 保存は一つのトランザクションで、その中で滞在のチェックインを読み直す（画面が読んだ値を使わない）。チェックインがあれば行を書き換え（同じ id、時刻、コメント、公開範囲を残し、施設名、位置、種類、場所を変える）、なければ加える。同期は id ごとに最新の行を採る。保存が終わるまで、次の選択は受け付けない。
- 場所の名前も施設の名前にする。ただし名前が利用者のものなら変えない（`core:VenueCheckIn.renames`）。名前の由来は場所の `name_source` に残す（DB 版 9。`user`：入力した名前と、施設 id のない名前。`venue`：施設 id とともに施設が付けた名前）。変えるのは、名前も種類（自宅など）もない場所と、由来が `venue` の場所だけである。版 9 より前の名前は由来が分からないので変えない。施設 id は手で名前を変えた後も残るので、id があることは由来の印にならない。チェックインの画面は、場所の名前を候補にするとき、由来が `venue` でなければ施設 id を付けない。`name_source` は同期しない。
- 「取り消し」は、その操作が書いた値が行に残っている場合だけ、元の値を書き戻す（加えたチェックインは削除する）。後の操作で行が変わっていれば何もしない。場所の名前も、その操作が付けた名前が残っている場合だけ戻す。
- 地図の面は日の表示と期間の表示と別で（`MapStyle.SurfacePicker`）、オンライン地図の同意は引き継がない。

**訪れた日**：施設のシートの「訪れた日」は、その施設に滞在した日の一覧を新しい順に最大 50 日示す。行は日付、時刻の範囲、滞在の長さで、押すとその日を日の表示で開く。同じ日に複数回の滞在があれば、最初の開始から最後の終了までを示し、回数を添え、長さは合計とする。

当初の試作は、索引なしで日ごとに位置を読んだ（今日から 730 日、1 分ごとに抜き出した位置が施設から 500 m 以内の日だけ日の記録を作る）。エミュレータで 79 日に 43 秒（位置の読み出し 16 秒、21 日の記録の作成 27 秒）かかり、1 分ごとの抜き出しと 500 m の判定は短い滞在や半径の大きい滞在を落としえた。これを日ごとの空間の索引に置き換えた。

- **内容**：日ごとに、日の表示と同じ組み立て（`TimelineRepo.built`、前後 12 時間の文脈、真夜中で切る）で得た滞在の開始、終了、中心、半径を持つ。各滞在を、中心から「施設にいる」とみなす距離（150 m と半径の大きい方、最大 2 km）の四角が触れるすべての区画（0.002° 四方。北緯 35° で南北約 220 m、東西約 180 m）に登録する（区画と日と滞在の行、区画に索引）。
- **問い合わせ**：施設の区画と隣の 8 区画に登録された滞在を、日の新しい順に 64 日ずつ読み、中心からの距離で絞り、50 日がそろえば止める（何年分を持っても読む量は増えない）。距離の判定は登録と同じ上限を使う（`VisitIndex.at`：中心から 150 m と半径の大きい方、ただし 2 km まで）。半径が 2 km を超える滞在は、中心から 2 km までの施設の日になる（チェックインの対象の判定 `VenueCheckIn.near` は上限を持たない。別の問いである）。極の近くで登録の区画を切った場合も、判定は登録した区画に施設があることを求めるので、索引と全件の判定は一致する。core のテストで、東京、南半球、北緯 64°、180° 経線、北緯 89.8° の無作為の滞在と施設について一致を確かめ、半径 2.5 km の滞在で両者が同じ 2 km で切れることを確かめた。
- **別のファイル**：索引は派生のデータで、記録と別の SQLite のファイル（`no_backup/visit_index.db`）に置く。記録のデータベースに表を加えない。いつ消しても記録から作り直せる。壊れたファイルは削除して作り直す（Android の既定の処理）。索引の失敗は一覧を空にするだけで、記録に触れない。記録サービスは索引を開かない。同期せず、バックアップに含めず、送信しない（[`privacy.md`](../privacy.md#訪れた日の索引)）。
- **新しさ**：索引は記録をどこまで読んだか（位置と動きの最大の rowid、削除の連番）を持つ。両表の rowid は増える一方である（`rowid_floor`）。その後に加わった行の時刻から、その行を文脈に含む日（前後 12 時間）を「変わった日」とする。読むのは 1 歩につき各表 20,000 行までで、1 歩ごとに短いトランザクションとし、止める指示で中断する。記録の位置は索引の書き込みの鍵を取ってから読むので、もう一方のプロセスが進めた位置を「記録より先」と誤らない。削除した期間は、重なる滞在をすぐに索引から除き、前後の日を変わった日とする。今日は一覧を開くたびに変わった日とする。変わった日は作り直すまで前の滞在を示す。日は世代の番号を持ち、作る間に別の変更が入った日は作り直しを待つ（両方のプロセスが同じ日を作っても古い結果で上書きしない）。版、時間帯、または読んだ位置が記録より先の索引（別の記録）は空にして作り直す。
- **見落とさない**：索引が読む前に整理が行を SQLite から移すと、rowid では見つからない。そこで `:maintenance` は日の整理の前と、その確定の後の 2 回、その日と前後の日を索引のファイルで変わった日にする（`VisitDays.beforeArchiving`、`afterArchiving`。記録のデータベースは変えない）。前の印だけでは足りない。印の後にもう一方のプロセスがその日を作り直して印を消費し、その後に退避ファイルの取り込みなどで過去の日の行が SQLite に入ると、同じ整理（最大の rowid はその後に読む）がその行を移し、行は rowid でも印でも見つからない。確定の後の印があれば、その間の作り直しの後に必ずもう一度作り直し、最終の状態を読む（core のテストで、印、作り直し、遅れた行、整理の順を再現した）。整理の前に、その日を `no_backup/visit_index.archiving` に耐久的に書き、後の印の後に消す。整理の間、`:maintenance` はファイルのロック（`visit_index.archiving.lock`）を持つ。確定と後の印の間でプロセスが終われば（ロックは外れ、記録は残る）、次の整理の回、自動の修復、「整理を修復」が、中断した確定を終えた後にその日に印を付け、記録を消す。記録が壊れているか読めない場合は、索引を「新しさ不明」にしてから記録を消す（黙って捨てない）。一覧を開いた本体のプロセスも、記録の日に印を付ける（壊れていれば「新しさ不明」にする。消すのは `:maintenance` だけ）。

「新しさ不明」の印（`no_backup/visit_index.stale`）は世代の番号を持つ。印や記録の書き込みに失敗した場合と、「整理を修復」がファイルを隔離した場合に、番号を一つ進める。番号の読み取り、加算、書き込みと、作り直しによる消費は、両方のプロセスが取る一つのロック（`visit_index.gen.lock`）の下で行い、書き込みは一時ファイルからの rename とする。印のファイルが壊れていれば「消費済み＋1」に一度だけ書き直し、消費の記録が壊れていれば 0 に書き直して印を一つ進める（同じ壊れたファイルを二度新しい世代と見なさない）。壊れた整理の記録は、その内容ごとに一度だけ番号を進める（`visit_index.archiving.bumped`。記録を消すときに一緒に消す）。索引を使う前に、索引の書き込みの鍵の下で、新しい世代の印があれば索引を空にして作り直す（世代ごとに 1 回）。印を消せる（その世代を `visit_index.stale.done` に書ける）のは、作り直しを始めたときと終えたときの両方で、整理が進行中でも記録が残ってもおらず、その間に整理が始まっていない（`visit_index.archiving.seq` が変わらない）場合だけである。そうでない作り直しの後は、静かなときにもう一度作り直す。このため、整理の間に印を消費した後にプロセスが終わっても、印は残る（core のテストで確かめた）。どれも整理を待たせず、失敗させない（失敗は logcat に残す）。位置と動きの行が SQLite から出るのは、整理（前後に印を付ける）と削除（削除の連番）だけである。電池、状態、気圧、生データの行は滞在を変えない。SQLite を経ずに記録を書く経路を将来加える場合は、そこで印を付ける必要がある。
- **作る時機**：一覧を開いている間、本体のプロセスの専用の背景のスレッドで、変わった日、まだ作っていない日の順に新しい日から 10 日ずつ作り、そのたびに一覧を更新する。一覧を閉じると止まる。1 日の読み込みは日の表示で日を開くのと同じ大きさである。`:maintenance` では、未完了の整理の修復と整理を先に行い、その後に充電中なら 120 日、それ以外は 7 日まで、2 分以内で作る。整理の前に索引の読み取りは行わない（日の印だけを付ける）。
- **読み込み**：記録は既存の読み手（`Db.fixes`、`Db.motion`、`ArchiveStore.reading`）で読む。未完了の整理があっても例外にならない（[規則 C](../recording.md)）。新しい行の時刻は SQLite の rowid の範囲から読むだけである。
- **表示**：索引にある日をすぐ示す。まだ作っていない日がある間は、最後の行に「以前の日は集計中」と示す。失敗は「なし」とも、古い結果とも区別する。索引を読めない場合、変更の確認に失敗した場合、作り終えた後も最新でない日（作ったことがない日と、変わった後に作り直せなかった日）が残る場合は、「読み込めません」（見つかった日を示している場合は「一部の日を読み込めません」）と「再試行」を示す（`VisitIndex.footer`）。行の TalkBack は「11月13日（金）、12:12 – 13:01、48分」と読み、操作の名前を「この日を開く」とする。

## 7. 脅威とプライバシーの分析

### 7.1 設定ごとに伝わるもの

| 設定 | 受け取る者 | 伝わるもの | そこから推測できること |
| --- | --- | --- | --- |
| オンライン地図、操作時のみ | 選んだ地図の配信元 | 同意した画面で表示した範囲のタイル番号（精度の粒度）、要求の順序と時刻、IP アドレス | 関心のある地域。現在地の近くを表示する習慣があれば現在地 |
| オンライン地図、自動 | 各地図の配信元 | 加えて、フィード、期間、他の端末の静止画の範囲（過去の日の経路と滞在地を収める範囲）。サムネイルでは各候補の配信元に現在の表示範囲 | 自宅、職場、移動の範囲、他の端末の所在 |
| オンライン地図、地域・地区 | 同上 | タイル番号の粒度がズーム 12、15 になる | 粒度は粗くなるが、隣り合うタイル、順序、時刻、画面の大きさから細かく推測しうる（[3.2 節](#32-精度の意味)） |
| オンライン地図（カスタム） | 入力した URL のホスト | 上記と、URL の API キー | 上記が、配信元の利用者アカウントと結び付く |
| フォントの要求 | 地図の配信元（OpenFreeMap） | 表示する文字の範囲 | 表示した地域の文字の種類（例：ハングル、アラビア文字）。座標は直接含まない |
| 地名検索、自動 | Geocoder の実装の提供者 | 索引で求まらない滞在地と、他の端末の現在地の座標（精度の粒度）、問い合わせの時刻 | 滞在した場所、他の端末の所在。提供者の側で端末やアカウントと結び付くかは未確認 |
| 施設のオンライン検索、操作時のみ | 有効にした Overpass のホスト（最大 4 ホスト、3 者） | 検索した位置（精度の粒度。地区では中央の 0.01° の区画）、時刻、IP アドレス、アプリの版 | その時刻にその場所付近にいたこと、または過去の訪問の場所 |
| データの取得、全域のみ | GitHub | 取得の時刻、IP アドレス、アプリの版、日本全体を取得したこと | アプリを使っていること、日本の地図を使うこと |
| データの取得、区画 | GitHub | 加えて、選んだ区画の集合 | これから行く地域、または関心のある地域。過去でなく未来の行動を示しうる。区画の組み合わせ（隣り合う 2 区画なら境界の近く）、追加と削除の履歴、再取得から、枠の位置を区画より細かく絞りうる |
| 自動更新 | GitHub | 同じ区画の再取得と時刻 | 区画への関心が続いていること。IP アドレスを通じて期間をまたいで結び付く |
| 出典のリンク | ブラウザで開く先 | 出典の URL。MapLibre の既定の画面では、URL によりカメラの位置 | アプリの出典の画面に置き換え、座標を付けない（[4.8 節](#48-呼び出し元の対応)） |
| 同期 | 同期サーバの運用者 | [`privacy.md`](../privacy.md) の表のとおり | 変わらない |

### 7.2 通信路の観察者

- 回線の事業者や Wi-Fi の運用者は、TLS の SNI と接続先の IP アドレスから、どの配信元に接続したかを知りうる（地理院タイルを使っている、Overpass に問い合わせた、など）。
- 地域データのパックは区画ごとに大きさが異なる。転送量から区画を推測されうる。詰め物（padding）で大きさを揃える対策は、容量の増加に見合わないので採らない。この残余は本書と `privacy.md` に記す。

### 7.3 精度の限界

- 精度は送る値の粒度であり、位置を隠す範囲の保証ではない（[3.2 節](#32-精度の意味)）。
- 固定の格子に丸めても、格子の境界を越えた時刻は伝わる。自動の送信を繰り返すと、区画の単位の移動の経路が伝わり、道路などの補助の情報と合わせて絞られうる。
- MapLibre は表示範囲の周囲や低いズームのタイルを先に読むことがあり、送る範囲は画面の範囲よりやや広い。
- 送信先を Never にしても、それ以前に送った情報は取り消せない。Geocoder は、変更の時点で OS に渡していた 1 件を取り消せない。MapLibre の端末内のキャッシュは、送信を伴わないので消さない。

### 7.4 この設定で守らないもの

- OS の測位サービス（Google 位置情報の精度）が送る情報。
- 利用者が他のアプリに渡したもの（`geo:`、共有）。
- 同期サーバの運用者に見えるメタデータ（別の文書で扱う）。
- 配信元の運営者が、IP アドレスを他の情報と結び付けること。
- 旧版のアプリに戻した場合の、[3.6 節](#36-旧版との互換) の反例の送信。

## 8. 試験の計画

### 8.1 core の単体試験（JVM）

- `Policy` の読み込み：重複したキー、送信先の重複、余分な項目（除いた後に正準形と一致すること）、未知の版、選べない組、欠けた送信先。破損と未知の版は復旧値になり、保存し直さないこと。利用者の変更で初めて上書きすること。
- 新規の導入の既定と復旧値が異なること。復旧値では、どの送信先も自動では送らないこと（`data` の自動の取得と自動更新も含む）。
- 移行：`blockExternalLocation` が true、false、値なし、型違いの 4 通りと、`onlineVenues` の有無の組み合わせ。`mapConsents` の引き継ぎ。
- 旧版向けの派生値：`blockExternalLocation` は旧設定のオフと一致する場合だけ false。`mapConsents` には精度「制限なし」の同意だけが入ること。
- 同値性：旧設定の 2 通りから作った `Policy` について、新しい判定が今の判定と一致すること。対象は判定の関数（地図の種類、同意、画面の表示、オフライン地図の有無の全組み合わせ）、静止画の待ち行列の待機中のジョブ、再試行を待つ取得、再起動の後に読み戻した同意、画面の外に出た地図、停止した作業である。
- 許し：規則の変更、精度だけの変更、一時停止の開始と解除で無効になること。他の送信先の変更で無効にならないこと。起動の識別子が異なる許しは、世代が一致しても通らないこと。
- 世代の保存：変更のたびに新しい乱数になり、規則と一度に書かれること。`externalGens` を読めない場合に新しい乱数になり、保存した作業の世代と一致しないこと。
- 保存した作業：予約の後に規則を変えた作業、世代の保存と作業の取り消しの間で止めた作業が、実行時に許しを得られず送らないこと。
- `Outbound`：送信の直前、再試行（`firstSuccess`、`ResumableDownload`）、リダイレクト（許可されていないホスト、途中で無効になった許し）のそれぞれで拒むこと。規則の変更で実行中の接続を切ること（偽の HTTP で確かめる）。
- MapLibre の interceptor（照合の部分を core に置く）：印のない要求、表にないトークンを拒む。トークンの送信先と URL の型が一致しない要求を拒む（同じホストのカスタムを含む）。持ち手が今の起動の許しを持たない、または組が一致しない要求を拒む。操作時のみの持ち手の画面が許可を返した後の要求を拒む。精度の上限を超える z を拒む。送る URL に印が残らない。
- `Precision.snap`：格子の中心を返す。負の座標、180° 経線、極付近。同じ区画の点は同じ値になる。
- Overpass の問い合わせ：地区では区画の bbox だけを含み、元の座標を含まない（問い合わせ文字列に元の座標の桁が現れないことを確かめる）。
- `TileStyle.capped`：すべてのソースの `maxzoom` が上限以下になり、すべての遠隔の URL に持ち手のトークンが付く。持ち手ごとに別のファイルになる。
- 地域データ：区画の計算（ズーム 8、境界、180° 経線）、枠と交わる区画、カタログの解析と検証、PMTiles のヘッダの範囲の検証、参照数の算出、書き込みの順序の各段で止めた後の起動時の照合、束のないパックが「取得済み」にならず消されもしないこと（「使用不可」になり、束を置くと戻ること）、`state.json` を読めない場合の復元、使用中のファイルを消さないこと、スタイルの束の保持、取得の順序が区画の識別子の順であること、Range での再開と sha256 の不一致（今の偽の `RangeHttp` を使う）。
- 容量の予算：受付の式、書いた分を未消化の予約から引くこと（偽の `F` で、書き込みと空きの減少を同時に進め、二重に数えないこと）、記録の書き込みで `F − Σ O_j` が `L` を割った時点で全処理が止まること、記録の予備の算出（測定値と既定値）、段階の境目の予約し直し、予約の返却。
- 合成したスタイル：`OfflineBasemapStyle.remoteUrls` が空であること。

### 8.2 形式検証

- `formal/tla/SendGate.tla`（[4.9 節](#49-形式検証)）を CI のパスに加える。
- モデルに再起動を加える。再起動はメモリの許しを消し、起動の識別子を替え、保存した世代と作業を残す。
- 変異として、世代を全体で一つに戻した版で「取り消しすぎない」性質が破れ、再試行やリダイレクトで許しを確かめない版、一時停止で世代を進めない版、世代を起動ごとに 0 から数え直す版で「有効な許しでだけ送る」性質が破れることを確かめる。

### 8.3 試作で確かめること

製品の実装の前に、試作で次を確かめる。

- **印が最終の要求まで届くこと**：資源の種類ごとに、MapLibre が実際に出す要求の URL に印が残ることを interceptor で記録する。種類は、スタイル、TileJSON、ベクタタイル、ラスタタイル、スプライト（MapLibre が `@2x`、`.json`、`.png` を付けて展開する URL）、フォント（`{fontstack}` と `{range}` を展開する URL）、そのほか MapLibre がテンプレートから作るすべての URL である。
- **古い要求が拒まれること**：規則の変更、一時停止、画面の外への移動、再起動の後に、MapLibre が予約していた要求が interceptor で拒まれること。
- **キャッシュ**：トークンを含む URL で MapLibre の端末内のキャッシュが効くこと。規則を変えない限り、再起動の後もキャッシュから描けること。
- 印が届かない種類は、[4.4 節](#44-outbound) の別の経路（`Outbound` で取得して `file://` で参照）に移し、その経路で描けることを確かめる。
- 区画ごとのパックの大きさ、パックの数と描画の時間、記録の書き込み速度（`L` の算出の元）を測る。

### 8.4 端末での試験

製品に組み込む前に必須とする。

- 通信の記録：デバッグ版で、`Outbound`、Geocoder の呼び出し、MapLibre の interceptor が扱うすべての要求の送信先、ホスト、パス、時刻を記録する。合わせて端末の外の HTTPS の中継で記録し、interceptor を通らない通信がないこと（MapLibre 自体の通信を含む）を確かめる。
- 次の筋書きごとに、記録が規則と一致することを確かめる。
  - 新規の導入：GitHub（オフライン地図、施設データ）以外へ送らない。
  - 旧設定 true と false からの更新：更新の前後で送信先と要求が変わらない。
  - 設定の破損：どこへも自動では送らない。
  - 地図だけ自動：静止画とサムネイルが送り、Geocoder へは送らない。サムネイルは Auto の候補の配信元にだけ送る。
  - Geocoder だけ地域：問い合わせの座標が 0.1° の格子の中心である。
  - 地図を地区：ズーム 16 以上でもズーム 15 を超える要求がない。
  - 規則の変更：待機中の静止画を捨て、実行中のものを中止し、変更の後に古い許しで送らない。
  - 詳細画面で時機と精度を順に変える：「適用」までは何も送らず、適用の後は新しい精度でだけ送る。
  - 一時停止：開始の時点で接続が切れ、データの取得の再試行が取り消される。解除の後に停止の前の要求が送られない。
  - リダイレクト：データの取得のリダイレクトが許可されたホストにだけ従う。
  - 再起動：同意と規則が保たれる。再起動の前に予約した WorkManager の作業は、実行時に許しを得直してから送る。規則を変えた直後（作業の取り消しの前）に強制終了した場合、再起動の後にその作業が送らない。再起動の前に MapLibre が予約していた要求が送られない。
  - Overpass の一部のホストをオフ：そのホストへ送らない。
  - 出典の画面：座標を付けたリンクを開かない。
- 地域データ：機内モードで、取得した区画の内側をズーム 14 まで描き（それより拡大した表示はズーム 14 のタイルを引き伸ばし、施設の層を重ねる）、区画の外ではオフライン地図に戻る。境界の見た目、文字の重なり、日本の外の文字、パックの数を増やしたときの描画の時間。
- 記録との独立：記録モード「最高精度」で記録しながら大きなパックとバックアップを同時に要求し、記録の欠落がなく、予算が書き込みを直列にし、`F − Σ O_j` が `L` を割る前に大きな処理が止まることを確かめる。空きの少ない端末の模擬（大きなファイルで空きを埋める）でも確かめる。
- 取得の中断：通信の切断、アプリの強制終了、端末の再起動を書き込みの順序の各段で起こし、起動時の照合で一貫した状態に戻ることを確かめる。

- TalkBack で、各行の状態（許可、送信しない）と時機が読み上げられること。

### 10.1 送信の経路と許し

| 経路 | 許しを得る時点 | 確かめる時点 |
| --- | --- | --- |
| 対話的な地図（`TrackMap`、持ち手は地図の面） | スタイルを読み込む直前。自動なら `permit(送信先, Auto)`、操作時のみなら画面にある間の許可（`grant`） | interceptor で要求ごと、リダイレクトの各段（OkHttp の network interceptor） |
| 静止画（`DayMap`、`DeviceScreen`、持ち手 `snapshot`） | 待ち行列のジョブの開始の直前 | 同上 |
| 地図の種類のサムネイル（持ち手 `thumb:<送信先>`） | 候補ごとに描画の直前 | 同上 |
| OpenFreeMap のスタイルと TileJSON | その地図の許しで、`Outbound` から取得 | `Outbound` の接続の前、リダイレクトの各段、応答の後、本文の読み込みのたび |
| Geocoder（`Geocoding.platformAddress`） | 専用の 1 本のスレッドで、呼ぶ直前 | 戻った時点。無効なら答えを捨てる |
| Overpass（`VenueSearch`） | 「オンラインで検索」を押した時点 | 各インスタンスの前（`firstSuccess`）と `Outbound` の各時点 |
| オフライン地図、施設データ（`PinnedWorker`） | 予約の時点の `mode` と世代を WorkManager の入力に保存し、実行のたびに `permitFor` | `Outbound` の各時点（`ResumableDownload` の再要求、同期サーバの `/v1/info` を含む） |

規則の変更と一時停止は、`Outbound` の接続（その送信先）を切り、MapLibre の要求のうちその送信先の印を持つものを取り消し（OkHttp の `Dispatcher`）、データの取得の予約を取り消す。

**変更の保証**：規則の変更と一時停止（`changeRule`、`changePaused`）は、変更した送信先（停止ではすべて）について、送信中の接続と要求を中止し、その結果を返す。

- `Done`：中止したものはすべて終わった。これ以降、それらは 1 バイトも送らない。変更の前に書き終えたバイトは送られている場合がある。
- `Stopping(n)`：共通の期限（`SendGate.RevokeWaitMs`、3 秒。`Outbound` と MapLibre の両方で一つの単調な時計の期限を使う）までに `n` 件が終わらなかった。中止は裏で続き（切断と `Call.cancel` を繰り返す）、すべて終わった時点で完了を知らせる。完了までは「止まった」とは言わない。画面は「停止中…」を出し、完了を待つ。
- どちらの場合も、許しは変更の時点で無効であり、中止された接続では、確認を通った後の呼び出しも始まらない（確認の直後に中止を見て失敗する）。止まらないのは、すでに OS の中で実行中の 1 回の呼び出しだけで、その呼び出しが戻ると次の呼び出しは失敗する。

仕組み：

- `Outbound` の接続は、I/O の呼び出し（接続、書き込み、応答の読み込み、見出し、本文の読み込み）のたびに、中止されていないことと許しが有効であることを確かめてから、その接続の読み取りの錠の下で呼ぶ。中止は、書き込みの錠が取れるまで（実行中の呼び出しが終わるまで）接続を切り直す。
- MapLibre の要求（非同期の呼び出し。本文の読み込みも呼び出しの中で行う）は `Call.cancel` で取り消し、Dispatcher から消えるまで取り消し直す。名前の解決で止まっている要求は、解決が戻った時点で接続せずに失敗する。
- 変更は専用のスレッドで行い（`Net.change`）、設定の画面は完了まで操作と戻る操作を受け付けない。完了の知らせは、その画面がまだ表示中の場合だけ画面を閉じる。
地図の送信先の変更では、その送信先の地図を新しい許しと印で読み込み直す（精度だけの変更でも同じ）。

### 10.3 試験

- `core` の単体試験：`MapHttpSuite`（OkHttp のクライアントをローカルのサーバと数える名前解決で動かし、拒む要求と転送では名前を引かず接続もしないこと、転送の後の段で持ち手と画面の許可を確かめ直すこと）、`ExternalPolicySuite`（読み込み、破損、未知の版、移行、旧版向けの派生値、世代、同意）、`SendGateSuite`（許しの無効化、他の送信先、一時停止、再起動、保存した作業、待ち行列）、`OutboundEquivalenceSuite`（旧設定の全組み合わせで、判定、待機中の静止画、再試行を待つ取得、再起動の後の同意、画面の外の地図、停止した作業が旧版のコード `legacy` と一致する）、`MapGuardSuite`（印のない要求、表にない印、URL の型、古い印、再起動、操作時のみの許可、ズーム、リダイレクト、スタイルの書き換え）、`PrecisionSuite`、`OutboundSuite`（ローカルの HTTP サーバで、ホスト、リダイレクト、応答中の無効化、一時停止による切断、`ResumableDownload` の再要求、確認と登録の後と接続の後に規則を変えた場合に要求が届かないこと）。
- 端末での試験：エミュレータで、`AshiOut` の記録（interceptor、`Outbound`、Geocoder の送信と拒否）を取りながら設定を変え、再起動と一時停止を行った（デバッグ版の `DebugReceiver` の `OUTBOUND`、`PAUSE` など）。確かめたこと：
  - 移行した既定（操作時のみ）では、同意した地図の面だけが OpenFreeMap に送り、画面の外に出た後は送らない。スタイルと TileJSON は `Outbound`、スプライト、フォント、タイルは印付きで interceptor を通る。
  - 地理院タイルを自動・地区にすると、表示のズーム 17、18 でもタイルはズーム 15 まで、地域ではズーム 12 までである（サムネイルも同じ）。
  - 一時停止の間は地図のどの要求も送られず、解除の後は新しい印で送る。詳細の画面で選んで「適用」せずに戻ると、規則は変わらない。
  - Geocoder は送信しない間は呼ばれず、地区では 0.01°、地域では 0.1° の格子の中心を送る。Overpass は地区で `overpass-api.de` を外すと残りの 3 ホストにだけ送り、送信しない間は送らない。データの取得は送信しない間は始まらない。
  - 壊れた設定で再起動すると、地図は送らず、「データの扱い」に読めない旨の 1 行を出す。

### 10.4 端末の外での確認

エミュレータのコンソールのパケット取得（`adb emu network capture`）で、シナリオごとに端末の外に出たものを記録し、tshark で DNS の問い合わせ、TLS の SNI、HTTP の Host、TCP の接続、宛先ごとのペイロード量（取得の前から張られた接続も含む。IPv4 と IPv6）を調べた。
各シナリオで、規則が禁じる送信先への DNS の問い合わせ、接続、ペイロードはなかった。

| シナリオ | 結果 |
| --- | --- |
| 新規導入の既定（地図の面に OpenFreeMap の同意） | OpenFreeMap だけ |
| すべて送信しない（地図、Geocoder、施設の検索、データの取得、地図の種類を操作） | アプリの送信先への通信なし |
| 一時停止 | 同上 |
| 地理院を自動・地域、ズーム 17 | 地理院だけ。記録ではタイルはズーム 12 まで |
| 操作時のみの地図が画面の外に出た後 | 地理院への通信なし（画面にある間は 348 KB） |
| スタイルのキャッシュを消して再起動 | 許可なら OpenFreeMap へ取得し、送信しないなら DNS の問い合わせもない |
| OpenFreeMap に届かない間に起動し、後で届くようにする | 取得の失敗を 4 回記録し、届くようになった直後に取得した |
| データの取得を送信しないで再起動 | GitHub への DNS の問い合わせなし |
| 取得元とカスタムの地図の要求を、許されないホストへ転送 | 転送を拒み（取得は `Outbound`、地図は interceptor）、転送先の DNS の問い合わせもない |

エミュレータは試験中に system_server が何度も再起動した。取得の前後の system_server の pid を記録し、再起動を含んだ回は取り直した。

最終の版（デバッグ版の APK と sha256 を各回に記録）で、次も確かめた。

| シナリオ | 結果 |
| --- | --- |

| コールドブートしたエミュレータで、OpenFreeMap の 2 つのスタイルとオフライン地図を表示 | 文字、アイコン、タイル、陰影を描いた。拒否は 0 件。以前に文字が出なかったのはエミュレータの状態によるもので、変更の前の版（465b8b1）も同じ条件で同じく描いた |

### 11.1 ツールと生成物

`tools/regionpacks/build.sh` は、Protomaps の日次ビルド（既定 `20261117`）から次を作る。

1. `cells.py` が `japan.geojson` と交わるズーム 8 の区画（136 個）を求める。
2. 区画ごとに、bbox を 1e-7° 内側に縮めて `pmtiles extract --minzoom=8 --maxzoom=14` を実行する（go-pmtiles 1.31.2、並列数 `JOBS`）。
3. `verify.py` が各パックのヘッダのズームと範囲、すべてのタイルが区画の内側にあることを確かめ、全パックで同じタイルが二つのパックにないことを確かめる。
4. `style.py` がスタイルの束を作る。束は、ソース名 `pack` の層（`@protomaps/basemaps` 5.7.2 の light、日本語の文字）、その層が使う 3 書体の全 256 範囲のフォント（端末が描く CJK などの範囲と、字形のない範囲は空のファイル）、スプライトを持つ。並びと時刻を固定した ZIP なので、同じ入力から同じバイト列になる。
5. `catalog.py` がカタログ（区画ごとのファイル名、大きさ、sha256、範囲、ズーム。束の大きさと sha256）を書く。

`package.sh` はカタログの大きさと sha256 を `app/src/main/assets/regions-pin.json` に書く。
`release.sh` はファイルとカタログの一致、アセット数と 2 GiB の上限を確かめ、公開のコマンドを表示する（実行はしない）。

| 6.8 記録用の目標空き容量 `L` | 測った速度、測れない間はモードの既定値 | 測った速度とモードの既定値の大きい方 × 24 時間（下限 256 MB）。既定値は省電力 2 MB/時、バランス 5 MB/時、高精度 20 MB/時、最高精度 210 MB/時。速度は、記録のデータベース、WAL、アーカイブ、あふれのファイルの大きさを 10 分ごとに記録し、6 時間以内の 1 時間以上離れた 2 点から求める。L は 24 時間分を目安とした推定値で、保証ではない（大きさの増減を測るので、整理による圧縮や WAL の再利用を含み、将来の最大の消費を上から押さえない）。記録のモードを変えると、主プロセスの次の確かめから新しい L を使う（すでに使った容量は戻らない） | 圧縮の直後は測った速度が小さく出る。安全な側に倒す。目標であり上限ではない（設計の相談、2026-11-20） |

| 6.8 SQLite の一括の書き込み | ― | 記録以外の一括の書き込みは、どちらのプロセスでも、一つのトランザクションを一括とし、その前と後に F ≥ H + M（M = 16 MiB、運用上の余裕）を確かめる（`BulkLoop`）。後で足りなければ、最後の一括の後でも、確定した一括は残し、次の一括を始めず、呼び出し元に知らせる（延期。次の整理で続ける）。行を捨てて進めることはない。一括の大きさは経験的に決める（`BatchSizer`）。64 行から始め、上限は 512 行（明示した運用値）、データベースと WAL の増加が 2 MiB 未満なら次を倍にし、4 MiB を超えたら次をすぐ比例して小さくする。一括ごとに、データベースと WAL の増加と、その後の実際の空き容量を別々に記録する。長い行、BLOB、疎らな削除、長い読み取りがあると、一括が 16 MiB を超えて消費することがあり、それを上限とは言わない。削除も WAL を書き、SQLite は空いたページを書き直して後で再利用するので、削除でファイルが一時的に大きくなる。旧形式のログは、同じ `BulkLoop` を通り、文字の量で同じ規則に従い（64 KiB から、1 MiB と 2,000 行まで。一括ごとの増加と後の空きも同じく記録する）、64 KiB を超える 1 行は取り込まず、元のファイルを `.skipped` として残し、未取り込みとして動作の記録に表示する。利用者による期間の削除は一つのトランザクション（期間とその印を一緒に書く）のまま、触れるすべての表の行と、生データの文字、送信待ちの BLOB を見積もり、F ≥ H + M + 見積もりなら始め、後で確かめる。途中の消費の上限は保証しない。整理の後、空きが WAL の大きさを H の上に持つ場合に限り、`PRAGMA wal_checkpoint` を PASSIVE、続けて TRUNCATE で行う（最善の努力） | 変えるページは事後にしか分からない。上限を主張せず、前後の確かめで次を止める（外部のレビュー 5、6 回目、設計の相談） |

| 6.8 足りない場合 | 始めず、後で再試行する | 止まってもデータは消さず、失敗とも数えず、後で続ける（延期）。取得は「空き容量が不足」として止まり（`.part` は残る）、地域データは作業の再試行で、オフライン地図と施設データは従来の再試行の規則で続ける。バックアップは「空き容量不足（記録用の予備を除いて N MB 必要）」で始めず、書き込み中なら中断し、途中の出力は消す（完成品として扱わない）。整理は、書いている途中のファイルを捨てて止まり（その区切りの行は SQLite に残る。それまでに確定した区切りは確定したまま）、「空き容量が少ないため中断（続きは次回）」を表示する | 利用者に見える状態を実際と一致させる |

| 6.8 バックアップ | 複製の見込み | 予約は、主プロセスの中で始めるかを決めるために使う（データベースの複製、ZIP、アーカイブと退避ファイルの見込み）。予約を複製を含むバックアップ全体の最大の消費とは扱わない（長い読み取りは WAL の再利用を妨げる）。書いた量は予約に報告するが（他の処理の判断のため）、続けるかは F ≥ L + 他の予約の残り + 1 MiB だけで決め、自分の見積もりを使い切っても止めない。ZIP の出力は 1 MiB 以下の区切りごとに確かめる。データベースの複製（`VACUUM INTO`）は分けられない。別のスレッドが 200 ms ごとに大きさを予約に報告し、実際の空き容量が L と他の予約の上に 1 MiB 未満になると中断を要求する（中断できる問い合わせ）。200 ms は要求の周期で、止まるまでの時間や超過の上限ではない。中断しても読み取りの接続は必ず閉じ、不完全な複製と ZIP は完成品として扱わない（画面とデバッグの書き出しは途中の出力を消す） | 見積もりは開始の判断にだけ使う（設計の相談） |

11.2 節の保証は次の文を正とする。

> 記録済みデータの整理では、新しい保存先の内容と永続化を確認するまで元データを削除しない。容量不足で処理を中断した場合も、元データまたは確定したコピーを保持する。
>
> 地図・施設・地域データの取得と展開は、記録用の目標空き容量 L を残すよう、最大 1 MiB の出力ごとに空き容量を確認する。L は 24 時間分を目安とした推定値であり、記録継続時間を保証するものではない。
>
> 整理などの共通処理は固定の停止目安 H を使う。SQLite の処理とデータベースの複製は、事前確認・監視・事後確認で消費を抑えるが、一回の消費量の上限は保証しない。

第 2 段階で、記録が容量不足になったときの経路（緊急の予備 R と、SQLite が満杯のときのあふれのファイルへの退避）を加えた。詳細は [`recording.md`](../recording.md) の「記録の容量不足」にある。次の点は案 C の文書に定めがなく、実装と 76 回目のレビューで決めた。

- R を最初に作る条件は、R + E + 16 MiB（約 112 MiB、運用値）とし、割り当ての途中も空きを確かめる。緊急状態から戻る条件は F ≥ H + 2R の 60 秒のままである。
- 「記録中」は、記録サービスが動いている、直前の 1 分にバッチが来た、または書き込みを待つ・書いているバッチがある、のいずれかとした。記録の設定がオンでもサービスが動いていない場合に、来ないバッチを待って戻れなくなることを避ける。
- 緊急状態は、R とは別の印のファイル（`files/emergency-state`）で端末に残す。印は R の解放より前に書き、R を置き直した後に消す。R の切り詰めも削除も失敗した場合、印を書いた後でプロセスが終わった場合も、再起動で緊急状態に戻る。
- 整理のプロセスへの停止の要求は、JobScheduler からのジョブの取り消しと、区切りごとに見る印と R の長さの二つで伝える。
- 失われた行数は、累計の目標値として書く。書けなかった場合は同じ目標値を書き直し、rename の後の失敗で二重に数えない。
- 文の `SQLITE_FULL` はロールバックの前に緊急状態に入る。COMMIT の失敗は `endTransaction` が返した後になる（`recording.md`）。

今後の課題として、次を残す。

- 空きが少なく R がない間の救出。今は、R がなければバックアップ、救出用のバックアップ、隔離したファイルの書き出しを延期する（第 3、4 節のとおり）。救出用のバックアップもローカルにデータベースの複製を作る。R を要しない救出の経路として、内部に複製を作らず、容量を共有しないと確かめた保存先へ直接書き出すものを、仕様の変更として設ける。
- 結果が確定しない COMMIT。ENOSPC 以外の I/O 障害で COMMIT が失敗と返しても確定している場合、そのバッチは退避もされ、取り込みで二重になりうる。対処するなら、受け取った時のバッチの番号を SQLite の記録と同じトランザクションで保存し、再試行と取り込みで照合する。
- メモリで待つバッチは、プロセスの強制終了で失われ、失われた行としても数えられない。保存を断念した行が 0 でも欠落がないとは限らない。

### 11.3 試験

`core` の単体試験（`RegionPacksSuite` 34 件、`StorageBudgetSuite` 6 件）：

- 区画：点の区画、範囲、x、y の順、範囲と交わる区画（境界の扱い、180° 経線）。
- カタログと固定値：正しいカタログを読み、ファイル名、大きさ、sha256、スタイル版、区画の重複、重複したキーを拒む。固定値と 1 バイト違うカタログを拒む。
- PMTiles のヘッダ：ズームと、範囲が区画の内側にあること。
- 状態：書いて読み戻せる。重複したキーと不正なパスは読めない。地域の間でパックを共有し、削除はその地域だけのパックを除く。更新は古い版のパックだけを予定し、「新しい版」の印はそれまで出る。見積もりは端末にあるパック、予定のパック、束を除き、カタログにない区画を分ける。
- 取得の手順（偽の `RangeHttp`）：束がパックより先、パックは区画の順。途中で止めると Range で続きから取得する。1 バイト違うパックは sha256 で見つけ、パックを失敗とし、置かず、再試行しない。sha256 が合ってもヘッダが区画の外なら置かない。予算に収まらないパックは始めず、書いている間に空きが予備を割ると止まり、`.part` が残る。束だけがないパックは、束だけを取得する。
- 予算：書いた分を未消化の予約から引く（二重に数えない）、同時に一つ、記録の予備と測った速度。
- 起動時の照合：改名の後で状態を書く前に止まったパックを「取得済み」に直す。束のないパックは消さずに「使用不可」とし、束を置くと戻る。古い版、参照のない区画と束、迷子の `.part`、展開の途中は削除の候補とする。ファイルのないパックはカタログから予定し直す。読めない状態はファイルから作り直し、何も消さない。
- 使用中：登録したディレクトリは解除まで消さない。
- 合成したスタイル：層の順（オフライン地図の図形、パックの図形、オフライン地図の文字、パックの文字）、ソースの範囲とズーム、束のフォント、遠隔の URL がないこと。
- 外部のレビュー（2026-11-19）の指摘による試験：同時の予約と、全処理が予備で止まること。展開が予算で止まり、何も残さないこと。状態の書き込みの失敗（ENOSPC）で状態が変わらず、何も投げないこと。ファイルを読めない場合に地域データが止まること。起動時の書き込みの失敗で何も消さないこと。描画中に削除して追加し直したパックが残り、取得し直さないこと。`state.json` がない場合の復元と初回の区別。カタログの版が変わった後の続きの取得が予定した版のリリースから取ること。更新中、更新の中断、更新の失敗の状態。表示の範囲によるパックの選択。
- 2 回目のレビューによる試験：切り詰めで空いた容量を他の処理が予約した後の取り直しが止まること。Range を無視する取得元からの取り直しが、ほかの書き込みで空きが減った時に、書く前に止まること。一覧の失敗で何も変えず消さないこと。読み込みの途中の読み手と変更が、読み込みの終わりを待ち、id がその状態から決まること。待ちきれない読み手に「読み込み中」を返し、変更を断ること。
- 4 回目のレビューによる試験：1 MiB を超える一度の書き込みが区切られ、各区切りの前に確かめること。L のファイルが壊れていれば最も安全側の L になること（下限にはならない）。二つの書き込みが競っても（偽の空き容量）、L を割るのは 2 MiB 以内であること。旧形式のログの一括が 1 MiB と 5,000 行以内であること。1 MiB を超える行グループの写しが区切られ、確かめられること。主プロセスの予約の返却が止まらないこと。主スレッドでの保存領域の読み書きは、デバッグ版が動作ログに残す（`IoCheck`）。地域データの画面を一通り操作して 0 件だった。
- 5 回目のレビューによる試験：床のファイルが時刻と一緒に書かれて読めること。30 分より古いもの、未来の時刻のもの、形の違うもの（以前の版の 1 つの数を含む）が最も安全側の L になること（古いものの扱いは 6 回目で変えた）。書けないディレクトリでは書き込みが例外を投げ、前のファイルが変わらないこと。予約の受け付けが渡す前に公開され、返却の後にも公開されること、公開に失敗した予約は受け付けないこと。SQLite の一括が、測った増え方に従っておよそ 1 MiB に収まること（生データの削除の 1 行 1.7 KiB で 20 万行、幅の広い行、WAL の再利用）。旧形式のログの一括が、一括ごとに聞いた文字の量に従うこと。1 行の大きさを文字数でなく UTF-8 のバイト数で量ること。
- 6 回目のレビューによる試験：床のファイルが L、予約、時刻の三つで書かれて読めること、以前の版の形を含む壊れたものを読めないとすること。整理のプロセスの床が、主プロセスが生きていれば古くても最後の床（5.04 GB を超えても下げない）、終わっていれば L だけ、どちらも自分の L 以上、読めなければ 5.04 GB になること。生存の錠を持つ間は生きている、離せば終わったと分かること。床を書けないディレクトリで、本物の `FloorPublisher` と `StorageBudget` をつないだ予約が断られ、ファイルが消えること、モードの変更はファイルを消したまま保存されること。4 つのスレッドが予約と返却を繰り返す間に最高精度へ変えると、新しい L の床を書いた後に古い L の床が書かれないこと（錠を外すとこの試験は落ちる）。SQLite の一括の行数の上限、増え方による倍と縮小、WAL の再利用で上限を超えないこと、1 行 6.3 KiB の分散した削除が 16 MiB を超えないこと。切り詰めで残りが増えた予約は公開できなければ止まること。（床のファイルと生存の錠は設計の相談の後に除いた）
- 設計の相談（案 C、第 1 段階）による試験：出力の確かめが、圧縮とバッファを上に重ねても、すべての出力を C 以下にし、各出力の直前に確かめること（ZIP の終端を書く close を含む）。モデルの上で、1、2、4 の書き手が L を割るのは書き手の数 × C 以内であること。SQLite の一括で、40 MiB の行や 6 MiB の BLOB を含む表を長い読み取りの下で消すと、一括が 16 MiB を超えて消費することがあり（許す）、後の確かめで足りなければ次の一括を始めず、行を捨てず、余裕ができた次の実行が続きから終えること。H + M 未満では最初の一括を始めないこと。`BatchSizer` が 64 行から始め、512 行を超えず、4 MiB を超えた次をすぐ小さくし、1 行より小さくしないこと。整理の確定の各段階で容量不足（`NoRoom`）で止め、次の実行もその段階で止め、三回目で終える場合に、三つの表のすべての入力行（行ごとに一意の値）がファイル、SQLite、隔離のどこかに残り、ファイルと SQLite の両方には残らないこと（あふれのファイルはこのモデルの外）。
- 案 C の第 2 段階（緊急の予備と退避）の試験：R を全長割り当て、fsync してから置き、それまで大きな処理を許さないこと。R + E + 16 MiB 未満では作らず、記録は SQLite に書くこと、作成中に E と 4 MiB を割れば緊急状態に入らずに取り消すこと。書き込みの直前の F < E、`SQLITE_FULL`、退避の容量不足、ほかの処理の報告のどれでも、大きな処理へ一度だけ停止を求め、R を 0 に切り詰め、解放した量を示し、以後のバッチを退避に回すこと。切り詰めが失敗すればファイルを消して空のファイルを印に置くこと、消すこともできなければその旨を示し、それでも緊急状態に入ること。R を作っていない時の容量不足も空のファイルを印にすること。再起動だけでは緊急状態を抜けず、全長の R は「予備あり」、残った割り当て中のファイルは消すこと。空きが一瞬増えただけでは戻らず、60 秒続いた後に一つのバッチだけを SQLite に試し、それが保存されてから R を割り当て直して戻ること（記録していなければバッチを求めない）。試したバッチが `SQLITE_FULL` なら時計をやり直すこと。割り当て直しの失敗、割り当ての途中の新たな容量不足、fsync と置く間の容量不足、割り当て中の F < E で、古い割り当てが置かれないこと。作成・置く・解放の各段階でプロセスが終わった後、ファイルから状態を正しく決めること。SQLite が満杯になる 200 のバッチ（一意の番号）が、SQLite か退避のどちらかに一度だけあり、復帰の後の取り込みで新しいバッチが先に入ること。何も保存できない場合は各バッチを一度だけ失われたと数えること。待ちが上限の時の退避が容量不足なら緊急状態に入り、もう一度だけ書くこと。退避ファイルの書き込み（`OverflowFiles.Batch`）で、ディレクトリの fsync の失敗の後の再試行が二つ目のファイルを作らず、中身も書き直さないこと、書き込みの失敗の `.tmp` を残し、再試行が別の名前の `.tmp` から一度だけ完成させること、fsync した `.tmp` の rename の失敗では、再試行が同じ `.tmp` を rename し、中身を書き直さず、その `.tmp` を消さないこと、バックアップが再試行の `.tmp` を完成したファイルとして扱えること、30 のバッチの書き込み・fsync・rename の後でプロセスが終わると、rename の前に終わったものは `.tmp` のまま取り込まれず、完成したものはちょうど一度取り込まれること。
- 76 回目のレビューによる試験：戻る判断の直後に緊急状態に入り直すと、その許可で割り当てても戻らず、もう一度 60 秒と一つのバッチを待つこと。印を R の解放より前に書くこと。切り詰めと削除がともに失敗しても、印から再起動で緊急状態に戻り、全長の R を解放し直すこと。印を書けなかった場合は R が返した空きで書き直し、切り詰めた R からも戻ること。印を書いた後、切り詰めの前後、削除の後、割り当て直しの各段階、印を消す前でプロセスが終わっても、再起動で緊急状態のままであること。印を消せなければ後で消すこと。取り込みが、1 ファイルごとに書き込みのキューの後ろへ回り、待つバッチを先に書くこと、待つバッチがあれば最初のファイルも取り込まないこと（生データと小さい行の区別なく）、古いものから取り込むこと、記録を止めていても 250 ファイル（以前の上限 20 と 50 を超える）を取り込み終えること、失敗したファイルを飛ばし、30 秒から倍になる間隔で取り込み直すこと、バックアップの間は 5 秒後に取り込み直すこと、緊急状態で止まること。失われた行数が、rename の後の失敗で同じ累計を書き直し（110 の後に 5 を加えて 115、125 にならない）、rename の前の失敗では未記録として示し、後で一度だけ書くこと。
- 主スレッドの確かめ（`IoCheck`）が見る範囲：目印を置いた箇所（地域データ、空き容量、オフライン地図と施設データの取得済みの版）と、デバッグ版で有効にした StrictMode（主スレッドでのプラットフォームを通したファイルとデータベースの読み書きをすべて。どのコードかを問わない）。ネイティブのコード（MapLibre）の読み書きはどちらも見ない。

このエミュレータでは、前面のアクティビティのプロセスが終わると、system_server がタスクのスナップショットで止まることがあった（gfxstream の `hasReadColorBufferDma` の表明）。プロセスを終わらせる試験は、アクティビティを開かずにブロードキャストでプロセスを起こして行った。アクティビティも記録サービスもないプロセスは、Android がキャッシュのプロセスとして凍結するので、確かめの間は止まり、次のブロードキャストで続いた（記録中は前面サービスがあり、凍結されない）。模擬の空き（`STORAGE_FREE`）で緊急状態に入った回は、空きが変わらないので解放した量を「+0.0 MiB」と示した。

### 11.5 公開の手順

公開には所有者の承認が要る。次の手順で行う。

1. パックを作る（承認の時点でビルド `20261117` が残っていれば、11.1 節と同じバイト列になる）。

   ```sh
   BUILD=20261117 JOBS=6 tools/regionpacks/build.sh "$WORK" tools/regionpacks/dist

   作業用のディレクトリは `"$WORK"/build-<BUILD>` に分かれるので、別の日付のビルドのデータが混ざらない。`dist` は版ごとに空のディレクトリを使う。
   ```

2. カタログを APK に固定する。`app/src/main/assets/regions-pin.json` ができる。

   ```sh
   tools/regionpacks/package.sh 20261117
   ```

3. 公開のコマンドを表示し、確かめてから実行する。リリース `regions-20261117` を、カタログと束で作り（`--latest=false`）、パックを 40 個ずつ 4 回に分けて加える。

   ```sh
   tools/regionpacks/release.sh 20261117
   ```

4. 公開したすべてのアセットを取得し、カタログと固定値に照合する。`release.sh` は、カタログが固定値と違う場合、ファイルがカタログと違う場合に失敗する。照合が通るまで、固定値を入れた APK を公開しない。

   ```sh
   gh release download regions-20261117 --repo sksat/ashidori -D /tmp/regions-published
   tools/regionpacks/release.sh 20261117 /tmp/regions-published > /dev/null
   ```

   カタログだけを確かめる場合：

   ```sh
   curl -fsSL -o /tmp/c.json https://github.com/sksat/ashidori/releases/download/regions-20261117/ashidori-regions-20261117.json
   sha256sum /tmp/c.json   # 693cbc0b…ecae57
   ```

5. `regions-pin.json` をコミットし、アプリの次の版に含めて公開する。
   公開の前のアプリは固定値を持たないので、地域データの画面を出さない。

- パックの数と描画の時間、区画の境界の見た目、記録の最高精度のモードと同時の取得を実機で測る（8.4 節）。
- 日本の外の区画と施設データのパック（未決 10）。
