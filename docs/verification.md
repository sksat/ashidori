# 検証

[概要に戻る](overview.md)

同期の設計とその実装は、コードレビューと形式検証の二つで確かめている。
形式検証の詳細、実行方法、各モデルの大きさは [`formal/README.md`](../formal/README.md) にある。

## レビュー

同期の仕様、サーバ、アプリについて、コードレビューを複数回行い、指摘を修正した。
指摘のうち並行処理や障害に関わるものは、修正前の設計を形式モデルにして反例として再現し、修正後のモデルで成り立つことを確かめた。

## 形式検証

二つのモデルは前提が異なる。
片方の結果を、もう片方の前提のもとで読まない。

| | 暗号モデル | 状態モデル |
| --- | --- | --- |
| ツール | Tamarin | TLA+ と TLC |
| サーバの扱い | 攻撃者（通信路、Worker、D1、R2 をすべて制御する） | 仕様どおりに動く。ただし status の取得では偽の一覧を出すサーバも扱う |
| 問い | 記録が漏れないか、blob を別のスロットへ移せないか | 並行処理と障害のもとで同期の状態が食い違わないか、いずれ完了するか |

### 暗号モデル（Tamarin）

`K` が漏れない限り、という条件のもとで次を示した。

| 性質 | 結果 |
| --- | --- |
| 攻撃者は `K` もバッチ鍵も得られない | 成り立つ |
| 暗号化した位置データを得られない | 成り立つ |
| 受理した blob は、同じ `K` と同じスロットで暗号化されたものである（スロットの束縛） | 成り立つ |
| あるスロット用の暗号文は、別のスロットでは受理されない | 成り立つ |
| 長さの等しい二つの候補のどちらを暗号化したかを区別できない | 成り立つ |
| 後から `K` が漏れると過去の暗号文も読める（前方秘匿性がない） | そのような実行がある |
| サーバは同じ端末 ID を 2 台に与えられる | そのような実行がある |

### 状態モデル（TLA+）

| 対象 | 確かめたこと |
| --- | --- |
| outbox と送信 | 同じスロットには常に同じ暗号文が入る。障害が止まれば全データが届く |
| アーカイブの分割送信 | 送信中にファイルが置き換わっても、版の混ざった送信をしない |
| バッチの確定と孤立オブジェクトの掃除 | 掃除が確定済みの blob を消さない |
| 登録と自己登録 | 一つのトークンに端末は高々一つで、再試行はすべて同じ端末を返す |
| 招待による登録 | 招待は利用者と最初の端末と同時にだけ使用済みになり、一つの招待からは一人だけができる。ユーザ名は一意 |
| 共有チェックインの版 | 遅れて届いた古い操作が新しい操作を取り消さない |
| フィードの再同期（アプリは未実装で、仕様の手順をモデルにした） | 表示はいずれ見えるべき集合に収束する |
| 他の端末の status の取得 | 偽の一覧行があっても、正しい status はいずれ読まれる（検査した件数の範囲で） |

## 証明していないこと

- モデルは仕様とコードを読んで手で書いたものであり、コードがモデルどおりであることは検査していない。
- AES-GCM、HKDF、SHA-256 は理想化している。nonce の衝突、実装の欠陥、サイドチャネルは対象外である。
- 端末内での `K` の扱いと、復旧コードの受け渡しの安全性は前提であり、検査していない。
- TLC は、各設定に書いた有限の大きさ（端末 2〜3 台、障害が数回）の状態だけを網羅する。
- 活性は、障害が有限回で止まることを仮定する。データを永久に返さないサーバに対しては、同期の完了を保証できない。
- 暗号モデルが守るのは内容だけであり、メタデータ（大きさ、時刻、件数）は対象外である。共有チェックインは平文なので対象外である。
