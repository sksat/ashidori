# 鉄道の路線の照合（設計案）

> 状態：**提案**。未実装である。
> 数値は、施設データと同じ Geofabrik の日本の抽出（`japan-261014`、OpenStreetMap 2026-10-14 時点）から pyosmium の試作のスクリプトで 2026-11-24 に測った。試作のスクリプトはリポジトリに含めない（段階 1 で `tools/rail/` として作る）。
> gpt-6-astra との設計の相談（データモデル、プライバシー、照合の方式）を反映した。主に、段階 1 では区間の境界を変えず照合の結果を補足として分けて持つこと、段 1 で経路の候補を複数残すこと、結果を分かったことの段で表すこと、利用者の修正をそのまま照合に渡すことである。
> 利用者の判断を待つ点を [10 章](#10-未決の事項) に挙げる。

## 1. 目的と範囲

### 1.1 課題

| 現象 | 原因 |
| --- | --- |
| 1 回の乗車が「地下鉄」「電車」と交互に分かれる | 地下で GNSS が途切れた区間を `ModeClassifier` が地下鉄（`gapRatio > 0.5`）、地上の区間を電車とする |
| 地上を走る地下鉄の路線（東西線の地上区間など）が電車になる | 種別を GNSS の欠けで決めている |
| 乗った路線と駅が分からない | 路線のデータを持たない |
| 乗換と、同じ列車の地下と地上が区別できない | 歩行の有無だけが手がかりである |

進行中の PR は、間に歩行のない隣り合う鉄道の区間（電車・地下鉄）を一つにする。
この規則は路線のデータを要しない。
本書はその上に、既知の路線との照合を加える。

### 1.2 目標

| 決めること | 照合の前 | 照合の後 |
| --- | --- | --- |
| 乗った路線 | 不明 | 路線グループ（[3.2 節](#32-路線グループ)）の列 |
| 地下鉄か電車か | GNSS の欠け | 路線の種別 |
| 乗換 | 歩行の有無 | 歩行の有無と、路線の変わる駅（段階 1 は表示だけで、区間を分けない） |
| 表示 | 「電車」 | 「つくばエクスプレス　つくば → 北千住」 |
| 地図の線 | 測位の点を結ぶ（地下は直線） | 地下の欠けを線路に沿って推定として描く（表示だけ、[6 章](#6-線路に沿った描画)） |

### 1.3 制約

| 制約 | 本書の扱い |
| --- | --- |
| 位置を送らない | 照合は端末の中だけで行う。路線データは日本全体を一つのファイルとして取得する（[3.5 節](#35-版固定配布)）。結果を書き出し、診断、同期に出さない（[5.6 節](#56-書き出し診断通信)） |
| 記録を失わない | 記録の測位を書き換えない。照合は読むときに求める派生のデータであり、基礎のタイムラインと分けて持つ（[5.1 節](#51-基礎のタイムラインと補足)、[5.5 節](#55-結果の保持)） |
| 電池と記憶域 | 日の表示を組み立てるときだけ照合する。記録のサービスは路線データを開かない |
| 日本を先に | データは日本の抽出だけから作る |
| ライセンス | ODbL 1.0。施設データと同じく Derivative Database として提供し、出典を示す |

### 1.4 対象外

- 時刻表（GTFS）による列車の特定。種別（快速など）は求めない。
- バスと船の路線。
- 日本の外。
- 記録の側の変更（測位の間隔、地下での GNSS の要求）。

## 2. 調査

### 2.1 OpenStreetMap の鉄道のモデル

| 要素 | タグ | 意味 |
| --- | --- | --- |
| 線路のウェイ | `railway=rail\|subway\|light_rail\|monorail\|tram\|narrow_gauge\|funicular` | 1 本の線路。複線は線路ごとのウェイである |
| | `tunnel=yes`、`layer`、`bridge` | トンネル、上下の順 |
| | `service=yard\|siding\|crossover\|spur` | 本線でない線路（操車場、側線、渡り線、引込線） |
| | `usage=main\|branch\|industrial\|…` | 用途 |
| | `name`、`operator` | 線路の名前（例「つくばエクスプレス」）、事業者 |
| 路線のリレーション | `type=route` `route=railway` | 線路の設備としての路線（例 東海道本線）。名前、`railway`、`usage`、事業者の同じ線路を束ねる [JA:Tag:route=railway] |
| 運行系統のリレーション | `type=route` `route=train\|subway\|light_rail\|monorail\|tram` | 列車の運行の経路（例 京浜東北線、のぞみ）。走る線路と停車駅を持つ。`name`、`ref`、`operator`、`network`、`from`、`to`、`colour` [JA:Tag:route=train] |
| 系統のまとめ | `type=route_master` | 方向ごと・種別ごとの運行系統を束ねる |
| 駅 | `railway=station\|halt`、`public_transport=station`、`station=subway` | 駅の点。事業者ごとに別の点がある |
| 駅の範囲 | `public_transport=stop_area` | 駅の点、乗降位置、ホームを束ねる |
| 出入口 | `railway=subway_entrance\|train_station_entrance` | 駅の出入口 |

日本の慣習を示す [JA:OpenRailwayMap/Tagging in Japan]。

- `operator` は、列車を運行し、線路を保有・保守する事業者とする。直通運転では、線路を保有する主な事業者を付ける。
- 線路の `name` は事業者名を含むことが多い。
- 地下鉄は標準軌が多いが、JR や私鉄と直通する路線は狭軌である。

### 2.2 日本の完全性

本線の線路を、`railway` が上の表の種別で、`service` がなく、`usage` が `industrial`、`military`、`test` でないものとした。

| 項目 | 値 |
| --- | --- |
| 本線の線路 | 97,000 ウェイ、41,709 km |
| 本線でない線路（`service` あり） | 41,783 ウェイ、8,135 km（`yard` 23,305、`siding` 12,590、`crossover` 2,731、`spur` 2,289） |
| 名前のある本線 | 長さの 99.1% |
| 運行系統に属する本線 | 83.6% |
| `route=railway` に属する本線 | 75.4% |
| どちらかに属する本線 | **98.6%** |
| どちらにも属さない本線 | 約 580 km（名前あり 0.9%、名前なし 196 km） |

駅を示す。

| 項目 | 値 |
| --- | --- |
| `railway=station\|halt` | 9,188（名前 100%、`operator` 45%、リレーションの要素 30%） |

- 線路の形と種別とトンネルは、ほぼ全域にある。
- 路線の名前は、運行系統か `route=railway` の少なくとも一方で 98.6% の線路に付く。
- 事業者名は表記が揃わない（「東京地下鉄」と「Tokyo Metro」）。名前も揃わない（「つくばエクスプレス線上り」「東京メトロ半蔵門線 : 渋谷→押上」「Train のぞみ: 東京 => 博多」の形）。表示の名前は生成のツールで整える（[3.2 節](#32-路線グループ)）。

### 2.3 直通運転、線路の共用、並行する線路

| 項目 | 値 |
| --- | --- |
| 2 つ以上の運行系統に属する本線 | 61.0% |
| 2 つ以上の事業者の運行系統に属する本線 | 17.9% |
| 名前の違う 2 つ以上の `route=railway` に属する本線 | 9.8% |
| 線路の事業者が 2 つ以上ある運行系統 | 305 / 1,638 |
| 30 m 以内に、共通の路線グループを持たない線路がある本線 | **11.6%** |
| 同じく 100 m 以内、200 m 以内 | 15.6%、18.9% |

- 直通運転は、運行系統として載っている。例：「東京地下鉄の直通運転 - 田園都市線」（`route_master`、`operator=東急電鉄;東京地下鉄`）、「東京地下鉄の直通運転 - 常磐線」、「湘南新宿ライン」「上野東京ライン」。
- 同じ線路を、路線（例 東北本線）と複数の運行系統（京浜東北線、宇都宮線など）が共有する。
- 本線の 11.6% は、別の路線グループの線路が 30 m 以内にある（山手線と京浜東北線、常磐線の快速と緩行など）。GNSS の位置だけでは区別できない。停車した駅と、乗った駅、降りた駅で区別する（[4.5 節](#45-並行する線路)）。

つくばエクスプレス（運行系統「つくばエクスプレス線上り」）は 65.7 km、トンネルは 31% である。北千住より南の 9.4 km は 86% がトンネルである。

### 2.4 すでに持つデータ

| データ | 鉄道について持つもの | 照合に使えるか |
| --- | --- | --- |
| オフライン地図（Protomaps、日本はズーム 6〜10） | ズーム 10 までは線路の線がない。駅の POI（名前）はズーム 10 にある | 使えない |
| 地域データ（ズーム 8〜14、区画ごとに任意） | `roads` 層の `kind=rail`。ズーム 11 で名前のない線、ズーム 12 から `name`、`is_tunnel`、`is_bridge`、`ref`、`network`、`service`。`kind_detail=subway` はズーム 14 だけ（`min_zoom` 15）。運行系統、路線、色、事業者はない。`transit` 層は空である [Protomaps Layers] | 使えない。タイルごとに切られ統合された線で、ウェイの同一性とリレーションを失う。取得は任意の区画だけである |
| 施設データ（AVEN） | 駅の点（`railway=station` 9,133、`tram_stop` 991、`halt`、`public_transport=station`）。名前、`name:ja`、OSM の id。路線、事業者、出入口はない（出入口は `build_index.py` が除く） | 駅の名前の照合にだけ使える。路線との関係がないので、照合には新しいデータが要る |

ズーム 14 のタイルの例として、東京の区画（`8-227-100`）の神田付近（`14/14553/6450`）を読んだ。

### 2.5 OpenStreetMap 以外の候補

国土数値情報の鉄道（N02）は、旅客鉄道と軌道の路線と駅を持つ。属性は鉄道区分、事業者種別、路線名、運営会社、駅名である。2020 年以降の版は CC BY 4.0 である。トンネルの属性はない [国土数値情報 N02]。

- 照合のデータには使わない。トンネルがなく、ODbL のデータと組み合わせると別の出典の扱いが要る。
- 評価（[7 章](#7-評価)）で、路線名の抜けを探す参照に使える。配布しない。

### 2.6 大きさ

本線の線路を Douglas–Peucker で簡略化し、座標を 1e-5° の整数の差分（zigzag の可変長整数）で書き、0.1° の格子ごとに deflate して測った。
ウェイごとに頂点、種別とトンネルの印、属するリレーションの番号、OSM の id を持つ。

| 許容の誤差 | 頂点 | 圧縮前 | 圧縮後（1,991 格子） |
| --- | --- | --- | --- |
| 2 m | 376,764 | 2.81 MB | 1.91 MB |
| **5 m** | 296,516 | 2.64 MB | **1.72 MB** |
| 10 m | 259,037 | 2.55 MB | 1.62 MB |
| 20 m | 234,413 | 2.48 MB | 1.54 MB |

| 部分 | 圧縮後 |
| --- | --- |
| 線路（5 m） | 1.72 MB |
| 路線の表（リレーション 2,106、名前、事業者、`ref`、色など） | 0.08 MB |
| 駅（12,205、名前と id） | 0.19 MB |
| 接続（分岐の節点 95,258 の番号）、索引、ヘッダ（見積もり） | 0.3〜0.5 MB |
| **計（見積もり）** | **約 2.5 MB** |

施設データ（約 18 MB）、オフライン地図（約 64 MB）より小さい。
全体を展開しても、頂点を `Int` の配列で持てば 10 MB 程度である。

## 3. データセット

### 3.1 内容

| 表 | 1 行 | 内容 |
| --- | --- | --- |
| 辺 | 分岐から分岐までの線路 | 頂点の列（5 m で簡略化）、両端の節点、長さ、種別（`rail`、`subway` など）、速度の区分、トンネルの区間（あり、なし、不明）、属する運行系統と路線グループ、元のウェイの OSM id |
| 節点 | 分岐、端 | 全体で一つの連番 |
| 接続 | 2 つの節点 | 種類：線路（OSM の共有の節点、渡り線）、同じ路線グループの線路の補完（複線のどちらを走ったか識別できないための仮説）、乗換（同じ駅の別の路線の乗降位置の間。歩かない乗換の候補） |
| 運行系統 | `route=train` などのリレーション | 方向、辺の順序、停車位置の順序。照合の根拠に使い、表示しない |
| 路線グループ | [3.2 節](#32-路線グループ) | 表示名、事業者（正規化）、`ref`、色、種別、由来（運行系統、`route=railway`、線路の名前）、元のリレーションの OSM id |
| 直通 | 路線グループの順序つきの列 | 境界の駅、方向、根拠の運行系統。乗換なしで走れる可能性を示し、乗換がなかったことの証拠にはしない |
| 駅 | 表示の駅（`stop_area`、なければ駅の点） | 名前、位置、乗降位置の一覧 |
| 乗降位置 | 駅の中の、ある路線グループの線路の上の位置 | 駅、路線グループ、辺と辺の上の距離、由来（`stop_position`、`stop_area`、距離による補完） |
| 出入口 | 出入口の点 | 位置、駅 |
| メタ | | 版、出典（抽出のファイル名、sha256、OSM の時刻）、生成のツールの版、品質の集計（3.6 節） |

選別：

- 本線の線路と、`service=crossover`（渡り線）を入れる。`yard`、`siding`、`spur` は入れない。
- 廃線、建設中、計画線（`disused`、`abandoned`、`construction`、`proposed`）は入れない。
- 2 つの節点の間で、種別、トンネル、所属が同じウェイは一つの辺につなぐ。
- 複線の線路は別の辺として残す。同じ路線グループの並行する線路の間には「補完」の接続を加え、照合がそれを使ったことを結果に残す。線路の接続と同じには扱わない（駅に渡り線があるとは限らず、自由につなぐと逆走や不自然な折り返しを生む）。
- トンネルのタグがないことを「トンネルでない」としない。`tunnel` も `layer` もない線路は「不明」とする。

### 3.2 路線グループ

表示の単位を **路線グループ** とする。
照合の根拠は運行系統（方向と停車位置の順序）であり、路線グループに潰さない。
`route_master` の子をすべて一つの集合にすると、「前半は系統 X、後半は系統 Y」という実在しない運行を合成できるためである。

| 由来 | 規則 |
| --- | --- |
| 運行系統 | `route_master` があればその子を一つにする。なければ、`ref` と事業者（または `network`）が同じで、経路の重なりか駅の列が一致する運行系統を一つにする。色は補助とし、色だけで束ねも分けもしない |
| `route=railway` | 運行系統の路線グループがない線路のためだけに、一つの路線グループとする |
| 線路の `name` | どのリレーションにも属さない線路は、`name` と `operator` で路線グループとする |
| 不明 | 上のどれもない線路。経路の探索には使い、路線名は出さない |

由来を辺ごとに持ち、運行系統による所属を、`route=railway` と線路の名前による補完より強い根拠とする。

表示名は次の順で選ぶ。

1. `route_master` の `name`。
2. 運行系統の `name` から、方向と区間（「上り」「（A → B）」「: A→B」「Train …:」）を除いたもの。
3. `route=railway` の `name`。
4. 線路の `name`。

事業者の表記（「東京地下鉄」「Tokyo Metro」「東京メトロ」）は、生成のツールが持つ対応表で揃える。
直通運転の運行系統（例「東京地下鉄の直通運転 - 田園都市線」）は表示名にせず、直通の列として持つ。

### 3.3 種別

路線グループの種別は、元のリレーションの `route` と線路の `railway` の多数（長さ）で決める。

| 種別 | 条件 | 移動手段（[5.2 節](#52-移動手段)） |
| --- | --- | --- |
| 地下鉄 | `route=subway`、または線路の多数が `railway=subway` | 地下鉄 |
| 電車 | `route=train`、`route=railway` で `railway=rail` | 電車 |
| 路面電車 | `route=tram\|light_rail`、`railway=tram\|light_rail` | 電車 |
| モノレール | `route=monorail`、`railway=monorail` | 電車 |
| 鋼索線 | `route=funicular` | 電車 |

- トンネルは種別を決めない。`railway=rail` のトンネルは 4,907 km あり、多くは山のトンネルである。トンネルは GNSS の欠けの弱い説明としてだけ使う（[4.3 節](#43-確率のモデル)）。
- `TransportMode` に値を加えない。路面電車、モノレールは路線グループの種別で表せる。値を加えると書き出しの鍵と同期の値が変わる。

速度の区分は、新幹線（`highspeed=yes`）、在来線、地下鉄、路面電車の 4 つとし、辺に持つ。

### 3.4 形式

形式は AVEN 2（[`tools/venues/build_index.py`](../../tools/venues/build_index.py)）の可変長整数と前方一致の文字列の符号化を使い、名前を **ARAIL** 版 1 とする。

格子とブロックの索引は、全体を読み込んだ場合の計測の後に決める。
約 2.5 MB を全体で展開して Pixel 8a で 100 ms 以内、ヒープで 16 MiB 以内に収まれば、索引を持たず、一度読んで照合の間だけ保持する。
収まらない場合だけ格子を使う。その場合、辺は通るすべての格子から引く（点の AVEN と違い、最初の頂点の格子に置くだけでは途中を見落とす）。

```
"ARAI" u8 version(=1) u8 flags(=0) u32be headerLength
header: uv scale(=1e5)、範囲、表ごとの件数と位置
sections（raw deflate、順に）:
  路線グループ { 表示名, 事業者, ref, 色, 種別, 由来, OSM id }*
  運行系統 { 路線グループ, 方向, uv 辺の列, uv 乗降位置の列, OSM id }*
  直通 { uv 路線グループの列, uv 境界の駅の列, 根拠の運行系統 }*
  節点 { sv dLat, sv dLon }*
  辺 { uv nodeA, uv nodeB, uv n, sv dLat[n], sv dLon[n], uv kind, uv speedClass, tunnelRuns, uv lines[], uv osmWay }*
  接続 { uv nodeA, uv nodeB, uv 種類, uv 費用 }*
  駅 { sv lat, sv lon, 名前, uv osm }*
  乗降位置 { uv 駅, uv 路線グループ, uv 辺, uv offsetM, uv 由来 }*
  出入口 { sv lat, sv lon, uv 駅 }*
```

同じ入力から同じバイト列を作る（並びを固定する）。

### 3.7 出典

- 路線データは OpenStreetMap から作る Derivative Database であり、ODbL 1.0 の下で提供する。生成の手順（`tools/rail/`）を示す。
- `tools/ATTRIBUTION` と `tools/rail/ATTRIBUTION` に施設データと同じ形で記し、アプリの「設定 > データの出典」に出す。
- 路線名や線路の線を出す地図には、OpenStreetMap の出典を地図の出典の表示に含める（地理院の地図など、OSM でない地図でも）。
- 公開する路線データの提供と、利用者の私的な記録（照合の結果）の扱いを分けて記す。照合の結果は配布しない。画面と書き出しでの扱いは、Produced Work の要件を実装の時に確かめる。
- 国土数値情報と組み合わせない（[2.5 節](#25-openstreetmap-以外の候補)）。

## 4. 照合

### 4.1 入力の単位

照合の単位は **乗車の連なり** とする。
旅程（`Trip`）の中で、歩行の区間に挟まれ、少なくとも一つの電車・地下鉄の区間を含む区間の列である。
進行中の PR が一つにする区間の列と同じである。
利用者が電車か地下鉄に直した区間も含める。

| 入力 | 使い方 |
| --- | --- |
| 連なりの測位 | 観測 |
| 停止の事象 | 間引く前の測位から、30 秒以上の停止（速度 1 m/s 未満）を事象として求める |
| GNSS の欠け | 欠けの間の経路は線路のグラフの上で探す |
| 前後の滞在、歩行の区間の端 | 乗った駅、降りた駅の候補（弱い制約） |
| 動き（`MotionWindow`） | 歩行がないこと |
| `energy_state` の GNSS の要求 | 要求中、要求なし、不明の 3 つ。終わりの不明な行を、プロセスの終了の後まで延ばさない |
| 利用者の修正（`ModeOverride` そのもの） | 照合が修正を上書きしないため（[5.2 節](#52-移動手段)） |

対象外：

- 単独の車・バスの区間（線路に沿う道路が多く、誤って電車にするのを避ける）。利用者が電車・地下鉄に直した区間は対象にする。
- `Unrecorded`（記録なし）。段階 1 では鉄道として復元しない。路線があるというだけで、記録のない間の移動を補わない。

照合は日で切る前の旅程に対して行う（`Stats.splitByDay` の前）。日をまたぐ乗車も一つとして照合する。

### 4.2 二段の照合

**段 1：線路の上の経路の候補。**
隠れ Markov モデル（HMM）で、観測の列を説明する線路のグラフの上の経路を求める [Newson & Krumm 2009]。測位の間隔が長い場合の、グラフの上の距離と時間による遷移の制約は [Lou et al. 2009] にならう。
どちらも道路の照合の研究であり、鉄道の長い地下の欠けと乗換の識別は、この用途で評価する（[7 章](#7-評価)）。

- 段 1 は一つの経路に決めず、路線グループの列の違う経路を最大 5 つ残す（k 最良）。山手線側の辺を段 1 で選び切ると、段 2 で停車した駅を見ても京浜東北線側に戻れないためである。打ち切りが起きたことを結果に残す。
- 状態：観測ごとの、近い辺の上の点。観測から `max(50 m, 3σ)` 以内で最大 8 個とし、路線グループ、方向、接続の成分の違う候補を優先する。同じ路線グループの複線の候補は一つにまとめる。
- 乗った駅、降りた駅：観測の状態と分けて持つ。前後の滞在と歩行の端から近い乗降位置を候補とし、距離は弱い費用とする（出入口があれば出入口から測る）。「不明」も候補に含める（走行中の記録の開始、大きな駅、欠けた歩行）。
- 観測：停止の事象を残したうえで、10 秒または 50 m ごとに間引く。それでも 1,000 を超える場合は時間で均等に間引く。
- 欠けを跨ぐ遷移：グラフの上の距離を時間の中で走れるかで判定する。Dijkstra は「速度の上限 × 時間」で打ち切る。探索が読み込んだ範囲の端に届いた場合は、範囲を広げるか結果を不完全とする。
- 鉄道でない説明：鉄道のグラフに乗らない「不明」の仮説（観測の誤差は同じ、経路は直線、速度は手段を問わない）を常に比べる。鉄道の候補どうしの順位だけで採らない。

**段 2：路線グループの列。**
段 1 の各候補の辺の列に、運行系統を割り当てる。
動的計画法で、各辺の運行系統の集合から一つを選び、次の費用の和を最小にする。

| 費用 | 値 |
| --- | --- |
| 辺の運行系統を外れる | 不可（所属が「不明」の辺は、どの系統でも中程度） |
| 系統を変える（直通の列の境界の駅） | 小 |
| 系統を変える（ほかの駅で、乗換の接続あり、停止の事象あり） | 中（歩かない乗換） |
| 系統を変える（駅でない所） | 不可 |
| 停止の事象がその系統の乗降位置にある | 減（加点） |
| 停止の事象が駅の外にある | 小（信号待ちを許す） |
| 乗った駅、降りた駅がその系統の駅でない | 大 |

停止を観測できなかったことを、通過とは扱わない（欠けの間の停車、短い停車）。

### 4.3 確率のモデル

| 項 | 式 | 根拠と注意 |
| --- | --- | --- |
| 観測 | 線路からの距離 d に対し `exp(−d² / 2σ²)` | Newson & Krumm の距離の正規分布。Android の `accuracy` は 68% の水平誤差の半径であり、等方の 2 次元正規分布なら `σ ≈ accuracy / 1.51` である [Android Location]。初期値をこれとし、下限 5 m で、持続するずれを実機で校正する |
| 遷移 | グラフの距離と直線の距離の差 Δ に対し `exp(−Δ / β(t))` | 同上の指数分布。β は欠けの時間 t とともに大きくし、長い欠けで環状線や迂回を強く罰しない |
| 速度 | グラフの距離 / 時間が速度の区分の上限（新幹線 90 m/s、在来線 36 m/s、地下鉄 33 m/s、路面電車 20 m/s）の 1.2 倍を超えると急に大きな費用 | 区分と距離の誤差で正解を排除しないよう、不可にしない |
| 欠けの説明 | GNSS を「要求中」の欠けの長さ g と、その間の経路のトンネルの長さの割合 τ に対し `exp(−min(c, (1 − τ) g / λ))` | 弱い補助の項。1 回の欠けで変わる量に上限 c を置く。距離の割合と地下にいた時間の割合は違い、地上でも測位できないことがある。「要求なし」「不明」の欠けとトンネル「不明」の辺は 1 |

λ、β、c、費用の値は模擬と実機で決める。

### 4.4 直通運転と線路の共用

- 直通運転（例 半蔵門線と田園都市線）は、直通の列の境界の駅で系統を変える費用を小さくする。路線グループの列は 2 つになり、境界の駅（渋谷）を持つ。
- 直通の列は乗換なしで走れる可能性であり、実際に乗換がなかった証明ではない。A–B と B–C の直通があっても、A–B–C を同じ列車で走れるとは限らないので、列にないつなぎは「歩かない乗換」の費用とする。
- 線路の共用（例 東北本線の線路を京浜東北線と宇都宮線が走る）は、辺が複数の運行系統を持つことで表す。乗った駅、降りた駅、停止の事象で選ぶ。
- 同じ路線グループの中での列車の乗り換えは、路線グループの列からは分からない。段階 1 では求めない。

### 4.5 並行する線路

本線の 11.6% は、30 m 以内に別の路線グループの線路がある。
この区間では観測の項が同じ値になる。

1. 乗った駅、降りた駅：片方の路線グループにしかない駅なら決まる。
2. 停止の事象：片方にしか乗降位置のない所で止まったなら、その路線グループである（例 常磐線の快速と各駅停車は止まる駅が違う）。時刻表を使わないので、一つの路線グループに停車の型（快速など）が複数ありうることを含める。
3. 決まらなければ「識別できない」を答えとする。誤りではなく正解の一つとして評価する（[7.2 節](#72-指標)）。

### 4.6 結果と採用の条件

結果は一つの数値でなく、何が分かったかの段で表す。
数値（スコア）は段を決めるための仮の量であり、校正の前は「正しい確率」と呼ばない。

| 分かったこと | 使ってよいこと |
| --- | --- |
| 鉄道に乗ったことだけ（「不明」の仮説より十分によい） | 移動手段の補正（電車・地下鉄の別は路線グループが決まった場合だけ） |
| 路線グループの列（複線のどちらかは不明でよい） | 路線名 |
| 加えて乗った駅、降りた駅 | 「路線名　A → B」 |
| 並行で識別できない | 鉄道であることだけ |
| 乗換と、その時刻の範囲 | 区間の分割の候補（段階 2 以降） |

採用の条件：

| 段 | 条件（初期値、校正で決め直す） |
| --- | --- |
| 鉄道 | 最良の鉄道の候補が「不明」の仮説より対数尤度で十分に大きい。経路から 3σ 以内の観測が 80% 以上 |
| 路線グループ | 加えて、路線グループの列の違う次の候補との差が十分に大きい。同じ列を説明する複線の候補はまとめて比べる。候補の数（2 つか 5 つか）を差に含める。所属が補完（`route=railway`、線路の名前）だけの区間が長ければ下げる |
| 駅 | 加えて、駅の候補の次点との差が十分に大きい。駅の近さを、端の制約と確からしさで二重に数えない |

閾値は、保留した実測の日で「採った結果の誤り率」と「採れた割合」を見て決める。
区間の誤った分割は、路線名の誤表示より重く扱う。

照合が採れない場合は、照合の前の結果（進行中の PR の統合を含む今の規則）のままとする。

### 4.7 計算量

| 項目 | 見込み |
| --- | --- |
| 1 日の乗車の連なり | 数個 |
| 1 つの連なりの観測（間引いた後） | 2 時間で約 720。上限 1,000 |
| 状態 | 観測あたり最大 8 |
| 段 1 の候補 | 最大 5 |
| 遷移 | 観測の組ごとに打ち切った Dijkstra。地下の 10 分の欠けで半径 20 km |

目標は、Pixel 8a で 1 つの連なりに 200 ms 以内、路線データを含めて 16 MiB 以内とする。頂点だけでなく、接続、所属、探索の状態を含めて測る。初回と再表示の p50 と p95、探索の打ち切りの割合を記録する。
計算は日の表示を組み立てる背景のスレッドで行う。記録のサービス、`:maintenance` の整理、「訪れた日」のデータベースの作成、書き出しでは行わない。

## 5. タイムラインへの組み込み

### 5.1 基礎のタイムラインと補足

照合の結果は、基礎のタイムライン（`Segment` の列）に書き込まず、別の **補足**（`RailNotes`）として持つ。

| | 基礎のタイムライン | 補足 |
| --- | --- | --- |
| 作るもの | `TimelineBuilder.build`（今の処理）と進行中の PR の統合 | `core:RailRefine.notes(trips, fixes, motion, energy, overrides, rail)` |
| 使うもの | 日の表示、統計、書き出し、「訪れた日」のデータベース、Web | 日の表示と地図だけ |
| 区間の境界 | 今の規則 | 変えない（段階 1） |

補足は区間（全体の開始と終了、`wholeStart`、`wholeEnd`）ごとに、照合で決めた手段、路線グループの列、駅、段（4.6 節）、使った接続の補完の有無を持つ。
`Leg.rail` を加えて基礎に混ぜる案は採らない。書き出し（`DataScreen` は `TimelineRepo.day` を JSON と GPX に渡す）と統計に照合の結果が混ざるのを防ぐためである。

### 5.2 移動手段

区間の表示の手段は、次の順で決める。

1. 利用者の修正：`ModeOverride` を区間に当てた結果（今の規則：区間と半分より多く重なる修正のうち新しいもの）。修正があれば、照合はそれを変えない。
2. 照合：段が「鉄道」以上で、路線グループが決まれば、その種別（[3.3 節](#33-種別)）による。複数の路線グループなら、最も長い時間乗ったものによる。
3. 規則：今の `ModeClassifier` と統合の結果。

完成した `Leg` だけからは修正の有無が分からない（修正が規則の推定と同じなら `applyOverride` は区間をそのまま返し、`corrected` にならない）。
このため `RailRefine` は修正そのものを受け取り、修正の当たった区間には手段を出さない。

| 値 | 持つ場所 |
| --- | --- |
| 規則による推定 | `Leg.autoMode`（今どおり） |
| 照合による推定と根拠 | 補足 |
| 利用者の修正 | `mode_overrides`（今どおり） |
| 表示の手段 | 画面が上の順で決める |

`Leg.inferred` の意味（修正の前の推定）は変えない。照合で変わった手段を `inferred` に入れると修正と区別できなくなる。

取り消しとの関係：

- 今の「取り消し」は、変更の前に表示していた手段を修正として書き戻す（`TimelineBuilder.undoMode`）。表示の手段が照合によるもの（例 地下鉄）なら、取り消しはその手段を修正として書く。
- 書き戻した手段が照合の推定と同じなら、その修正は「照合と同じ」として扱い、`corrected` の印を出さない。
- ただし、その修正は後の路線データの版で照合の推定が変わっても残る。「修正を解除して自動の推定に戻す」操作は、今の取り消しと別のものであり、段階 1 では作らない（[未決 7](#10-未決の事項)）。
- 修正が電車・地下鉄以外（バスなど）なら、路線の表示も出さない。

### 5.3 統合と分割

段階 1 は区間の境界を変えない。

| 場合 | 基礎（進行中の PR） | 段階 1 の補足 |
| --- | --- | --- |
| 地下と地上を交互に走る 1 回の乗車 | 一つ | 路線グループ 1 つ |
| 直通運転（押上 → 中央林間） | 一つ | 路線グループ 2 つ、境界の駅 渋谷 |
| 歩かない乗換（同じホーム） | 一つ | 路線グループ 2 つ、乗換の駅。区間は分けない |
| 歩く乗換 | 歩行で分かれる | それぞれの区間に路線 |

区間を分けると、修正の当たり方（半分より多く重なる）が分割と再統合で変わる。
例：20 分の区間を 8 分と 12 分に分け、利用者が 8 分の側を直した後、路線データの更新で 20 分の区間に戻ると、重なりは 40% になり修正が当たらない。
分割は段階 2 以降とし、そのときに、修正が当たった元の区間と範囲を追跡して分けた区間に引き継ぐ方式を設計する。修正の範囲を厳密な時間の区間として扱う方式に変えるなら、アプリと Web を同時に変える。

### 5.4 表示の名前

| 例 | 表示 |
| --- | --- |
| 1 つの路線、駅が分かる | つくばエクスプレス　つくば → 北千住 |
| 1 つの路線、駅が分からない | つくばエクスプレス |
| 直通運転、歩かない乗換 | 半蔵門線・田園都市線　押上 → 中央林間 |
| 鉄道であることだけ、並行で識別できない | 手段の名前だけ（「電車」） |

駅の名前は路線データの駅の `name` による。

### 5.5 結果の保持

段階 1 では、補足を保持しない。`TimelineRepo` の日のキャッシュ（メモリ）にだけ置く。

| 捨てる時 | 理由 |
| --- | --- |
| 記録の追加、整理、復元、期間の削除 | 前後の文脈に依る結果も含めて、すぐに無効にする |
| 動き、`energy_state` の変化 | 入力が変わる |
| 路線データの版の変化、照合の版の変化 | 結果が変わる |

利用者の修正は補足に含めず、表示のたびに当てる。修正の変更で照合をやり直さずに済む。

照合が日の表示を遅くする場合に限り、`no_backup/rail_match.db` に保持する。

- 鍵は、入力（測位、動き、`energy_state`、前後の文脈）の世代か正規化した入力のハッシュ、路線データの sha256、照合とパラメータの版とする。測位の数と最後の rowid だけでは足りない。
- 「訪れた日」のデータベースと同じく派生のデータであり、壊れれば消して作り直す。記録のデータベースに表を加えない。同期せず、OS のバックアップ、アプリのバックアップの ZIP、診断の ZIP に含めず、送信しない。WAL を含めて削除の時に消す。
- 記録の測位を書き換えない。

### 5.6 書き出し、診断、通信

| 経路 | 扱い |
| --- | --- |
| 書き出し（Timeline.json、GPX） | 基礎のタイムラインを読む。照合の手段、路線、駅、線路に沿った線を含めない（含めるなら別の判断として決める） |
| 診断と障害報告 | 路線名、駅、候補、時刻、経路を logcat と自動添付に入れない。数（照合した乗車の数、時間）だけを出す |
| オンライン地図 | 照合の結果から地図の範囲を自動で広げない、先読みしない。線路に沿った線を描いても、取得するタイルは今と同じ表示の範囲だけである |
| 同期 | 補足を同期しない |

### 5.7 Web ビューアとの一致

Web ビューアは `server/web/src/data/timeline.ts` で同じ基礎のタイムラインを作る。

| 案 | 内容 | 位置が伝わるか | 評価 |
| --- | --- | --- | --- |
| A. Web は照合しない | Web は基礎のタイムラインだけを出す | 伝わらない | 段階 1 で採る。アプリと Web の表示の違いを [`web-viewer.md`](../web-viewer.md) に書く |
| B. Web も路線データ全体を取得する | オフライン地図と同じく、全体を一度取得し、固定の sha256 で確かめ、Cache Storage に置く。範囲の取得はしない。照合を TypeScript に移し、`WebFixtures` で同じ結果を確かめる。照合の結果はメモリだけに置く | 通常の取得と照合では伝わらない（取得元に IP アドレス）。配信者がページを書き換えられるという Web の信頼の前提は残る | 段階 2 で採る。約 2.5 MB なので負担は小さい |
| C. アプリの照合の結果を同期する | 結果を暗号化した stream で送る | 運用者には伝わらない（暗号化） | 採らない。同期の形式を変え、派生のデータを同期することになる |

B で同じ結果を得るには、同じ路線データ、パラメータ、入力の文脈、動き、`energy_state` が要る。Web は今 `energy_state` を読まないので、B ではその読み出しも加える。古い記録で情報がない場合は、両方で同じ「不明」とする。
B の取得元は、オフライン地図と同じく同期サーバ（同じオリジン）とする。CSP の `connect-src` を広げない。

## 6. 線路に沿った描画

- 段が「路線グループ」以上の区間は、乗った駅から降りた駅まで（駅が不明なら最初と最後の観測の近い点まで）の線路を描く。
- 測位のある部分は今どおり測位を結ぶ。測位のない部分（地下の欠け）だけを線路に沿わせ、今の不確かな部分と同じく推定として薄く描く。路線が分かっても実測の点が増えたわけではない。
- 描く線は表示のたびに求め、保存しない。書き出しは今の測位の経路のままとする（5.6 節）。
- 距離（`Leg.distanceM`）は変えない。統計と書き出しに直結するためである。線路の長さは、要るなら補足に別の値として持つ。

## 7. 評価

### 7.1 模擬

`core:sim` の `TrajectorySimulator` に、路線データの線路に沿って動く手順を加える（`Step.Rail(運行系統, 乗る駅, 降りる駅)`）。
試験には、つくばと東京の周りだけを切り出した小さな路線データ（数十 KB の見込み）を `core/src/test/resources/` に置き、ODbL の出典をそこにも置く。

模擬の正解には、路線グループの列に加えて、同じ列車か、乗換の事象、乗った時刻、降りた時刻、乗換の時刻を持たせる。

同じ路線データから作り、トンネルで必ず測位が消え、駅で必ず止まる模擬だけでは、照合の前提を再現できることしか確かめられない。
前提と違う場面と、照合に渡すデータだけを壊す試験を加える。

| 場面 | 確かめること |
| --- | --- |
| TX つくば → 秋葉原 | 北千住より南のトンネルで途切れても、つくばエクスプレス、電車 |
| 半蔵門線 → 田園都市線 押上 → 中央林間（直通） | 路線グループ 2 つ、境界の駅 渋谷 |
| 東京メトロ東西線 中野 → 西船橋 | 地上の区間があっても地下鉄 |
| 山手線と京浜東北線（秋葉原 → 新橋） | 区別できる停止がある場合とない場合。ない場合は「識別できない」 |
| TX → 千代田線（北千住で歩く乗換） | 区間 2 つ、それぞれの路線 |
| 直通の関係がないのに実際は歩かない乗換、直通の関係が欠けたデータ | 直通できることと実際の乗換を混同しない |
| 同じ路線グループの中での乗り換え | 路線グループの列からは分からないことを確かめる |
| 地上の長い受信断、地下での断続的な測位 | 欠けの説明の項に引きずられない |
| 並行する線路の片側へ数分ずれ続ける測位 | 相関した多数の観測で誤って確信しない |
| 駅の外の停止、短い停車、通過 | 停止の項による誤選択 |
| 走行中の記録の開始、日をまたぐ乗車、片方の端が不明 | 駅への強制の吸着をしない。日ごとの結果が変わらない |
| リレーション、駅、接続、トンネルのタグを欠落・誤設定したデータ | データの不備を誤りに変えず、低い段の採用か棄権になる |
| 鉄道と誤って分類された道路の移動、車と誤って分類された鉄道 | 入口を含めた性能 |
| 省電力のモード（測位の間隔が長い）、`energy_state` が不明 | 欠けで確からしさを上げない |
| 記録の追加、削除、復元、路線データの削除と更新 | 古い結果を出さない。修正が消えない |
| 路線データがない | 照合の前と同じ結果 |

### 7.2 指標

| 指標 | 定義 |
| --- | --- |
| 路線名の適合率と採用率 | 出した路線名のうち正しい割合と、路線名を出した割合。時間と乗車の数の両方で |
| 乗車の完全一致率 | 路線グループの列、乗った駅、降りた駅がすべて正しい乗車の割合 |
| 駅の正解率と棄権率 | 乗った駅、降りた駅ごと |
| 乗換の適合率と再現率 | 歩かない乗換と直通の区別を含む。時刻の誤差（または推定の範囲が正解を含む割合） |
| 移動手段の正解率 | 電車と地下鉄を別に数える（`familyAccuracy` は同じに数えるので使わない） |
| 誤照合率 | 鉄道でない移動を鉄道とした時間の割合 |
| 段ごとの正解率 | スコアの帯ごとの実際の正解率（校正） |
| 改善と退行 | 照合の前の規則から、正しくなった区間の数と、正しかったものを誤りにした数 |
| 時間と記憶域 | 初回と再表示の p50、p95、ピークのヒープ、探索の打ち切りの割合 |

`Evaluation` は検出されなかった移動の時間を混同行列で `Still` に寄せる。鉄道の評価では、`Unrecorded`、照合の対象外、棄権を別に数える。

### 7.3 実機での確認

所有者の端末で行う。記録も結果もリポジトリに入れない。

1. デバッグ版の「端末診断」に、日ごとの乗車の連なりと照合の結果（段、路線グループ、駅、次の候補、打ち切り）を出す画面を加える。画面だけに出し、logcat に出さない。
2. 正解：乗った駅と降りた駅は交通系 IC カードの利用履歴で、路線と乗換は本人の記憶とその日のメモで決める。乗降の駅だけから経路を決めない。
3. 調整に使う日（同じ通勤の経路）と、評価に使う日（別の日、別の路線）を分け、評価の日で閾値を変えない。
4. 数え方：7.2 節の指標を日ごとに数え、合計だけを報告する。
5. 移動手段の修正のある区間で、照合の手段と修正の一致を数える（参考。路線と乗換の正解ではない）。
6. Pixel 8a で、乗車の最も多い日の照合の時間と記憶域を測る。

## 10. 未決の事項

1. **表示名**：運行系統の名前（山手線、京浜東北線）を優先する案とした。路線の名前（東北本線）を使う場面はあるか。
2. **直通運転の表示**：一つの区間に「半蔵門線・田園都市線」とする案とした。段階 2 で境界の駅で区間を分ける方がよいか。
3. **トンネルの多い電車の路線**：田園都市線の渋谷〜二子玉川、総武快速線の東京〜錦糸町などは、種別の規則で「電車」になる。これでよいか。
4. **路面電車、モノレール**：手段は「電車」とし、路線名で区別する案とした。これでよいか。
5. **並行して識別できない場合**：手段の名前だけを出す案とした。「山手線または京浜東北線」や事業者名だけを出すか。
6. **路線の修正**：利用者が路線を直す、または区間ごとに路線名を消す操作を作るか。作る場合は、修正の stream に路線（路線データの OSM id と表示名）を加える同期の形式の変更になる。
7. **自動の推定に戻す操作**：今の取り消しは表示していた手段を修正として書く。照合の推定に追従する「修正の解除」を別に作るか。
8. **Web ビューア**：段階 2 で路線データを同期サーバから配る案とした。GitHub Releases だけでよいか。
9. **更新の頻度**：施設データと同じ時に作り直す案とした。
10. **書き出し**：照合の結果を書き出しに含めない案とした。路線名を含めたい用途はあるか。
