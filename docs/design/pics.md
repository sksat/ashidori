# 高度化PICS の受信（設計案）

> 状態：**段階 A を実装した**。受信と形式の解釈、走査の判定（3 章）、`pics_adv` の記録と保存・アーカイブ・同期（4.1 節、4.4 節）、交差点の一覧（4.3 節のうち一覧と格子の索引）、`energy_state.ble`、画面（6 章のうちステータス、端末診断、設定）、受信だけに限る仕組み（7.1 節）である。
> 段階 B は未実装である。派生する事象と信号待ち（4.2 節、`PicsEvents`）、受信済みの交差点と `sites.json`（4.3 節）、位置の補正（5 章）、タイムラインとマップの表示、`EnergyModel` の `ble` の項（3.6 節）が残る。
> 実装での判断：待受の出口は入口と同じく（距離 − 精度）で比べる（250 m 以上）。静止中は待受も始めない（便乗だけを続ける）。電車・地下鉄・飛行機の判定は、乗り物の間の直近 5 分の測位と動きを `ModeClassifier` で分類して得る。

> 電池の消費の数値は文献と AOSP の値からの見積もりであり、Pixel 8a では測っていない。
> Fable（案の相談）と gpt-6-astra（レビュー、指摘 13 点）の意見を反映した。

## 1. 目的と範囲

高度化PICS（歩行者等支援情報通信システム）は、交差点の BLE 路側機が歩行者用信号の状態を BLE のアドバタイズで送信する仕組みである。
公式のアプリは「信GO!」である。
ashidori はこの電波を受信だけして、次の三つに使う。

| 目的 | 内容 | 段階 |
| --- | --- | --- |
| 記録 | 受信したアドバタイズを、時刻と RSSI とともに記録する | 1 |
| 信号待ちの時間 | 交差点での待ち時間をタイムラインに出す | 1 |
| 位置の補正 | 既知の交差点の受信を、位置の弱い制約として使う | 1（外れ値の除去と PDR の再固定）、2（横断歩道の学習） |

対象外とするものを示す。

- 接続、アドバタイズ、青時間延長要求（携帯電話からのアドバタイズ）。路側機への接続と書き込みも含め、実装しない（[7.1 節](#71-受信だけに限る仕組み)）。
- 横断の支援。ashidori は視覚障害者向けの案内アプリではない。信号の色は受信の記録として出すが、音や振動による横断の案内は作らない（[7.5 節](#75-安全)）。

## 2. 送信される内容

### 2.1 方式

UTMS協会の 2018 年の報告書（モデル実証）と日本信号の 2019 年の報告書（ナビアプリとの連携）から分かる方式を示す。
どちらも本文は読めたが、2019 年の報告書の別添（BLE 路側機仕様書（案）とその解説）は PDF に含まれていない。
規格の名称は「BLE 路側機―携帯電話間通信アプリケーション規格（案）」であり、公開されていない。

| 項目 | 内容 | 出典 |
| --- | --- | --- |
| 準拠 | Bluetooth 4.2、ARIB STD-T66、2400〜2483.5 MHz | 2018 5.3.4、2019 表 3.4 |
| 送信出力 | 10 mW 以下 | 2019 表 3.4 |
| 到達範囲 | 送受信部から半径約 70 m。一つの交差点に送受信部を複数置くことがある | 2018 表 3.1、3.1.1 |

| アドバタイズの型 | `ADV_NONCONN_IND`（接続できない）。2016 年度の `ADV_IND` から変えた | 2018 3.1.3 |

| 受信の前提 | 携帯電話が 1 秒に 1 回受信できること。2 回続けて受信できなければ案内を止める | 2018 5.3.4 |

### 2.2 形式（非公式）

`ble-pics-viewer`（MIT、[参考資料](#参考資料)）の解析と、デイリーポータルZ の記事の受信例による。
オフセットは、メーカー固有データ（AD type `0xFF`）の会社 ID を除いた値の先頭からの位置である。
Android の `ScanRecord.getManufacturerSpecificData(0x01CE)` も同じ範囲を返す。

| 位置 | 内容 | 確からしさ | 根拠と補足 |
| --- | --- | --- | --- |
| 会社 ID | `0x01CE` | 高 | 複数の受信例。`0x01CE` は HOUWA SYSTEM DESIGN, k.k. に割り当てられた ID であり、PICS だけの値ではない |
| 長さ | 24 バイト | 中 | 受信例は 24 バイト。flags（3 バイト）を含む 31 バイトのアドバタイズに収まる最大の長さである |
| 0–1 | 不明（受信例は `58 01`） | 不明 | 版や長さの可能性がある |
| 2 | 種別（0、1、2） | 中〜高 | |
| 3 | メッセージ ID | 中 | 意味は不明。送信ごとの番号か、種別ごとの固定値かは分からない（受信例は `FF`） |
| 4–5 | 不明（受信例は `00 00`） | 不明 | 青延長の受付の状態の可能性がある |
| 6–9 | 交差点 ID | 中 | 受信例は `00 CD 08 49`。符号なし 32 ビットの十進は 13437001 で、先頭の 13 は東京都の都道府県コードと一致する（受信は東京都新宿区）。県番号・所轄番号・通し番号の並びという仮説は 1 例しかなく、確からしさは低い |
| 種別 0：10–23 | 識別の文字列（UTF-8、NUL で埋める） | 中 | 中身（名称か符号か）は不明 |
| 種別 1：10–17 | 緯度と経度。符号付き 32 ビット、ビッグエンディアン、1e-6 度 | 中〜高 | 18–23 は不明。半径、対象方向、世代管理番号がここにある可能性がある |
| 種別 2：10–15 | 横断歩道ごとに 1 バイト、最大 6 個 | 中 | |
| 　下位 4 ビット | 状態。0 信号なし、1 赤、2 青点滅、3 青、4 対象なし | 中 | `0xF` は空き（受信例の `FF`） |
| 　上位 4 ビット | 残り時間の目盛り。0〜7 は 1〜8 段、8 以上は不明 | 低 | 秒ではない（2.1 節）。受信例の 5 と 6 は記事の「赤=[6] 青=[5]」と一致する |
| 種別 2：16–23 | 不明（受信例はすべて 0） | 不明 | |

### 2.3 公開された受信例

公開された実際の受信例は次の 1 件だけである（デイリーポータルZ、2025 年、東京都新宿区の交差点）。

| バイト | 値 | 解釈 |
| --- | --- | --- |
| 2 | `02` | 種別 2（動的情報） |
| 3 | `FF` | メッセージ ID |
| 6–9 | `00CD0849` | 交差点 ID |
| 10 | `43` | 歩行者信号 1：青、目盛り 5 |
| 11 | `51` | 歩行者信号 2：赤、目盛り 6 |
| 12–15 | `FF` × 4 | 空き |

### 2.4 不明な点

- バイト 0–1、3、4–5 と、各種別の後半の意味。
- 残り時間の目盛りの段数、向き（増えるか減るか）、時間との対応。目盛りを持たない交差点もある（記事）。
- 交差点 ID の構成と、全国で一意かどうか。
- 種別 0 の文字列の中身。
- 種別 1 の座標が交差点の中心か、送受信部の位置か。
- 一つの交差点の複数の送受信部が、同じ内容を送るか、別のアドレスか。
- 横断歩道の番号と実際の横断歩道の対応。報告書ではアプリ側のデータとして持つ（「歩行者灯器の方向等の名称」）。
- 2019 年の正式な規格での変更点。

## 3. 受信の方針と電池

### 3.1 状態

受信の状態は四つである。
判定は core の純粋な関数（`PicsScanPolicy.plan`）とし、記録サービス（`LoggerService`）が結果に従って走査を開始・停止する。

| 状態 | 走査 | 入る条件 | 出る条件 |
| --- | --- | --- | --- |
| 停止 | なし | 機能がオフ、権限がない、Bluetooth がオフ、記録が停止、速さの条件の外（下記） | ― |
| 便乗 | `SCAN_MODE_OPPORTUNISTIC` | 速さの条件の内（下記） | 速さの条件の外、静止 |
| 待受 | `SCAN_MODE_LOW_POWER` | 便乗の条件に加え、5 分以内の測位があり、既知の交差点から（距離 − 精度）が 150 m 以内 | 交差点から 250 m 以上離れた、測位が 5 分以上古い、または便乗の条件を外れた |
| 受信中 | `SCAN_MODE_BALANCED`（一括受信では `LOW_LATENCY`、3.2 節） | 待受または便乗で、条件を満たす受信（下記）があった | 20 秒間条件を満たす受信がない、60 秒間種別 2 の受信がない、速さの条件の外、静止が 5 分続いた |

- **条件を満たす受信**は、10 バイト以上で、種別が 0、1、2 のいずれかで、交差点 ID を持つ受信である。会社 ID が一致するだけの受信では受信中に入らない。
- **既知の交差点**は、APK に含める警察庁の一覧（[4.3 節](#43-交差点の一覧)）と、信頼の条件（[5.1 節](#51-使える制約)）を満たした受信済みの交差点である。受信した座標だけでは待受の範囲に加えない。一覧は網羅的ではないので、一覧にない交差点は便乗の走査で見つける。
- **判定に新しい起床を使わない。** 距離は記録サービスが測位を受け取るたびに求める（格子の索引、640 点程度）。Android の Geofence（Google Play 開発者サービス）は使わない。
- **静止。** 走査を新しく始めないが、受信中は続ける。赤信号の待ちは 3 分の静止の判定（`MotionStateEstimator`）より短いことが多く、待ちの途中で止めると待ち時間を記録できない。静止が 5 分続けば止める。
- **速さの条件。** 移動の手段ではなく速さで決める（所有者の決定）。直近の測位の速さが 14 m/s（時速 50 km）以下なら走査してよく、徒歩、自転車、交差点の付近を走る自動車を含む。電車、地下鉄、飛行機と判定された区間は、速さによらず走査しない（線路の上は信号の交差点ではない）。速さが分からない間（測位がない、判定中）は徒歩と同じに扱う。
- **望む状態と登録した状態を分ける。** `PicsScanPolicy.plan` が望む状態を返し、走査の登録を持つ部分（`PicsScanner`）が登録した状態との差を埋める。期限は単調な時計（`elapsedRealtime`）で持つ。
- **開始の回数。** Android は 30 秒に 5 回を超える走査の開始を拒否する（AOSP の既定値）。開始はどの経路（状態の変化、開き直し、再試行、端末診断の試験）でも 10 秒に 1 回までとし、待たせた変化はその後に適用する。停止はすぐに行う。
- **開始の失敗。** `onScanFailed` が `SCAN_FAILED_SCANNING_TOO_FREQUENTLY` なら 30 秒後に再試行する。ほかの失敗は 1 分から倍にして最長 30 分の間隔で再試行し、動作の記録と端末診断に示す。
- **10 分の制限。** Android は、走査が長く続いたアプリのフィルタ付きの走査を `LOW_POWER` に下げる（既定 10 分）。受信中が 8 分を超えれば走査を開き直す。開き直しで制限が解けるかは未確認であり、保証ではない（[8.3 節](#83-実機での試験)）。
- **画面。** ステータスが表示中でも走査の状態は変えない。端末診断の「受信の試験（60 秒）」だけが、距離と動きの状態を問わず `SCAN_MODE_LOW_LATENCY` で 60 秒走査する。権限、Bluetooth、記録の停止の条件は試験にも優先する。

### 3.2 フィルタと走査の設定

| 設定 | 値 | 理由 |
| --- | --- | --- |
| `ScanFilter` | `setManufacturerData(0x01CE, …)`（値の条件なし） | フィルタのある走査は画面がオフでも続き、対応する端末ではコントローラが照合する（AP を起こさない） |
| callback type | `CALLBACK_TYPE_ALL_MATCHES` | `ALL_MATCHES_AUTO_BATCH` は画面オフで `SCAN_MODE_SCREEN_OFF`（5 %）に下がり、受信中に足りない |
| report delay | 受信中かつ画面オフかつ一括受信に対応（`isOffloadedScanBatchingSupported`）なら 5 秒（Android の下限）、それ以外は 0 | AP の起床を減らす。各結果の時刻（`getTimestampNanos`）は保たれる |
| scan mode（一括受信） | `LOW_LATENCY` を要求する | 一括受信の窓は `LOW_LATENCY` なら 183/730（25 %）、それ以外は 140/1400（10 %）である。受信中に 25 % を得るため |
| scan type | 使える端末（version 36.1 以上）では `SCAN_TYPE_PASSIVE` | 既定の能動的な走査は、スキャンできるアドバタイズに scan request を送る。PICS（`ADV_NONCONN_IND`）には送らないが、受動的な走査なら何も送らない |
| legacy | `setLegacy(true)` | PICS は従来のアドバタイズである |

一括受信を止める前と走査を止める前に `flushPendingScanResults` を呼び、コントローラが持つ結果を受け取ってから止める。

AOSP（`packages/modules/Bluetooth`、Android 15 系）の走査の窓と間隔を示す。端末の設定で変わりうる。

| 要求したモード | 画面オン | 画面オフ（前面のサービス） |
| --- | --- | --- |
| `LOW_POWER` | 140 ms / 1400 ms（10 %） | `SCREEN_OFF` 512 ms / 10240 ms（5 %） |
| `BALANCED` | 183 ms / 730 ms（25 %） | `SCREEN_OFF_BALANCED` 183 ms / 730 ms（25 %） |
| `LOW_LATENCY` | 100 ms / 100 ms（100 %） | 同じ |
| 一括受信（report delay > 0） | `LOW_LATENCY` は 183/730（25 %）、それ以外は 140/1400（10 %） | 同じ |

PICS は各情報を 200 ms ごとに 3 チャネルで送る（1 秒に 10 回のアドバタイズのうち、種別 2 は 5 回）。
走査の窓は 1 チャネルずつ聞くので、受信できるアドバタイズの割合はほぼ窓の割合になる。
Siva らの測定（2019、Android）では、受信の割合は `LOW_LATENCY` で 81〜86 %、`BALANCED` で 36〜40 %、`LOW_POWER` で 0〜10 % だった。

| 状態 | 種別 2 の受信の見込み | 用途に足りるか |
| --- | --- | --- |
| 待受（画面オフ） | 10 秒に 1 回の窓で 2〜3 件 | 交差点の発見。歩行 1.3 m/s で 13 m の遅れ |
| 受信中（`BALANCED`） | 1 秒に約 2 件 | 状態の変化の時刻を 1 秒程度で捉える |
| 試験（`LOW_LATENCY`） | 1 秒に約 4 件 | 受信率と RSSI の測定 |

### 3.3 PendingIntent による走査の評価

`startScan(filters, settings, PendingIntent)`（API 26）は、Bluetooth のスタックが走査を続け、結果をブロードキャストで渡す。

| 観点 | callback（採用） | PendingIntent |
| --- | --- | --- |
| プロセスの終了後 | 走査も止まる | 走査が続き、結果でプロセスを起こす |
| 結果ごとの費用 | プロセス内の呼び出し | ブロードキャスト（IPC）。受信中の 1 秒数件では重い |
| 取り残し | 起きない | アプリが落ちても走査が残る。次の起動で `stopScan(PendingIntent)` が要る |
| 位置との結び付き | 記録サービスの測位と動きの状態をその場で使える | 記録が止まっていれば、位置のない受信になる |
| 電波の費用 | 同じ（コントローラの走査は同じ） | 同じ |

記録サービスは記録中は前面のサービスとして動くので、走査は callback で記録サービスの中に置く。
PendingIntent は、記録の外でも受信したい場合の案として残す（[決定の事項](#9-決定の事項)）。

### 3.4 権限と端末の条件

| 項目 | 扱い |
| --- | --- |
| `BLUETOOTH_SCAN` | 実行時の権限（「付近のデバイス」）。機能をオンにした時に求める。拒否されたら機能はオフのまま |
| `neverForLocation` | 付けない。付けると Android が一部のビーコンを結果から除く。位置に使うので `ACCESS_FINE_LOCATION`（既存）を前提にする |
| `BLUETOOTH_CONNECT`、`BLUETOOTH_ADVERTISE` | 宣言しない（[7.1 節](#71-受信だけに限る仕組み)） |
| `uses-feature bluetooth_le` | `required="false"` |
| Bluetooth がオフ | 走査しない。オンにするよう求めない。`ACTION_STATE_CHANGED` で再び判定する |
| 前面のサービスの種類 | 既存の `location` のまま。走査に種類の追加は要らない |
| ハードウェアのフィルタ | `isOffloadedFilteringSupported` を端末診断に示す。非対応の端末では一致しないパケットも AP で捨てるため費用が増える |

### 3.5 消費の見積もり

Pixel 8a の電池は 4492 mAh（公称）である。
走査中のコントローラの受信電流を 5〜18 mA と置く。
上限は Siva らの測定（連続の走査で 10 分に 3 mAh 以下、平均 18 mA 以下）、下限は仮定である。
Pixel 8a の `power_profile.xml` には Bluetooth の値がない（GNSS は 44.6〜46.4 mA）。
平均の電流は「窓の割合 × 受信電流 + AP の起床」で見積もる。
AP の起床の費用は分からないので、表は電波の分だけを示す。

| 状態 | 窓の割合 | 電波の平均 | 1 時間あたり（4492 mAh 比） | AP の起床 |
| --- | --- | --- | --- | --- |
| 便乗 | 0 | 0 | 0 | 一致した結果だけ |
| 待受（画面オフ） | 5 % | 0.25〜0.9 mA | 0.006〜0.02 % | 10 秒に数件 |
| 待受（画面オン） | 10 % | 0.5〜1.8 mA | 0.01〜0.04 % | 1 秒に約 1 件 |
| 受信中 | 25 % | 1.3〜4.5 mA | 0.03〜0.1 % | 1 秒に約 4 件（一括受信なら 5 秒に 1 回） |
| 試験 | 100 % | 5〜18 mA | 0.1〜0.4 % | 1 秒に約 8 件 |
| 参考：GNSS | ― | 約 45 mA | 約 1 % | ― |

1 日に待受 30 分、受信中 10 分とすると、電波の分は最大で約 1.2 mAh（0.03 %）である。
歩行中の GNSS（1 時間 1 % 程度）に比べて小さい。
AP の起床がこれを上回るかは実機で測る（3.6 節）。

### 3.6 実機での計測

- 記録の状態（`energy_state`）の末尾（`seq` の後）に列 `ble` を足す。値は `off`、`opp`、`low`、`bal`、`balb`（一括受信）、`lat` である。列を足す前の行とファイルは null（不明）のままとし、`off` に読み替えない。走査の状態が変わるたびに、測位の計画の変化とは別に区間を分ける。
- `EnergyModel` の説明変数は固定であり、列を足すだけでは推定に入らない。`low`、`bal`、`balb`、`lat` の時間を項として足し、`off` と `opp` を基準とする。`ble` が null の時間が 1 割を超える読みの間は使わない（区間で覆われない時間と同じ扱い）。項ごとの必要な時間（`needHours`）に満たない項は推定しない。
- 端末診断に、当日のモードごとの走査時間と受信件数を示す。
- 手順は [8.3 節](#83-実機での試験) にある。

## 4. データモデル

### 4.1 受信の行（`pics_adv`）

受信したアドバタイズは、流れ（送信元、種別、交差点 ID の組）ごとに、同じ内容が続く間を 1 行にまとめる（連なり）。
行は記録の表（`Archive.SignalTables`）であり、測位などと同じ規則で保存、アーカイブ、同期する。
行はまとめの要約であり、個々の受信は残さない（例外は端末診断の試験、下記）。

| 列 | 型 | 内容 |
| --- | --- | --- |
| `start` | Int64 | 連なりの最初の受信の時刻（ms、UNIX 時刻）。`ScanResult.getTimestampNanos` から換算する |
| `end` | Int64 | 最後の受信の時刻 |
| `addr` | Str | 送信元の Bluetooth アドレス |
| `iid` | Str | 交差点 ID（バイト 6–9 の 16 進、8 文字）。10 バイトに満たなければ null |
| `kind` | Int32 | 種別（バイト 2）。3 バイトに満たなければ null |
| `msg` | Int32 | 最初の受信のメッセージ ID（バイト 3）。4 バイトに満たなければ null |
| `msg_last` | Int32 | 最後の受信のメッセージ ID |
| `msg_changes` | Int32 | 連なりの中でメッセージ ID が変わった回数 |
| `n` | Int32 | 連なりの受信の件数 |
| `rssi_max` | Int32 | RSSI の最大（dBm） |
| `rssi_max_at` | Int64 | RSSI が最大になった最初の受信の時刻 |
| `rssi_min` | Int32 | RSSI の最小（dBm） |
| `data` | Str | 最初の受信のメーカー固有データの値（会社 ID を除く）の 16 進。長さを問わずそのまま |
| `scan` | Str | 受信した時の走査（`opp`、`low`、`bal`、`balb`、`lat`、デバッグ版の注入は `debug`） |

- **流れと連なり。** 流れごとに開いている連なりは一つである。内容（バイト 3 を除いた `data`）が変わると、その流れの連なりを閉じて新しい連なりを開く。赤、青、赤と変われば 3 行になる。種別 1 と種別 2 が交互に届いても、別の流れなので互いの連なりを閉じない。
- **閉じる条件。** 内容が変わった、最初の受信から 5 秒たった（静止中は 60 秒）、最後の受信から 3 秒受信がない、走査のモードが変わった、走査が止まった、地方時の 0 時をまたぐ、のいずれかである。閉じた行を書き込みに回す。
- **静止中の長さ。** 静止中も便乗の走査を続ける（所有者の決定）。信号機の近くの自宅などで受信が続くと 5 秒ごとの行は 1 日に数万になり、受け入れの上限に届きうる。静止中は連なりの最長を 60 秒に延ばす。強制終了で失いうるのは同じ内容の繰り返しだけである。アーカイブでは Parquet の辞書と連長圧縮で繰り返しを小さくする。信号機の近くに 1 日静止した場合の行数と容量が上限の内に収まることを試験で確かめる（`PicsRunSuite`）。
- **閉じた行は変えない。** 書き込みの再試行と退避ファイルは、閉じた時の行をそのまま使う。保存した行を後から延ばすことはない。全列が同じ二つの連なりは、アーカイブの重複の除去で 1 行になる。時刻、件数、RSSI がすべて同じであり、失われる情報はないものとする。
- **バイト 3。** 送信ごとに変わる番号かもしれないので、内容の比較から除き、最初と最後の値と変わった回数を残す。意味が分かれば、列の約束を変えずに読み方を決める。
- **端末診断の試験（60 秒）。** 受信を 1 件ずつ 1 行にする（`n` が 1）。形式の調査のためであり、別の上限（60 秒で 1,000 行）を持つ。
- **形式を解釈しない。** 種別や長さが想定と違うパケットも、会社 ID が一致すれば `data` に残す。解釈は読む時に行う。

受け入れの上限は、書き込みに回す前に適用する。
上限で書かなかった受信（受け入れの拒否）と、受け入れた後に保存できなかった行（保存の失敗）は、端末診断で分けて示す。
受け入れた行は、ほかの記録と同じく退避と緊急の予備の仕組みで守る。

| 上限 | 値 | 超えた場合 |
| --- | --- | --- |
| 送信元ごとの行 | 1 秒 2 行（20 行までの連続を許す） | その送信元の受信を書かない |
| 全体の行 | 1 秒 10 行、1 日 20,000 行（見積もりの約 10 倍） | 1 日の上限に達したら、その日の残りは受け入れない |
| 開いている連なり | 64 | 新しい流れを受け入れない |
| 追跡する送信元 | 最近の 256 個 | 古いものから忘れる |
| 1 分に新しく現れる送信元 | 32 | 新しい送信元を受け入れない |

- 拒否の件数は 1 分ごとに動作の記録（LifeLog）に残す。0 でない場合は、偽の送信か上限の誤りとして調べる。
- 1 日の上限の行は SQLite で約 3 MB である。偽の送信を受け続けても、記録の容量と緊急の予備（64 MiB）を使い切らない。

### 4.2 派生する事象

事象は保存しない。
タイムラインの区間と同じく、読む時に core（`PicsEvents`）が `pics_adv`、`motion`、`fixes` から求める。
求め方を変えても記録は変わらない。

| 事象 | 内容 | 求め方 |
| --- | --- | --- |
| 受信 | 交差点（4.3 節の受信済みの交差点）、開始と終了、RSSI の最大とその時刻、送信元の数 | 同じ交差点に結び付いた行を、30 秒未満の間隔でつなぐ |
| 信号の変化 | 交差点 ID、横断歩道の番号、前と後の状態、時刻の範囲 | 種別 2 の状態が変わった直前の受信と直後の受信の間。範囲の幅が分解能である |
| 信号待ち | 交差点 ID、横断歩道の番号、開始と終了、確からしさ | 下記 |

信号待ちは次をすべて満たす区間とする。

1. 交差点を受信している。
2. 歩数が止まり（`motion` の窓の `steps` が 0）、測位の速度が 0.5 m/s 未満。3 分の静止の判定は使わない。
3. 止まっている間に、ある横断歩道が赤から青（または青点滅を経ない青）に変わり、その後 10 秒以内に歩き出す。

- 開始は止まった時刻、終了は歩き出した時刻である。最長 4 分とする。
- 3 を満たさない停止（青への変化がない、歩き出しが遅い）は、確からしさを低くして残す。タイムラインには出さない。
- 歩き出した後 30 秒の移動が 10 m に満たなければ、待ちとしない（店先での立ち止まりなど）。

### 4.3 交差点の一覧

警察庁は都道府県ごとの整備交差点と全国の CSV を公開している。

| 項目 | 内容 |
| --- | --- |
| ファイル | 「全国高度化PICS整備交差点（CSV版）」令和 8 年 4 月 1 日現在、76 KB、Shift_JIS |
| 列 | 都道府県、市町村、交差点名称、よみ方、所在地、緯度、経度（後ろに空の列。京都府の 11 行は「未併用 N」の注記） |
| 行 | 638（宮城県 145、神奈川県 92、三重県 60 など） |
| 座標の桁 | 小数 6 桁 578 行、5 桁 53 行、4 桁 7 行（4 桁は約 11 m の丸め） |
| 交差点の間隔 | 最も近い交差点までの距離は最小 53 m、中央値 162 m。100 m 未満が 96 交差点 |
| 交差点 ID | **含まない** |

- **APK に含める。** 76 KB と小さく、更新は年に 1 回程度である。施設データ（約 18 MB）のように別に公開する理由がない。取得の通信が要らず、外部への送信先が増えない。地名データベースと同じく APK に置く（`app/src/main/assets/pics/sites.csv`、UTF-8）。
- 生成のツールは `tools/pics/` とする。元のファイルを取得して sha256 を記録し、文字コードを変え、列と座標の範囲（日本の範囲）を確かめ、`manifest.json`（取得元、現在日、sha256、行数）を書く。出典は `tools/ATTRIBUTION` と「設定 > データの出典」に加える（[7.3 節](#73-交差点の一覧の利用条件)）。
- **ID との対応。** 一覧に ID がないので、種別 1 の座標から 60 m 以内の一覧の交差点を探す。一つだけなら名前を対応させる。二つ以上なら対応させない（100 m 未満の組が 96 交差点ある）。
- **受信済みの交差点。** 交差点は（交差点 ID、位置）で区別する。受信を交差点に結び付けるのは、ID が一致し、同じ送信元の種別 1 の座標がその交差点の位置から 60 m 以内の場合である。同じ ID で離れた座標が届けば別の交差点とし、両方に「ID の重複」の印を付ける。座標を受信していない送信元の行は、同じ ID の交差点が一つだけで、受信中の測位がその位置から R 以内の場合に結び付ける。どちらでもなければ結び付けない（記録は残る）。
- 交差点ごとに、種別 1 の座標の中央値、種別 0 の文字列、一覧との対応、受信した日の数、信頼の条件（5.1 節）を満たしたか、矛盾の印を持つ。数は 2,000 までとし、超えれば信頼されていない交差点から古い順に忘れる。
- `files/pics/sites.json` に、受信が終わるたびに一時ファイル、fsync、rename で書く。記録のデータベースには書かない（記録の書き込みを待たせない）。`pics_adv` から作り直せるので、アーカイブと同期とバックアップに含めない。利用者が期間を削除したら、削除の完了の後に作り直す（削除した受信による交差点や信頼を残さない）。

### 4.5 容量の見積もり

測っていない。次の仮定による。

- 送信元 1 台につき 1 分あたり、種別 0 と 1 は 5 秒ごとに各 12 行、種別 2 は変化と 5 秒ごとで約 30 行、計約 54 行。
- 1 行は SQLite で約 150 B（`data` の 16 進 48 文字、アドレス 17 文字を含む）。

| 場面 | 行 | SQLite | Parquet（gzip、推定） |
| --- | --- | --- | --- |
| 交差点 1 回（受信 2 分、送信元 2 台） | 約 220 | 約 33 KB | 約 3〜6 KB |
| 1 日（交差点 10 回） | 約 2,200 | 約 330 KB | 約 30〜60 KB |
| 1 年 | 約 80 万 | ― | 約 11〜22 MB |

参考：最高精度の測位（1 Hz）は Parquet で 1 時間約 47 KB である（energy-elevation.md）。
実装の後に、合成の受信を今の writer で書いて測り、この表を置き換える。

合成の受信での測定（`PicsRunSuite`、送信元 2 台、種別 0・1・2 を各 200 ms ごと、90 秒周期の信号で目盛りが段ごとに変わる）を示す。実機の受信ではない。

| 場面 | 受信 | 行 | Parquet |
| --- | --- | --- | --- |
| 信号機の近くに 1 日静止（ほかのアプリの走査が 1 分に 10 秒、その間の受信 40 %） | 172,641 | 16,082 | 129 KB |
| 同じ場所で 1 日中受信し続ける（25 %、最悪の場合） | 648,892 | 20,000（1 日の上限） | 173 KB |

静止中の行の多くは目盛りの変化による種別 2 の行であり、1 日の上限の 8 割に当たる。受信し続ける場合は上限に達し、残りの受信は拒否として数える（ほかの記録は止まらない）。実機で目盛りの変化の頻度を確かめ、上限か内容の比較を見直す。

### 4.6 記録を失わないための扱い

- 走査の callback（Binder のスレッド）は、結果を上限のある待ち（2,000 件）に入れるだけにする。解釈と連なりのまとめは専用のスレッド（`ashidori-pics`）で行い、閉じた行を `LoggerWrites` に渡す。待ちがあふれれば受け入れの拒否として数える。
- 一括受信の結果は時刻順とは限らない。流れごとに時刻で並べてからまとめ、開いている連なりより古い結果（遅れて届いた結果）は別の連なりとして閉じる。
- PICS の処理の例外は専用のスレッドで受け止め、記録サービスを落とさない。続けて失敗すれば機能をその起動の間止め、端末診断に示す。
- 記録の停滞の通知は、渡したのに保存されない行だけを数える。受信がないこと（交差点から遠い）は停滞ではない。

失われうるものを段ごとに分ける。

| 段 | 失われうるもの | 最大 |
| --- | --- | --- |
| コントローラ | 走査の窓の外のアドバタイズ（3.2 節の割合）。一括受信の結果の、端末のバッファの上限を超えた分 | 窓と端末による |
| 一括受信の待ち | プロセスの強制終了の時点でコントローラが持ち、まだ渡していない結果 | 約 5 秒 |
| まとめ | 強制終了の時点で開いている連なりと、待ちの中の結果 | 約 5 秒 |
| 保存 | 受け入れた後は、測位と同じ（退避、緊急の予備、失われた行の数） | 測位と同じ |

一括受信の間に強制終了すれば、最後の約 10 秒が失われうる。測位のメモリの待ちと同じく、失われた行としても数えられない既知の制約である。

## 5. 位置の補正

### 5.1 使える制約

| 観測 | 制約 | 大きさの目安 | 使う条件 |
| --- | --- | --- | --- |
| 交差点の受信 | 交差点の位置から半径 R 以内である確率が高い | R = 70 m（到達範囲）+ 座標の誤差。実機の受信の距離の分布で決め直す。誤差の上限ではない | 交差点が信頼でき、受信が近さの裏付けを持つ（下記） |
| 二つの交差点の同時の受信 | 二つの円の共通部分 | 交差点の間隔による | 両方が同じ条件を満たす |
| RSSI の極大 | 送受信部に最も近づいた時刻 | 時刻だけ。距離には使わない | 参考 |
| 信号待ちから青で歩き出す | 横断歩道 k の上、その方位 | 横断歩道の幅（約 5 m）、方位 ±15° | 横断歩道 k の方位を学習済み（段階 2） |

条件は二つに分ける。
一覧の座標との一致は、座標が正しいことを示すが、送信機が近くにあることは示さない。
遠くの交差点の正しい座標を送る偽の送信機は、一つ目の条件を満たす。

1. **交差点の信頼。** 種別 1 の座標が一覧の交差点の座標と 30 m 以内で一致する（一覧は独立な情報源である）。一覧にない交差点では、3 日以上の受信で座標が同じ（10 m 以内）で、そのたびに受信中の良い測位（精度 20 m 未満）がその座標から R 以内にある。
2. **その受信の近さの裏付け。** 受信の 60 秒前から受信の間に、精度 50 m 未満の測位（GNSS か Wi-Fi・基地局）が交差点から R + 精度 以内にある。または、最後の裏付けのある位置からの移動が、歩行の速さ（3 m/s）× 経過時間 + 精度 で交差点に届く。

二つを満たさない受信は、記録と信号待ちの表示にだけ使い、位置には使わない。
精度が R 未満の GNSS の測位がある間は、どの補正も行わない。

開けた場所の GNSS（数 m）より半径 70 m の円は粗い。
都市の谷間の GNSS の誤差（報告書の測定で 10〜20 m）も、この円では直せない。
円が効くのは、測位が大きく外れた場合と、GNSS がない場合だけである。

### 5.2 既存の推定との統合

保存した測位（`fixes`）は書き換えない。PICS から作った点も `fixes` に書かない。

| 時点 | 処理 | 対象のコード |
| --- | --- | --- |
| 記録の時点 | PDR が動いている（屋内の歩行）間に、5.1 節の二つの条件を満たす受信があり、PDR の推定が円の外にあれば、円周上の最も近い点に寄せ、精度を R とする。以後の PDR の測位は従来どおり `fixes` に入る（`provider` は `pdr`） | `Pdr.onAnchor`（`onNetworkFix` と同じ扱い）、`LoggerService` |
| 表示の時点 | `Geo.removeSpikes` の後、受信の区間に重なる測位のうち、交差点から R + 2 × 精度 より遠いものを外れ値として除く。経路の描画と距離に使わない。区間の測位の過半数が R + 2 × 精度 以内にある場合だけ除く（測位の多くと合わない交差点では何もしない） | `TimelineBuilder` の前処理（`PicsAnchor.prune`）。引数の受信が空なら今と同じ結果 |
| 表示の時点 | 信号待ちをタイムラインの歩行の区間に重ねる。区間の切り方と移動手段の判定（`ModeClassifier`）は変えない | `PicsEvents`、画面 |
| 段階 2 | 交差点ごとに、横断歩道の番号と、青に変わった後の歩き出しの方位（良い GNSS か PDR）の組を数える。同じ番号で 5 回以上、方位が ±15° に集まれば、その番号の横断歩道の方位とする | `PicsCrosswalks`（`sites.json` に保存） |

信号待ちは最長 4 分で、滞在の判定（`StayPointDetector`）の条件より短い。
歩行の区間の中の停止として残り、滞在にはならない。

### 5.3 期待できる精度

| 場面 | 期待 |
| --- | --- |
| 開けた場所 | 改善しない（GNSS が円より正確） |
| 都市の谷間 | 交差点から 70〜100 m 以上外れた測位を除く。10〜20 m の誤差は残る |
| 建物や地下から交差点へ出た直後 | PDR の誤差の上限が R になる |
| 段階 2（横断歩道の学習の後） | 横断の時刻に、横断歩道に直交する方向で 5 m 程度。学習が成り立つかは未確認 |

### 5.4 評価の方法

1. **受信の距離。** 最高精度で開けた交差点を歩き、精度 5 m 未満の測位を真値として、受信の有無と RSSI を交差点からの距離ごとに集める。99 % の受信が収まる距離を R とする。
2. **外れ値の除去。** 真値の歩行に、都市の谷間の記録から取った誤差の系列を加え（`core` の `sim`）、除去の前後で経路の長さと点の誤差を比べる。
3. **誤った除去。** 真値の歩行で除いた良い測位の数を数える。0 でなければ R を広げる。
4. **信号待ち。** 実際の横断で待ち時間をストップウォッチで測り、求めた値と比べる。
5. **横断歩道の学習。** 同じ交差点を 10 回以上渡り、学習した方位を地図の横断歩道の向きと比べる。

### 5.5 危険と対策

| 危険 | 影響 | 対策 |
| --- | --- | --- |
| 座標の誤り（設定の誤り、符号や桁の誤り、試験の値） | 位置を誤った方へ制約する | 一覧との一致か、日をまたいだ一致を求める（5.1 節）。矛盾すれば補正に使わず、端末診断に示す |
| 送受信部の位置と交差点の位置の違い | 円の中心がずれる | R に含める。受信の距離の分布で決める |
| 同じ ID の複数の送受信部 | RSSI で距離が分からない | RSSI を距離に使わない。アドレスごとに受信を分けて記録する |
| ID の重複（全国で一意でない場合） | 遠くの交差点と取り違える | 交差点を（ID、位置）で区別する（4.3 節）。ID だけで場所を決めない |
| RSSI の揺れ（体、向き、反射） | 距離の推定が当てにならない | 距離に使わない |
| 偽のアドバタイズ（認証がない） | 位置を動かされる。記録を埋められる。待受の範囲を広げられる | 近さの裏付けを求める（5.1 節）。良い GNSS があれば補正しない。外れ値の除去は測位の過半数と合う場合だけ。受信した座標だけでは待受の範囲に加えない。受け入れの上限（4.1 節） |
| `0x01CE` の別の製品 | PICS でない受信が混ざる | 長さと種別が合わない受信は記録するが、事象と補正に使わない |
| 時刻の誤り | 待ちと変化の時刻がずれる | `elapsedRealtimeNanos` の時刻を使う。一括受信でも結果ごとの時刻を使う |

## 7. プライバシーと法令

### 7.1 受信だけに限る仕組み

約束するのは「接続しない、アドバタイズしない、青時間延長要求を送らない」ことである。
電波を一切出さないことまでは約束しない。
Android の既定の走査は能動的であり、スキャンできるアドバタイズに scan request を送りうる。
PICS は `ADV_NONCONN_IND`（スキャンできない）なので、PICS の路側機には送らない。

- マニフェストに `BLUETOOTH_CONNECT` と `BLUETOOTH_ADVERTISE` を宣言しない。Android 12 以降、この二つがなければアプリは接続もアドバタイズもできない。
- コードで `BluetoothLeAdvertiser`、`connectGatt`、`BluetoothGatt` を使わない。
- 使える端末では受動的な走査（`SCAN_TYPE_PASSIVE`、version 36.1 以上）を選び、端末診断に走査の種類を示す。
- core の試験（`ReceiveOnlySuite`）が、マニフェストとアプリのソースにこれらがないことを確かめる（`DbOpenSuite` がソースを検査するのと同じ方法）。ソースの検査は無線の動作の証明ではない。
- 青時間延長要求は実装しない。延長の受付の状態を読めても、要求の形式は調べない。

### 7.2 端末内と同期

- 受信と事象の計算は端末の中で行い、外部のサービスには送らない。一覧は APK の中にあり、取得の通信もない。
- `pics_adv` はほかの記録と同じく暗号化して同期する。運用者は中身を読めない。
- 残る漏れ：運用者に見えるのは `archive` stream の batch の数、大きさ、送信の時刻であり、表の名前と日付は暗号文の中にある。受信のない日は `pics_adv` のファイルができないので、batch の数が日によって 1 つ増減し、受信した日を確からしく推測される可能性がある。0 行のファイルを毎日作っても、大きさ、送信の時刻、後の世代と月の統合の違いは残り、漏れは消えない（[決定の事項](#9-決定の事項)）。
- 記録するのは `0x01CE` のアドバタイズだけである。ほかの機器（利用者や他人の端末、イヤホン）の受信は記録しない。ただし `0x01CE` は PICS 以外の製品も使いうる会社 ID であり、そうした機器の受信も記録に入りうる。
- リポジトリは公開されている。試験の値は合成したものを既定とする。実機の受信の 16 進のダンプは、受信した交差点、時刻、送信元のアドレスを含み、所有者の通った場所を示す。入れる場合は、交差点を意図して選び、時刻とアドレスを除く（[決定の事項](#9-決定の事項)）。

### 7.3 交差点の一覧の利用条件

- 警察庁のウェブサイトの利用規約は、特記がない限り、コンテンツを公共データ利用規約（第 1.0 版）（PDL1.0）に準拠した条件で利用できるとする。PDL1.0 は政府標準利用規約の後継である。一覧のページに別の権利表記はない。
- 出典の記載が要る。編集・加工した場合は、その旨も記載し、国が作成したかのような態様で公表しない。
- e-Gov データポータルの同じデータセットには、利用条件の欄がない。

出典の記載は次のとおりとする（`tools/ATTRIBUTION`、「設定 > データの出典」）。

```text
出典：警察庁ウェブサイト「全国高度化PICS整備交差点（CSV版）」（令和8年4月1日現在）
https://www.npa.go.jp/bureau/traffic/seibi2/annzen-shisetu/utms/pics.html
を加工して作成（文字コードと列の変換。ashidori）
```

`ble-pics-viewer`（MIT）のコードは使わない。
試験の一部に同リポジトリの試験の値を使う場合は、そのファイルに著作権の表示と MIT の許諾の文を置く。

### 7.4 電波法

本節は法的な判断ではない。参照した条文と行政の説明を記す。

- 電波法 59 条は「特定の相手方に対して行われる無線通信」を傍受して、その存在や内容を漏らし、または窃用することを禁じる。罰則は 109 条にある。
- 高度化PICS の下りは、報告書が「ブロードキャスト型」とする、不特定の携帯電話に向けた送信である（2018 5.3.4）。警察庁は整備交差点を公開し、2019 年の報告書は、アプリの作成事業者が交差点 ID などの静的情報を参照してアプリに登録する流れを示す。
- 総務省の FAQ は、無線 LAN やコードレス電話の通信について、内容を聞いただけでは電波法に違反するとは言い切れないが、漏らしたり盗用したりすると 59 条に違反するとする。
- 以上から、ashidori の扱いは「特定の相手方に対して行われる無線通信」に当たらない放送型の送信の受信と考えるが、判断は所有者が行う。送信の機能を持たないことは 7.1 節の試験で保つ。

### 7.5 安全

- 信号の色の表示は、最後の受信から 2 秒以内だけ色で出し、それより古ければ灰色にする。古い状態を今の状態に見せない。
- 音や振動による通知、ウィジェット、残り時間のカウントダウンは作らない。残り時間は秒ではなく目盛りであり、横断の判断に使える精度ではない。
- 試験の送信機は会社 ID `0x01CE` を使わない。PICS と同じ形のアドバタイズを道路の近くで出すと、信GO! の利用者に誤った信号の状態を伝えうる。デバッグ版だけが試験用の会社 ID `0xFFFF` も受け付け、試験の送信は屋内の机上で行う。

### 8.2 エミュレータ

エミュレータには BLE がない。
`DebugReceiver` に操作を足し、走査の callback と同じ入口（`PicsIngest.onResult`）に値を渡す。

```sh
# アドバタイズ 1 件（会社 ID を除いた値）
adb shell am broadcast -n net.sksat.ashidori.debug/net.sksat.ashidori.DebugReceiver \
  -a ashidori.debug.PICS --es hex 580102FF000000CD08494351FFFFFFFF0000000000000000 \
  [--ei rssi -62] [--es addr 02:00:00:00:00:01] [--ei company 462] [--el at <ms>]
# 合成の横断（接近、赤 40 秒、青、歩き出し）を測位と動きとともに流す
... -a ashidori.debug.PICS_WALK [--es site <一覧の交差点名>] [--ei wait 40]
# 走査の判定の入力と結果を動作の記録に出す
... -a ashidori.debug.PICS_STATE
```

- 注入した行は `scan` が `debug` になる。
- 確かめること：連なりの行が SQLite に入る、日のまとめで Parquet になる、修復の中断の試験（`files/maintenance/crash-after-rename` に `pics_adv`）、退避ファイル（`SPILL_SMALL` と同じ方法）、タイムラインの信号待ち、端末診断の表示、上限を超えた注入で記録が止まらない。

| 公式の規格 | UTMS協会と警察庁への開示の問い合わせはしない |
| 信号の色 | ステータスに出してよい。6 章と 7.5 節の鮮度の扱い（2 秒以内だけ色、古ければ灰色） |
| 既定の状態 | オフ。設定でオンにし、そのときに「付近のデバイス」の権限を求める |
| 実機のダンプ | 公開のリポジトリには入れない。試験の値は公開済みの例と合成した値だけ |
| 同期のメタデータ | 受信した日にファイルが増えることを許容する（ファイルの種類は暗号化の内側にあり、運用者に見えるのは数と大きさだけ） |
| 位置の補正 | 段階 1（外れ値の除去と PDR の寄せ）から始める |
| 記録の外での受信 | しない（PendingIntent の走査は使わない） |
| 静止中の便乗 | 続ける。4.1 節の静止中の長さで行を抑える |
| ブラウザの表示 | 後で検討する |
| 一覧にない交差点 | 近さの裏付けと日をまたいだ一致の後に待受の範囲に加える |
